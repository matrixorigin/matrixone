# Independent engine and local service reproduction

Install the tested Python dependencies in an isolated directory:

```bash
python3 -m pip install --target /tmp/variant-deps --pre duckdb==2.0.0.dev2610011535 pyarrow==26.0.0 pymysql
export PYTHONPATH=/tmp/variant-deps
export MO_VARIANT_INTEROP_DIR=/tmp/variant-fixtures
python3 test/variant_interop/duckdb_instances.py generate --dir "$MO_VARIANT_INTEROP_DIR"
go test ./pkg/sql/colexec/external -run '^TestParquetVariantDuckDBInstance$' -count=1
go test ./pkg/frontend -run '^TestParquetVariantIndependentInstanceExport$' -count=1
python3 test/variant_interop/duckdb_instances.py verify --dir "$MO_VARIANT_INTEROP_DIR"
```

These files are independently generated by a running embedded DuckDB. `automatic` means default automatic shredding, not unshredded. The explicit schema leaves the drift attribute in the residual. Native Go dependencies and normal project CGO flags are required.

For Doris, run the pinned all-in-one image on local SQL port 19030 and BE HTTP port 18040 with the fixture directory mounted at `/interop`, one backend and replication_num=1. Configure `enable_outfile_to_local=true` in the **test** FE. Allocate 1.5 GiB FE heap / 2 GiB BE memory and sufficient file descriptors; keep the environment's required network proxy. This environment's launcher proxy rejection was removed only in the test-container launch scripts; host kernel parameters were left unchanged and the launcher's optional ulimit precheck skipped for this small workload.

```bash
python3 test/variant_interop/doris_native_probe.py --dir "$MO_VARIANT_INTEROP_DIR"
python3 test/variant_interop/doris_json_bridge.py --dir "$MO_VARIANT_INTEROP_DIR"
go test ./pkg/sql/colexec/external -run '^TestParquetDorisInstanceExport$' -count=1
```

The native probe exits with a failure status for content incompatibility and explicitly checks the observed **failed semantic compatibility** of this version even when Stream Load says Success. The bridge counts missing/type-changed source fields and exports what Doris actually returned. A successful MO import of that export does not recover identities Doris already changed. Use a fresh fixture directory for each Doris export, since OUTFILE will not overwrite files. All table writes use the isolated `mo_variant_interop` test database.

Build and start the modified MO service with a fresh local launch configuration. Then:

```bash
python3 test/variant_interop/mo_local.py --port 16001 --state /tmp/variant-fixtures/mo-expected.json
# Stop/restart the service on the same data directory, then repeat:
python3 test/variant_interop/mo_local.py --port 16001 --state /tmp/variant-fixtures/mo-expected.json --verify
```

The script uses the isolated `variant_local.traces` table and deliberately recreates it in the first phase. It checks actual READ-COMMITTED isolation rather than assuming repeatable reads. It verifies precise DECIMAL, path-only queries, full document queries and SQL/JSON NULL after flush, update, rollback, deletion and restart. JSON_EXTRACT_STRING only accepts JSON string values; numeric latency uses JSON_EXTRACT_FLOAT64.

For complete process-to-process file ingestion/export through MO SQL:

```bash
python3 test/variant_interop/mo_files.py --port 16001 --dir "$MO_VARIANT_INTEROP_DIR"
python3 test/variant_interop/duckdb_instances.py verify --dir "$MO_VARIANT_INTEROP_DIR" --file mo-sql-variant.parquet
```

This loads and flushes both DuckDB files and the Doris export in the built MO service, checks every full document and exact DECIMAL path value, and verifies the SQL OUTFILE result in DuckDB.

For the PR #30071 review regressions, run the updated source build:

```bash
go test ./pkg/objectio ./pkg/objectio/ioutil ./pkg/sql/plan ./pkg/sql/colexec/table_scan -count=1
python3 test/variant_interop/review_json_subcolumns.py --port 16001
```

The SQL script creates a uniquely named `review_json_30071_*` database and drops only that database on exit. It checks C0/DEL/C1 and quoted/Unicode keys after flush, full-document preservation, 63/64/65 JSON-column queries, exact 64 KiB projection-contract boundaries and JSON-escape expansion beyond the limit. It requires PyMySQL and the local test account `root`/`111`; it does not start or configure a server. The native Go regression also poisons allocator buffers on final release to exercise the borrowed BOOL ownership boundary that ordinary MemoryFS alone cannot expose.

For exact-JSON remote admission, use the repository's native test wrapper:

```bash
.agents/skills/mo-dev/scripts/mo-cgo-test -p 1 -count=1 ./pkg/defines ./pkg/pb/plan ./pkg/sql/plan ./pkg/sql/compile
.agents/skills/mo-dev/scripts/mo-cgo-test -p 1 -count=1 -run '^TestExactJSONWorkerWire' ./pkg/sql/plan/function
.agents/skills/mo-dev/scripts/mo-cgo-test -p 1 -count=1 -timeout=300s -run '^TestExactJSONProtocolSQLFallbackAndUpgrade$' ./pkg/tests/sqlintegration/multicn
```

The last test owns a fresh two-CN cluster and four rows. It checks results and
actual worker addresses with v113 advertised, then with v114 restored. Both CNs
run the current binary. To reproduce the independent old executor witness,
copy only `pkg/sql/plan/function/exact_json_worker_contract_test.go` into a clean
worktree at pre-feature main `5d971d07a7c5a52a71f2c10390b109cebf5c0825`, build
its native libraries through `make cgo`, and run the same worker-wire selection.
The large positive/negative decimals and function 598 must fail there;
`0.125` must pass. This deliberate baseline failure is not a current-head pass.
Real old/new rolling-upgrade and R1 release-cost/restore gates remain separate.
