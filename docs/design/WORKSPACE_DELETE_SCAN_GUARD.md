### Evidence, invariant and placement

The supplied profile identifies repeated `Transaction.deleteTableWrites` work (5.52s cumulative CPU), especially vector extraction and block-ID checks, with no matches dominant. No matches alone does not establish guard eligibility or wall savings. Existing `colexec.TxnWorkspaceSegment` and `IsDeletionOnTxnUnCommitInMem` (`pkg/sql/colexec/cn_segment_map.go:30–84`) distinguish raw workspace row IDs. `NewTxnWorkSpace` (`disttae/types.go:739`) initializes that segment; INSERT `writeBatch` allocation (`txn.go:371`), `batchAllocNewRowIds` (`:2010`) and merged-INSERT regeneration (`:2147`) retain it. Persisted INSERT metadata is excluded by the existing scan. Thus a legal raw workspace INSERT cannot match a delete key outside this namespace.

Choose the guard **inside `pkg/vm/engine/disttae/txn.go:Transaction.deleteTableWrites`**, after its original Lock/deferred Unlock. Read W=`len(txn.writes)` under that lock and B=`len(deleteBlkId)`. Only when **B==1 && W>1**, inspect the sole block key. If its segment is not `colexec.TxnWorkspaceSegment`, return; otherwise execute the entire original scan unchanged. For B==0, B>1 or W<=1, do not iterate block-map keys: take the original scan. Use `blockID.Segment().EQ(&colexec.TxnWorkspaceSegment)`; a one-key range is sufficient, with no flag needed. A false-valued workspace key conservatively selects the original scan, which retains the boolean membership check. No unlocked transaction-state read, table/block index, caller change or new helper API.

Keep `deleteBatch` unchanged, including persisted-uncommitted bookkeeping, both shrink operations, map construction, and selection-slice ownership. Its block map can still include persisted-uncommitted rows already removed from the input batch: scanning that superset is safe because such keys cannot create a false negative. A workspace key anywhere conservatively selects the old path. Leave block/range filtering, match counters, selection sort/compact, and slow-path locking unchanged; do not combine this with a single-block-assumption fix.

Proof obligation: in every legal state admitted by the existing writers, absence of workspace-segment block keys means the old scan's mandatory first-row block-membership check cannot succeed, so it cannot increment `mp` or add a batch selection. This proof does not require consistency between `mp` and the block map: the old block filter is itself necessary. The guard therefore elides only a no-op. An INSERT producer accepting arbitrary non-workspace raw row IDs would invalidate this approval: stop and re-review if discovered. Synthetic test workspace rows must obey the real allocator contract; do not weaken existing expectations to accommodate the optimization.

Synchronization: retain the original mutex acquisition on every call, including the no-match return, with deferred Unlock. Both the cardinality read and the old scan are protected. The sole production caller, `deleteBatch`, owns the block map and does not mutate it concurrently; transaction locking does not newly authorize concurrent input-map mutation. The optimization targets repeated vector extraction/write traversal, not lock avoidance.

### Alternatives, cost and lifecycle

The caller-side boolean in `deleteBatch` avoids an extra traversal, but couples the optimization to caller filtering and expands the differential boundary. Defer it unless measured overhead warrants a revised design. A new table/block index is rejected: compaction, spill, rollback and row-ID regeneration would require new invalidation state. Existing approximate insert counts exclude system tables and are not a general replacement for this proof.

A4 adds only constant-time cardinality checks and at most one namespace comparison, with O(1) extra space and no allocations, logging, goroutines or new resources. Multi-block and sparse-workspace requests never incur a new map traversal. The W>1 condition preserves the measured one-write/one-block scan choice rather than paying namespace lookup to avoid at most one entry. A4 deliberately forgoes potential multi-block savings to remove the measured systematic multi-block scan overhead. Constant-time does not mean universally faster: a two-entry unrelated workspace can still be cheaper to scan than to check the sole map key. Disclose that measured constant cost, and preserve mutex/map ownership and transaction cleanup. Reverting the isolated optimization requires no migration.

## Measurements and A4 decision

The prototype timings in the next paragraphs used a functionally equivalent but not statement-identical reference. They are retained as investigation history, not final comparative performance proof. The accepted final reference matches the original method's signature, statement order, branches and scratch-slice reuse exactly; final measurements are recorded below.

Task-owner benchmark evidence, three samples in `/tmp/mo-testinfra-delete-benchmark.log`: A2 W=0/B=256 reference about 5.2ns versus guard 1,640ns; W=1/B=256 about 19.7ns versus 1,620ns; W=1/B=1 about 18.6ns versus 27ns. At W=1,024, B=1 reference about 16.2us versus 27ns; B=256 about 16.8us versus 1.67us. Mixed W=1,024/B=2 reference 16.25us versus 16.43us (about 1%). All reported zero allocations. These are method-level measurements, not whole DELETE or suite costs.

The sparse case is reachable: committed-row deletion calls `deleteBatch` before the current DELETE is appended, and its batch can span many persisted blocks while the workspace has zero/few writes. Caller map construction is common to both versions and does not erase the incremental scan. This evidence originally motivated A3; the subsequent boundary measurements below motivate the narrower A4 correction.

Exact A3 boundary measurements in `/tmp/mo-testinfra-delete-a3-boundary-benchmark.log` expose systematic costs at W=256/B=255: unrelated persisted reference 1.26–1.32us versus A3 1.75–2.02us; unrelated mixed 1.29–1.51us versus 1.98–2.07us; same-table mixed 4.45–5.08us versus 5.35–5.92us. All allocate zero. The isolated run `/tmp/mo-testinfra-delete-a3-isolated-benchmark.log` also showed the sparse scaling regression fixed and strong dense single-block benefit. These logs were inspected by the design reviewer. Earlier broad acceptance of A3's tradeoff is superseded by A4 at the owner's request for a narrower correction.

Choose B==1 rather than another numeric tuning threshold: it is the exact one-key case and needs no scan proportional to delete cardinality. It remains a general workspace no-op elimination, with no test name, SQL shape or data-boundary special case. Dense single-block deletion is a demonstrated favorable microbenchmark and a plausible explanation for the DML benefit; final A4 unchanged DML evidence must confirm retained public-path improvement. Do not infer that every expensive DML invocation is single-block without evidence.

Required final A4 validation, replacing rather than accumulating A3 gates:

- Differential cases for B==1 with W=0,1,2/many; persisted key early return and workspace-key fallback; B=0 and B>1 unchanged fallback. Retain all existing false-value/inconsistent-map, counter, selection, caller and lifecycle controls. All prior test identities and assertions stay.
- Focused reference/A4 benchmarks for W=0,1,2,1024 with B=1, including unrelated and same-table writes plus a workspace-key fallback. Reuse existing benchmark cases. Run the already-existing W=256/B=255 mixed/unrelated controls and B=256/257 bypass controls to establish that A4 removes the extra multi-block traversal. No expanded matrix or arbitrary threshold search is requested.
- Run affected final-source functional/race owning-package checks and the planned unchanged full-DML comparison sequentially using the required native wrapper. Existing A2/A3 evidence stays historical; reuse baseline and unrelated infrastructure results. Do not launch duplicate concurrent native/cluster validation.
- Final source review confirms original locking and scan remain intact and no caller/data/oracle changes. Document residual constant microbenchmark overhead rather than claim universal non-regression. Delivery still requires preserved coverage and retained target benefit; whole-suite performance remains a separate claim.

The caller-fused predicate remains deferred because it changes the caller loop and adds per-row work across all delete batches. A new index remains rejected for invalidation complexity. No B<=N tuning constant, B/W ratio adjustment, or additional heuristic is authorized. The A4 decision closes algorithm selection unless a concrete correctness failure or failure to retain the intended improvement invalidates its evidence.
