# MatrixOne 表级 TTL 第一版

基础提交：`87ade1b8fb`（当前工作区代码）；实现和资料核验日期：2026-10-13。

## 功能与使用

为永久、普通、非分区用户表声明一个时间列和固定保留时长。后台任务自动提交事务 DELETE；首次清理和后续进度取决于任务调度、锁竞争与执行预算。

```sql
CREATE TABLE events (
    id BIGINT PRIMARY KEY,
    event_time DATETIME(6),
    payload VARCHAR(256)
) TTL event_time + INTERVAL 7 DAY DELETE;

SHOW CREATE TABLE events;
ALTER TABLE events MODIFY TTL event_time + INTERVAL 30 DAY DELETE;
ALTER TABLE events REMOVE TTL;
-- REMOVE 后可修改、重命名或删除原时间列，再重新声明策略。
ALTER TABLE events TTL event_time + INTERVAL 1 WEEK;
```

`DELETE` 关键字可省略。`TTL` 仍可用作普通列名/表名；`MODIFY ttl INT` 和 `MODIFY COLUMN ttl INT` 保持原含义。第一版的 TTL ALTER 必须单独执行，不能与其他 ALTER 子句混合。

支持 `DATE`、`DATETIME`、`TIMESTAMP`，含可空列与微秒精度。支持 `SECOND`、`MINUTE`、`HOUR`、`DAY`、`WEEK`；时长必须是正整数，最大为 `100 × 365` 天。不接受 MONTH/YEAR、复合间隔、任意表达式、条件 DELETE、列级 TTL、聚合或存储迁移。

- 行的过期条件：`时间列 + 保留时长 <= 本轮 UTC 时间`；等于截止时间的行过期。
- NULL 时间值保留；未来时间值保留。晚到的过期数据允许写入，在后续清理中处理。
- DATE 按 UTC 零点计算；DATETIME 是无时区值，TTL 将其按 UTC 墙上时间解释；TIMESTAMP 按绝对时间计算，插入时遵循客户端时区转换。
- 清理前，过期行仍可查询。没有额外的查询时过滤。
- 删除通过普通 DELETE 路径维护主键、唯一索引、其他索引和事务可见性。逻辑删除提交与底层对象回收分离，历史版本仍受已有快照/PITR/GC 规则管理。
- 临时表、外部表、cluster 表、分区表、系统库和已有外键引用的父表不支持启用 TTL。后续添加外键仍受正常 DELETE 约束检查，可能阻止清理。
- 必须先 REMOVE TTL 才能修改、重命名、CHANGE 或 DROP 时间源列。普通其他列的 COPY ALTER、表重命名、CREATE TABLE LIKE 和恢复的 CREATE DDL 使用已有元数据路径。

## 参考实现与取舍

| 系统 | 官方实现要点 | 第一版采用的思路 |
|---|---|---|
| [ClickHouse TTL](https://clickhouse.com/docs/concepts/features/operations/delete/ttl) | 表/列 TTL；在 merge 时异步删除，还支持迁移和聚合 | 相似的表级声明语法、异步删除语义；暂不进入 MatrixOne 的 merge 层 |
| [DuckDB DELETE](https://duckdb.org/docs/current/sql/statements/delete) | SQL DELETE 与 CHECKPOINT 空间回收是不同过程 | 重用事务 DELETE，区分逻辑删除与物理回收；不假设 DuckDB 已有同样的原生 TTL 调度接口 |
| [Snowflake Storage Lifecycle Policy](https://docs.snowflake.com/en/user-guide/storage-management/storage-lifecycle-policies) | 自动执行行过期/归档策略，增量分批处理；克隆的策略行为另有规定 | 持久化策略、后台分批、预算与故障隔离；本版没有独立可复用策略对象或归档层 |
| [Snowflake 策略表达式](https://docs.snowflake.com/en/sql-reference/sql/create-storage-lifecycle-policy) | 策略表达式确定待过期的行 | 第一版限制为绑定时间列与固定时长，减小表达式安全和依赖范围 |
| [InfluxDB 保留策略](https://docs.influxdata.com/influxdb/v2/reference/internals/data-retention/) | 定期删除整体过期的 shard group | 采用后台最终清理；粒度保持行级，避免误删同对象中的新数据 |
| [Timescale 保留策略](https://www.tigerdata.com/docs/reference/timescaledb/data-retention/add_retention_policy) | 按 chunk 删除，自动化保留策略管理 | 完整过期分区/对象的快速回收作为后续优化方向 |

Snowflake 的 Storage Lifecycle Policy 与 Time Travel 的历史版本保留期是不同功能。MatrixOne TTL 也不替代 PITR/快照保留策略。与 Snowflake 的克隆规则不同，本版 `CREATE TABLE LIKE` 通过 SHOW CREATE 重建 TTL 声明并继承策略；应显式 REMOVE TTL 才能取消目标表的过期清理。

选择 SQL DELETE 而非直接操作 TAE 对象/墓碑，是为了第一版复用现有索引、外键、MVCC 与事务路径。代价是扫描与锁竞争开销，适合先建立正确语义和可验证行为；不宣称已经达到分区丢弃的吞吐。

## 持久化与执行

策略保存在已有的表属性 `mo_ttl` 中，经 `StreamConfigsDef` 写入 `mo_tables.constraint`，不新增系统表或 SchemaExtra 字段。JSON 格式有明确版本：

```json
{"version":1,"column":"event_time","seqnum":1,"seconds":604800}
```

CREATE 绑定物理列顺序对应的序号，ALTER 使用当前目录列身份。策略在计划深拷贝、protobuf 序列化、CN 目录缓存和重启后保持可读；SHOW CREATE 将其渲染为 TTL 子句，不暴露内部 JSON。TTL ALTER 使用已有 ReplaceDef/UpdateConstraint 路径，只在策略变化时发布约束更新。

CN 为任务框架注册新的 `TableTTL = 17` executor 和 `table_ttl` cron，使用 stopper 管理注册重试及取消。任务元数据限制调度并发为 1；重复调用仍由事务校验保护。

默认参数（`pkg/sql/ttl/worker.go`）：

| 项目 | 默认值 |
|---|---:|
| 调度表达式 | `0 * * * * *`，每分钟触发 |
| 单批删除上限 | 1024 行 |
| 单表每轮批次数 | 8 |
| 单表时间预算 | 5 秒 |
| 整轮时间预算 | 50 秒 |
| 锁等待 | 1 秒 |
| 可重试事务错误 | 最多 8 次完整事务尝试；有界退避 |

这些是代码默认值，第一版没有新增 SQL/session/config 调参接口。`WorkerOptions` 可供内部调用或测试设置；不同机器负载下的完成时间不是固定 SLA。

一次执行流程：

1. 系统账户发现用户表，读取账户 ID、物理表 ID、版本、库/表名和策略约束；检查长度并跳过无关的索引/FK 编码。
2. 固定本轮 UTC 时间；按轮次旋转表的起点，避免预算耗尽时总是从第一张表开始。
3. 每批在目标账户下开启新的 pessimistic RC 事务，获取目标表锁。
4. 锁后重新核对账户、物理表 ID、版本与完整约束字节，再验证源列名称、序号、隐藏属性和序列化列类型。
5. 执行 `DELETE ... WHERE 时间列 <= CAST('固定截止时间' AS DATETIME(6)) LIMIT 批量上限`，提交并等待 logtail 应用。
6. 重试时重新开启整个事务、重新校验，不仅重跑 DELETE。错误匹配使用 `errors.As`，可识别执行器包装的 RC 错误。失败的表不阻止其他表；失败保存在任务结果中。

DROP/CREATE 同名表、策略变更、表改名和版本变化会使旧候选失效。TTL 获取的是短事务中的独占表锁，因此该批清理会暂时串行化同表写入和 DDL；读取遵循已有事务语义。没有新增常驻表级 goroutine。

目录发现是 O(用户表元数据)，每轮每表最多 8192 行是计数上限而不是吞吐保证。初版没有专门的过期索引、持久化扫描游标、对象级快删或 TTL 指标。事务失败、预算不足或暂停后的积压由后续任务继续处理。


## 部署边界和后续工作

该版本要求相关 CN 使用支持 TTL 的构建。旧 CN 不识别新增语法和 executor；尚未添加独立的集群协议能力门禁，不建议混合版本开启 TTL。当前已覆盖单 CN 的真实事务、索引、租户与重启；多 CN/TN 故障、机器时钟漂移、大规模积压吞吐、物理磁盘回收速度未作为通过的验证结论。

后续可增加：用户可配调度与批量、过期积压/进度指标、按时间列的索引扫描、完整过期分区/对象快删、日历 MONTH/YEAR 的明确月末语义、条件 TTL、源列重命名依赖重写，以及集群版本门禁。这些能力不在第一版声明范围内。
