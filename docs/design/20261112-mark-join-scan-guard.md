## Problem and contract

For a wide base table, an uncorrelated `key IN (subquery) OR alternative` predicate may be implemented as a MARK hash join followed by an OR filter. The MARK preserves all probe rows until the OR is evaluated. When only a few rows pass, that plan can materialize many wide rows before filtering them.

A 61,000-row, two-512-byte-payload, single-CN fixture on the 4.2 base `51c0af67` read about 69.6 MiB at the MARK input before returning one row. A diagnostic literal-OR query, whose subquery value was already known, still visited the narrow rows but read about 5.82 MiB and returned one row from the scan. The literal query is not a general rewrite; it shows that a scan-local row predicate can allow the existing selected-row reader to defer wide columns. In the same fixture, changing `SELECT * FOR UPDATE` to `SELECT id FOR UPDATE` reduced warm elapsed time from about 133–140 ms to 5.25–5.52 ms. Removing `FOR UPDATE` from the wide query did not materially change the result. These observations identify a local wide-materialization cost; they do not attribute every production delay to the same cause.

The optimization must preserve the result multiset, SQL NULL semantics, the tenant/workspace residual, the original subquery snapshot and evaluation, and lock targets and refresh behavior. It may reduce the candidate rows entering the original MARK, but the original MARK, OR filter, and lock operator remain the final authority. The optimization is optional; unsupported shapes and incomplete runtime data execute the original plan.

## Decision and correctness argument

Let `M(r)` be the positive equality MARK for probe row `r` over the original subquery result `S`, and let `B(r)` be the other OR arm. When a complete exact set of joinable keys from the existing hash build is available, evaluate the following **row-only guard** in the base scan:

```text
G(r) = (probe_key(r) IN exact_keys(S)) OR B(r)
```

A row accepted by `M(r) OR B(r)` must have either `B(r) = TRUE` or `M(r) = TRUE`. In the latter case, equality requires a matching joinable key to be present in `S`, and the exact producer/consumer encoding makes the membership test true. Therefore every row accepted by the original WHERE predicate passes the guard. SQL FALSE and UNKNOWN may be represented differently by an optional row guard only if neither is accepted; the original MARK and OR still evaluate every surviving row. The guard neither unions two independently executed branches nor runs `S` a second time, so overlap and duplicate rows do not introduce duplicate results.

The build message maps to the guard as follows:

| Build message | Scan behavior |
| --- | --- |
| Complete valid IN keys | Evaluate `(probe_key IN keys) OR B` as a scan row predicate. |
| DROP for a complete empty set of joinable keys | Evaluate `B` alone; B-only rows must not be dropped. |
| PASS, unsupported encoding, exceeded budget, or a message failing the consumer's checks or binding | Omit the guard and run the original plan. |
| Producer failure or cancellation | Preserve the existing query error or cancellation and waiter/reader cleanup; do not infer an empty set. |

NULL-only and mixed-NULL builds retain the MARK's normal null tracking. An empty joinable key set does not mean that the other OR branch is empty. The guard is appended to the scan's runtime **row** filters, never installed as an independent PK, range, zone-map or block predicate. Existing runtime filters and ordinary tenant predicates remain in place. The late-materialization reader loads the guard's columns first and then reads wide payload for its survivors when that reader is available; tracing, reader summaries and unsupported readers retain their existing eager behavior.

## Eligibility and ownership

Installation occurs in `Compile.installMarkScanGuard` after physical scopes have been compiled. It does not change the optimizer's access path, join order, scan placement, row-count estimate, or the cached logical plan. It accepts a conservative subset of SELECT plans: one local non-shuffle equality hash MARK with a single matching independent hash-build producer, a directly above OR filter containing the positive marker and a safe literal VARCHAR equality, direct and unambiguous projection lineage to the base TABLE_SCAN, and at most the supported intervening INDEX join. It rejects missing lineage, extra or unsafe expressions, unsafe intervening cardinality/order boundaries, a producer with its own message dependency, existing producer RFs, ambiguous scope/message ownership, and other unproved shapes. Scan filters that the early guard could reorder are restricted to the same safe equality class. The probe and alternative columns are mapped through each actual MARK, INDEX when present, and TABLE_SCAN projection to their input positions; the scan input position need not equal its projected output position.

The equality domain is deliberately narrow. Probe/build columns and the alternative's folded literal must satisfy the bounded VARCHAR type and exact runtime-filter encoding checks. Main also checks charset, collation version and merge conflicts; unsupported collations and comparisons decline. Reusing the existing exact-filter pair is essential: a raw type name alone does not prove SQL equality is preserved for every collation or padded value. Prepared executions use the ordinary current execution's binding and physical eligibility checks; eligibility at PREPARE time alone does not imply every later execution is guarded.

The planner and scan-local caller share one exact-filter construction and codec validation path. A call-local environment resolves planner context and service at their original short-circuit points; invalid expressions and unsupported encodings do not initialize a process or allocate binding context. The scan-local caller supplies its existing context and service directly. This preserves protocol checks and does not cache service state across calls. On main, a targeted five-sample microbenchmark measured an unsupported pair at about 4.3 ns with zero allocations on the base and 43.5 ns with two allocations after the initial extraction; this is per-call evidence, not an end-to-end latency claim.

The compiler matches the producer to the actual MARK by join-map tag and allocates an unused current-query message tag only after checking the relevant plan/scope tags; unresolvable or overflow cases decline. The producer owns bounded optional key collection in the original HashBuild. The source scope privately owns the consumer descriptor. Once readers are constructed, the source scope receives the optional message on the current-CN message board and installs the row filter before `TableScan.Prepare`; reader setup may overlap the build. TableScan owns the resulting expression executors and their normal Reset/Free lifecycle. The MARK's normal hash map, null state and result evaluation remain independent of whether the optional key collection succeeds.

The installer separates side-effect-free discovery and lineage checks from the final attachment using an execution-local candidate. Only after every check, tag and exact-filter pair succeeds does one pre-execution commit block attach both the private source descriptor and the producer spec. A declined candidate must leave both absent; no tag or descriptor is written into a cached logical plan. This is a change to code organization and defensive behavior, not a broader eligibility rule.

The producer contract is one complete terminal runtime-filter message from one independent HashBuild. As a defensive check, if the consumer receives more than one same-tag terminal message in a single `ReceiveMessage` result, it omits the optional guard for that execution. The receiver returns when the first batch is available; this check cannot rule out a second message that arrives later or prove that one IN payload contains every key. Completeness and exactly-once publication still depend on the producer protocol, and malformed payload decode can follow the existing executor error path. The consumer must not free message-board-owned payloads early.

Only a topology proved local to the same CN and message board is eligible, with a single independent build and bounded scan worker count. Remote, lazy, shuffled, ambiguous or unsupported scope paths decline without forcing a placement change. The special OR guard is private execution state, not a new plan or pipeline protobuf field: an older CN must never interpret its IN arm as a mandatory independent probe. This avoids adding a new mixed-version wire contract, but a live mixed-old/new upgrade has not yet been tested. The PR reports a separate same-version two-CN SQL run; the checked-in `TestMarkScanGuardSQL` uses one CN.

## Bounds and costs

The current implementation admits a scan only when nondefault table statistics estimate at least 8,192 rows and the actual scan projection contains a wide column that existing late materialization can defer. This is a usefulness heuristic, not proof that the alternative is selective. It caps the optional message at 128 distinct keys, 512 actual bytes per key, 128 KiB of serialized payload, and eight scan workers. The producer checks key count and actual bytes before copying; it discards the optional collection and sends PASS when its bounds cannot be met. Retained live key bytes are at most 64 KiB; vector capacity slack, metadata and serialized copies add bounded overhead, so this is not a total-memory peak bound. Per-reader exact-IN state and scratch are bounded by these limits and normal block/vector sizes; the normal MARK hash table is a separate pre-existing cost. No new global cache, shared collector, background worker, wire field, or extra subquery execution is introduced.

The guard still evaluates narrow columns, builds bounded key state and can add CPU or selected-row read overhead when most rows pass. It does not promise block pruning or avoid visiting all narrow workspace candidates. Existing `FILTER` estimates above the MARK are a fixed 0.05 and do not measure the alternative arm. Equality estimates based on global NDV assume uniformity, cannot represent a tenant-specific hot value and may be stale. Main's optional manual-ANALYZE byte distribution is not universally present and does not solve conditional tenant selectivity. No such estimate is used as a hard broad-case switch.

The independent [4.2 QA report](https://github.com/matrixorigin/matrixone/pull/32608#issuecomment-6818939585) measured a 9.2x selective wide improvement and a repeatable 41.769 to 50.985 ms (+22.1%) base-to-head regression when the alternative matched all rows; 10% and 50% cases improved. The 100% base and head physical plans differed: only the head showed an INDEX join. The guard installer executes after physical scheduling and does not introduce that join, but the measurements do not isolate the join's cost or prove why those plans differed.

A clean 4.2 base control, restored through a test-only overlay and run in a newly constructed separate cluster with the same SQL, data distribution and settings, chose MARK plus INDEX for the selective, 10%, 50% and 100% cases. This does not recreate the QA environment or explain its different plans.

A separate same-head, same-data 4.2 experiment used a test-only guard switch, confirmed installation and identical INDEX/MARK plans, and alternated eight guard-off and eight guard-on executions. Median complete-result times for selective, 10%, 50%, and 100% alternatives were respectively 144.07 to 3.07 ms, 150.60 to 95.69 ms, 166.83 to 127.87 ms, and 180.85 to 181.52 ms (+0.4%). A matching EXPLAIN ANALYZE experiment, avoiding transfer of the wide result, measured 155.47 to 3.68 ms, 157.88 to 99.68 ms, 160.90 to 116.59 ms, and 154.83 to 155.56 ms (+0.5%). These are warm, single-CN local samples, not a universal bound or a reproduction of the QA base/head comparison. Repeated cold and production replay measurements remain open.

A corresponding main same-head, same-plan experiment also alternated eight guard-off and eight guard-on executions. Median complete-result times for selective, 10%, 50%, and 100% alternatives were respectively 130.90 to 4.00 ms, 142.40 to 107.79 ms, 154.20 to 136.65 ms, and 171.47 to 178.27 ms (+4.0%). Guard installation and result cardinalities were checked. This is a real broad-case overhead in this fixture, and the code-organization changes do not claim to remove it.

A per-worker adaptive guard bypass could observe actual guard survival and stop applying only the optional guard to subsequent blocks. It might help a measured broad-case guard cost, but requires new worker state, an accurate per-guard counter, batch-boundary transitions, and restoration of scan column configuration. Its first sampled blocks can also mispredict later selective blocks. The present same-plan data does not justify that complexity; keep it as a separately measured follow-up, not part of this implementation.

A test-only `IF(B, TRUE, probe_key IN keys)` guard was also compared with the existing OR and guard-off in the same 4.2 cluster, four executions per variant. For selective, 10%, 50%, and 100% alternatives the respective off/OR/IF medians were 152.43/3.42/4.06 ms, 159.22/102.52/102.10 ms, 175.78/130.27/131.35 ms, and 189.22/190.00/186.14 ms. Both guards were observed installed and results matched in this fixture. IF improved the broad OR comparison by about 2%, but was about 19% slower on the selective target; this small local sample does not justify replacing OR. IF and OR have the same TRUE-row set in a WHERE guard, but differ between FALSE and NULL when B is NULL and IN is FALSE, so IF is not a general three-valued-expression replacement. Its masked execution also incurs selection, vector compaction and expansion costs.

## Alternatives considered

A post-MARK narrow plan with exact PK backfill can preserve correctness, but needs a correctness-bearing membership step and its own broad-result memory and fallback design. An index-based candidate union can duplicate the subquery, introduce completeness, error timing and lock/snapshot concerns, and require extra state. Existing shared producer rules for the relevant `FOR UPDATE` shape do not establish that this avoids those problems. A serialized guarded runtime-filter field would require an explicit mixed-version capability contract; treating an unknown field as compatible could lose B-only rows. These alternatives are not needed to capture the measured scan-local late-materialization opportunity.

## Validation and remaining work

Public SQL tests compare original expected result multisets for IN-only, B-only, overlap, different rows, neither branch, NULL and empty builds, duplicate keys, tenant mismatch, selected encodings, and IN/DROP/PASS boundaries. The checked-in lock regression observes a B-only row's holder/waiter pair and verifies progress after rollback; it does not retain a delete-after-wait scenario. Producer and scope tests exercise key and byte caps, cancellation, build failure, cleanup, reuse and parallel clones. Decomposition tests assert that covered declined candidates leave both ends unattached, and that multiple already-available same-tag terminal messages in either order omit the guard; those tests do not establish absence of later duplicate publication. PR evidence reports focused package and SQL race runs on both branches; the checked-in main SQL regression covers prepared reuse with changing build contents. The independent QA report provides additional tested cases and timings. These results do not prove every topology or every future execution engine path.

Future evaluation should reproduce the QA 100% case with the same data snapshot, statistics, physical INDEX decision, head and guard on/off; record actual plans and rows before attributing the +22.1%. Compare repeated warm and controlled cold runs, output-transfer and executor-only measurements, key cardinality boundaries, skew within and across blocks, multiple tenants and concurrency. A candidate adaptive or conditional guard must retain the above multiset, lock and error contract, decline safely on missing/stale estimates, and show a repeatable end-to-end benefit without losing the selective gains on both branches. A live mixed-version rolling-upgrade test remains separate from the existing same-version two-CN evidence.
