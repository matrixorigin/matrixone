# Issue #29226：跨协调 CN 的 IVF 扫描对象归属设计

- 负责 issue：[matrixorigin/matrixone#29226](https://github.com/matrixorigin/matrixone/issues/29226)
- 实现 PR：[matrixorigin/matrixone#29319](https://github.com/matrixorigin/matrixone/pull/29319)
- 评审记录：以本文件的 Git 修订和 PR 上明确的设计审批决定为准；在审批前不得把实现视为已获批准

## 问题、目标和边界

同一批 CN `{A, B}` 执行 IVF 扫描时，原实现按“协调 CN 在前”的列表给分片编号。入口从 A 切到 B 后，同一个落盘 entries 对象的读取 CN 可能随之交换，削弱 CN 内存缓存的复用。目标是：在选中的 CN 身份集合不变时，每个落盘对象的负责 CN 与 SQL 入口无关，并且每个对象恰由一个分片读取。查询结果、事务可见性、取消行为和混部安全性必须保持不变。

本文只规定 IVF 向量索引扫描的执行期归属，不修改对象的存储位置、对象 ID、索引格式、全局缓存策略或普通表扫描。CN 集合变化时，对象分配可以重算；本设计不保证每个 CN 的占用恰好相等，也不保证容量不足时整个索引都驻留缓存。例如 10 GiB 索引与两个各 6 GiB 可用缓存，稳定归属只提高重复查询的复用机会，实际占用仍取决于 ObjectID 分布和读到的数据。

## 不变量与所有者

1. 对选中的 `N` 个 CN，按 `(ServiceID, PipelineServiceAddress)` 升序生成稳定的执行列表，赋予 `CNIDX=0..N-1`。不修改同一查询供其他扫描使用的原始协调 CN 列表。地址仅在身份缺失或相同时参与排序；选中成员或其身份变化时不承诺归属连续。
2. 每个持久化对象的分片由现有 `IVFObjectIDHashToRange(full ObjectID, N)` 与 `ShouldSkipObjByShuffle` 决定。完整 ObjectID 而非 SQL 入口或协调 CN 决定分片；排序后的分片编号再映射到 CN。`relationScanner` 在各执行 CN 上把相同的 `CNCNT/CNIDX` 传给隐藏表 `Ranges`，因此每个对象仅归一个 CN；appendable 与 persisted 的同一对象使用同一归属规则。散列不是数据复制或缓存分配协议。
3. 未落盘或事务工作区数据由本地执行路由拥有，与对象分片编号独立。`ScanIdentity.IsRemote` 从真实 `Scope.IsRemote` 产生；本地分片即使编号非零也可收集内存行，远端分片即使编号为零也只收集已提交的持久化数据。单分片、复制读取的元数据/centroid 和需要 membership filter 的路径遵守原有策略；可写工作区、`ForceOneCN` 等保持本地执行。
4. 执行计划中的分片编号和路由在编译完成后不因探测结果变化而重排。若发送前或接收时发现能力降级，失败并交给上层查询重试机制；不得在已经产生部分结果的同一执行中静默改用另一套对象归属。

## 控制流与嵌套传输

编译器只在多 CN、只读工作区、非强制单 CN、非必需 membership 的向量扫描上考虑稳定布局。它检查本地服务的 `MOProtocolVersion`，再向选中的每个非本地 CN 发 `GetProtocolVersion`。服务身份和 pipeline 地址必须与当前集群目录匹配；缺失、未知、RPC 失败或超时都视为能力不足，保留原有“协调 CN 在前”的分布式布局。父 context 取消直接返回取消错误。一次探测共用 5 秒上限，每个响应都释放；探测结果不跨执行缓存。

稳定布局允许远端执行分片零。发送端在编码远端 scope 前，检查包括子 pipeline 在内的整个树，并针对实际目的 CN 再次探测。接收端在解码后、执行前递归检查本地协议版本。远端分片零要求双方至少 MORPC 95；任一检查不满足即拒绝执行。旧布局的远端非零分片和本地解码没有新门槛。`IsRemote` 取决于执行路由，不能用分片零推断。版本 94 已由无损 NoFull CDC 启动水位语义占用，不得作为 IVF 能力证据。

MORPC 95 是本变更的部署能力门槛，而非新的持久化编码或 protobuf 字段。这里复用已有 pipeline 节点的 `CNCNT/CNIDX`、`ScanIdentity` 和查询能力 RPC。若部署回退到 94 或更低，新的查询选择旧布局；已经编译好的稳定布局在发送/接收保护处失败而不产生不完整结果。重启、备份恢复和已有索引对象无需迁移，因为对象数据及其 ObjectID 未改变。滚动升级要先让所有参与 CN 支持 95，再提升服务本地协议门槛；滚动回退先降低门槛，停用稳定布局。

## 资源、可观测性与故障边界

排序的空间与时间分别为 `O(N)`、`O(N log N)`；能力探测最多逐一访问所选 CN，整个操作受 5 秒超时和查询父 context 约束。结果只保存在本次编译中，不引入长期状态、队列或后台 worker。对象读取量由原有 ObjectID 分片规则确定；稳定映射减少入口切换引起的缓存归属漂移，但仍可能发生缓存驱逐、热点偏斜与远端对象存储读取。缓存上限继续由既有 CN memory cache 管理。

能力不可确认时的正常降级是旧布局；父取消向上传递；发送/接收时的协议不匹配为显式错误。排查可从执行计划中确认向量索引扫描及 CN 路由，从版本门槛、能力 RPC、发/收保护错误中识别回退或降级；不打印索引数据或租户私有内容。现有事务与租户过滤流程不改变，新路径不扩大跨租户读取权限。

## 替代方案和取舍

| 方案 | 正确性与兼容性 | 成本与取舍 |
| --- | --- | --- |
| 保持协调 CN 在前 | 原有混部行为稳定，但同一对象随入口改变 owner | 不解决跨入口缓存复用 |
| 始终只在入口 CN 扫描 | 无跨 CN 对象归属协议 | 放弃已有分布式并行度，单 CN 内存与 I/O 压力增大 |
| 引入全局对象到 CN 的持久化映射/一致性哈希环 | 可在成员变化时减少搬迁 | 新增持久状态、失效/恢复/租户隔离协议，不符合本次问题规模 |
| 本方案：稳定排序 + 既有 ObjectID 分片 + MORPC 95 门槛 | 固定 CN 集合时无重漏；旧/未知版本沿用旧布局 | 成员变化仍重分配，逐 CN 能力探测增加编译耗时 |

不采用把全部索引复制到每个 CN 的方案：它使每 CN 内存和 I/O 按 CN 数增加，也无法在单 CN 缓存小于全量索引时保证驻留。

## 验证、验收与尚待决定事项

- 确定性 UT：两/三 CN、不同入口顺序映射出相同 ObjectID owner；每个完整 ObjectID 恰有一个 owner；appendable/persisted 一致；本地非零/远端零的内存行策略；单分片和普通扫描不变。
- 协议 UT：94 的 coordinator/worker 均回退旧布局，95 双方启用稳定布局；未知/失联/取消分别降级或返回取消；嵌套 pipeline、发送前降级、接收端降级、response release 均闭合。
- 端到端：两个真实嵌入式 CN 的 MySQL 查询，从两入口运行 `Vector Index Scan`，验证 peer 执行、落盘与内存数据、提交和回滚后的完整有序结果。原有 IVF BVT 与 SCA 通过。
- 规模验收：在实际索引规模和明确 CN 缓存预算下，分别记录固定入口/交替入口的缓存命中、对象存储 I/O、解码、QPS/延迟和每 CN 内存。小样本本地对照不能证明生产规模收益；该项完成前不宣称性能提升倍数。

提议的决议是：接受成员集合变化时重分片；按“全部参与 CN 支持 95 后启用，回退前先关闭门槛”的顺序部署；能力下降时显式拒绝既有稳定布局的执行。这些取舍已在上文说明，不留下实施阶段再决定的策略问题。本文仍处于待评审状态，只有评审者在版本化修订上明确批准后才算设计通过。
