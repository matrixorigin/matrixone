# Consolidating temporal index planning and execution ownership

**Status:** design for [issue #32318](https://github.com/matrixorigin/matrixone/issues/32318) and [PR #31944](https://github.com/matrixorigin/matrixone/pull/31944). This document describes the intended implementation; verification evidence is recorded separately in the PR. The examined PR head is `6ba845886cdd8e3f4d21f6867c557c7fb79e714f`, which includes the earlier main baseline `5e024527f7d30e9cbd52c16a365fce24c91a3afe`. Main has since advanced; `bfdf875816929653ad2ff3e3c403943c7afc4645` was the latest observed revision at design time, not a measured baseline for this proposal. Freeze the actual main SHA when validating the implementation.

This design narrows ownership around the existing temporal access path. It keeps the typed inversion and its independently maintained proof in [Mixed DATETIME/TIMESTAMP candidate-range semantics](20261028-temporal-index-ranges.md), and the ordinary-resolution ownership in [Planner borrowed reads](20261106-planner-borrowed-reads.md). Neither proof is replaced by this document. All proposed deletions are contingent on the acceptance checks below; when a boundary cannot be proved, retain its current implementation and document the failed case.

## Decision and data flow

For an admitted, parameter-free covering index candidate, retain the two execution-time DATETIME/TIMESTAMP endpoint functions and `types.BuildTemporalCandidate`. Remove the fifth, mutable permission argument; the separate empty guard and its helper; the guard's Expr/FoldVal provenance; and the whole-plan copy and rewrite used to set that argument. Keep the complete SQL predicate as the residual and keep the temporal candidate marker. The marker identifies a necessary range and its reader behavior; it is neither SQL authorization nor a substitute for checking the physical access path.

The existing flow remains:

1. The frontend supplies an intent and a single-use root planning input to the actual optimizer attempt. The ordinary resolver supplies the base relation and transaction read evidence; the optimizer proves the original and current shapes, costs the actual reader input, and considers supported covering indexes. The winning hidden relation is resolved once through the ordinary owner and checked against the base relation before publication.
2. The selected hidden-table scan contains the marked necessary range in `BlockFilterList` and the original, fully mapped SQL predicate in `FilterList`. `ParentObjRef` retains the logical base identity. No range replaces the residual, and cost statistics or a relation handle do not grant access.
3. The frontend validates the execution intent and reauthorizes an unscoped safe rebuild on drift. Compile retains physical INDEX placement/intent checks, local `ForceOneCN`, sticky candidate topology, reset rejection, and existing retry/definition-rebuild behavior. `Query.TemporalIndexNeedsReplan` retains the BASE-to-later-INDEX recost requirement. No new initial `Run` rebuild is introduced.
4. During a native Run, `runPipelineAttempt → prePipelineInitializer → Scope.InitAllDataSource` initializes the source; `compileTableScanDataSource` creates private storage-filter expressions and evaluates their folds. `scope.handleRuntimeFilters` evaluates block-filter folds before reader/range construction. A remote scope receives raw `remoteBlockFilters` and builds its own fold executors. This is not evaluation during ordinary `Compile.Compile`, nor a fresh scalar evaluation for every block. Sirius has its own reader initialization, but existing candidate placement admission excludes offloading the production candidate.

The runtime endpoints consume the execution's bound and zone. Preserve the supported single-statement ownership of the process, clock and zone across source initialization, block pruning and residual evaluation. A Compile-to-Run drift test must inspect these actual boundaries; if a supported actor can concurrently mutate this state between them, establish the existing owner's serialization or retain the old implementation. A helper name is not a concurrency guarantee.

## Range and guard correctness

Let `P` be the complete SQL residual, `G` the old empty guard, and `R` the old necessary physical range. The established typed proof requires `P = TRUE ⇒ G ∧ R`. Dropping `G` produces a superset: `P = TRUE ⇒ R`. Extra candidates are filtered by `P`, including SQL UNKNOWN. This establishes only guard removal; removing permission also changes how endpoints are selected when the old permission was false. The new runtime range must independently satisfy `P = TRUE ⇒ R` for the actual bound, scale, operation and zone, not assume permission was true.

Keep the existing fixed-zone inverse, rounding and open/closed bound rules, zero sentinel, DATETIME physical tails, and serial/prefix encoding. Invalid controls, unsupported or non-fixed/nil zone, arithmetic overflow, and `BuildTemporalCandidate.Empty` or NULL inputs widen endpoints to the full physical domain (`Lo=MinInt64`, `Hi=MaxInt64`, `Sentinel=MinInt64`). In particular, do not approximate a daylight-saving zone with one offset. The complete residual remains authoritative. A widened range may read extra rows but must not introduce another non-cancellation error or diagnostic.

For the currently published candidate, the old guard is additionally expected to be true: admission evaluates a non-NULL scalar, rejects Empty/Full, and accepts only an immutable literal without `Src` or `CURRENT_TIMESTAMP` overload 0 with no arguments or a literal FSP in 0–6. Its result scale must equal the effective FSP. `CURRENT_TIMESTAMP` maps the int64 Unix-nanosecond clock into the interior calendar domain and applies `TruncateToScale(FSP)`, so its value is non-NULL and on the admitted precision grid. A literal cannot change during the generation. The non-grid equality rejected by `TemporalTimestampBoundNotEmpty` yields Empty or, on overflow, Full, both already rejected by `estimateTemporalRange`. Verify all scales and overflow branches before deleting that redundant cost check. Guard invariance explains expected production performance; correctness rests on the superset and typed necessary-range proofs.

An endpoint currently checks `proc.Ctx.Err()` and `BuildTemporalCandidate` can return a context error. Removing the permission branch can introduce an additional cancellation observation; preserve the existing error contract and test ordering rather than claiming a custom cancellation cause was already returned. Preserve the positive admission of literals/current time and reject unproved parameter or `Src` provenance, unsafe or diagnostic expressions, unsupported shapes, non-covering indexes, early stop, and disallowed placement. Separately test synthetic missing-intent, unmarked and reentrant cases without presenting them as reachable public SQL witnesses.

## Concrete changes and retained boundaries

- Change endpoint helpers 633 and 634 to four arguments. Remove `__mo_temporal_bound_not_empty` and its two overloads, ID 635 registration, guard construction/marking, and the redundant scalar guard check only after the range proof above. If 634 remains the highest ID, set `FUNCTION_END_NUMBER` to 635; do not renumber other functions. Keep `IsTemporalBoundFunction`, `ContainsTemporalBound`, real-time/constant-fold and zonemap handling for the two remaining helpers.
- Remove `TemporalCandidateGuard` from Expr and FoldVal protobuf definitions, generated code, copying and fold propagation. Remove the guard-specific Fold branches from `readutil/pk_filter_base.go` and `readutil/expr_filter.go`. The recursive temporal boolean in `pk_filter_base.go` exists only for that guard and may go. The corresponding scoped boolean in `expr_filter.go` must stay: it also controls OR unknown/quick-break behavior and bounded prefix/ordinary seek. Generalizing those paths requires a separate proof for their non-temporal consumers.
- Remove `prepareTemporalExecutionPlan`, `setTemporalCandidateNarrowing`, and the plan-wide copy used to mutate permission. Keep the existing execution-owned filter copies, fold executors and remote raw-expression ownership. Delete the replaced production route rather than maintaining a second switchable implementation.
- A plan copy also isolates other mutations: `compileQuery → CalcQueryDOP` writes node `Stats.Dop`, analysis writes plan data, and `Source.node` borrows a node. Real selected candidates carry `TemporalIndexNeedsReplan` and are barred from ordinary and prepared cross-execution reuse, but this alone does not prove all frontend aliases are harmless. Before removing the copy, compare `cw.plan`, logging, EXPLAIN, result metadata, retry and error behavior on real ordinary and SQL/binary prepared paths. If a persistent template still shares a mutated object, isolate it at that actual boundary; do not silently remove the isolation.
- `Function_INTERNAL` has not been shown to prevent direct SQL calls through the general binder. These names and the five-argument signature were introduced by this unmerged PR: explicitly audit SQL and persisted-expression consumers and record that the old direct call and removed guard name cease to resolve. Do not invent a compatibility implementation solely because the branch was pushed. Regenerate protobuf and function registries, and verify the repository's shutdown-only upgrade assumption and any actual persisted/mixed-version consumers before deletion.
- Charge the actual constructed expression against the existing bounds. Removing a guard changes expression size and may change cost, budget exhaustion or an INDEX/BASE tie; record actual admission and plan changes. Do not add dummy nodes to preserve a number. Keep cancellation, resource bounds and transactional publication checks.

## Proof ownership and reuse

Keep `temporalOriginalScan` and the original lifetime analysis in this change. Current-path proof reuse is still worthwhile: `temporalBaseReaderShapeSafe` already visits the current path, and enumeration parses the atom; `temporalIndexOperands` currently repeats both per index and the winner repeats them after hidden resolution. Split the operation into one current scan/path/atom proof per synchronous enumeration and index-specific checks for algorithm, parts, leading column, completeness, collation and covering. Carry the proof only in the attempt-local `temporalIndexAccess`; do not persist it in the plan or a global cache.

After resolving the winning hidden table, perform one fresh current scan/path/atom proof. A test-injected resolver can reenter or mutate an object in place, so pointer equality is insufficient. Preserve the independent original proof, `BorrowStillCurrent`, actual intent and transaction checks, `VerifyTemporalIndexPair`, scan/tag/version and next-tag checks, budgets, `context.Cause`, and private construction before publishing the node and column map. Failed, canceled or reentered attempts must not publish a partial candidate.

The original proof is not retained merely because a test manually deletes an unsafe expression. The current optimized BASE IR is the result comparison point, and the eligible post-index unary passes have been inspected for residual, projection and early-stop preservation. However, removing `originalSafe` can make `enumerateTemporalIndexCandidates` run for a formerly skipped path. Its deferred `context.Cause` may then precede an error that the old `applyIndicesWithOrder` would encounter before `applyIndices` checks cancellation. No real SQL witness for that competition has yet been established, and final-row equivalence alone does not close error priority. Retain the original state until real bind/rewrite traces and deterministic cancellation/error injection prove equivalence or identify an existing owner that preserves the ordering without another persistent state.

A 100,001-row instrumented 6ba fixture checked five real SQL cases: the plain predicate, unused division or invalid-datetime projections, `AND 1=1`, and a duplicate predicate. Each returned the same 100 rows and zero warnings as its IGNORE INDEX counterpart; only the plain case selected the four-block index path. The other four had `originalSafe=false` and `replan=false`. Deleting only `originalScan` while retaining lifetime admission would not make those examples eligible, and five samples do not prove all rewrites equivalent.

## Existing semantic, cache and catalog owners

Reuse existing expression-totality owners (`isTruncationSafeRowExpr`, `isTruncationSafePredicateExpr`, `comparisonEvaluationIsTotal`) for shared recursion and comparison semantics. A private temporal policy may additionally admit exactly the existing source-free literal or validated statement-clock forms; other consumers retain their current acceptance. Runtime stability by itself does not prove that a function is total or free of diagnostics. Share the existing parameter/`Src` traversal only after comparing its reachable Expr cases and budget behavior. Do not broaden AND/OR, NOT/XOR, UDF, parameters, FSP, evaluation timing or warning behavior to obtain a smaller function count.

Keep the distinct reuse decisions at their actual owners:

- Ordinary COM_QUERY cache admission and lower-level generation update have different existing predicate sets. Share an attempt-local result only when it removes a real repeated traversal and each caller consumes its original subset; preserve AST transfer and failure cleanup.
- Prepared template rebuilding, type/value-bound `runtimePlan` specialization, and physical `Compile` reuse answer different questions. Keep their schema, protocol, permissions, binding/diagnostic and generation checks. Percentile/EWM execution-dependent configuration can prohibit a physical compile hit without requiring a logical template rebuild.
- Keep `TemporalIndexNeedsReplan`, including when the current result is BASE: a later statement clock or distribution can make INDEX cheaper. Do not replace it with `Node.NotCacheable`: that bit has real non-temporal uses, and ordinary VALUE_SCAN plans such as prepared `SELECT 1` also carry it. Unconditionally using it in `shouldRebuildPreparePlan` would force unnecessary rebuilds.

The base and hidden relations remain borrowed from the same ordinary resolution, owned by the engine/transaction, and released from the builder attempt on every exit. Keep exact compiler identity, root single claim, fresh prepared/FIELD attempts, the 64-record bound, duplicate/overflow fail-closed behavior and final real pair verification. A wrapper may alter catalog or tenant semantics; never open the relation again by name or discover a promoted richer method through an arbitrary wrapper.

There is one real non-temporal read-stamp consumer: the frontend view schema provider. It may be possible to consolidate repeated comparison in the existing `client.CatalogReadStamp`, binding the **actual caller's** operator and stable workspace visibility after raw sampling, and then remove `engine.TemporalRead`'s duplicate data and comparisons. Raw `CatalogReadStamp` and `TryCatalogReadStamp` must not substitute the underlying implementation for a caller wrapper. Preserve view's blocking/must-succeed errors and order, including its structural `reflect.DeepEqual` snapshot check; temporal checks use `Timestamp.Equal` plus actual operator/visibility and remain nonblocking Try with optional BASE fallback and the existing cancellation behavior. In particular, timestamp `Equal` omits fields that view's structural comparison includes. Do not call workspace visibility under the transaction lock, change the old behavior of incomparable wrappers without a separate decision, or drop frontend context/process/handler and engine read-only/DDL/tenant/schema/pair checks. If the common API cannot preserve these contracts or adds unjustified hot-path work, keep the present read type.

## Alternatives and verification

Materializing the optimizer's observed range would eliminate both remaining endpoints, but it would require reliable handling of Compile-to-Run drift. The existing retry constructor is not a safe drop-in: it can advance the workspace offset again, and the replacement has unresolved Process, board, warning, counter, Sirius, session-plan and release ownership. Frozen EXPLAIN ANALYZE/PHY may already have sent a title not covered by `sameResultMetadata`. This proposal therefore keeps dynamic endpoints and does not add that Run state machine. A generic dependency framework, blind `NotCacheable` reuse, re-resolving relations by name, and renaming Temporal types do not remove a proved responsibility and are not selected.

Before implementation is accepted, record exact binaries, source and test selection and run:

1. **Typed range and reader:** independent SQL-comparison oracle versus old enabled helpers and new endpoints for both type directions, all comparisons and scales, signed/fractional zone offsets, grid boundaries, zero, NULL, Empty/Full, overflow and physical tails. Verify `P = TRUE ⇒ R` for direct and encoded prefix keys; exercise object/block pruning, memtable, PK and unmarked/ordinary OR/seek paths. Check cancellation, warnings, bounds and the old permission-false case.
2. **Planner and ownership:** zero, one and multiple indexes; path/atom mutations before and after winner resolution; wrapper/reentry, original proof and current proof, budget exhaustion, malformed metadata, tenant, snapshot/workspace/visibility changes and cancellation. Assert real pair checks and no partial publication. Compare old and new costs, admission and final typed plans. Test original-proof error ordering separately, without claiming the five fixture cases prove it.
3. **Frontend, compile and cache:** ordinary SQL, SQL PREPARE and binary prepare/execute, observing template, runtime-plan and physical-compile hit/build behavior. Cover dense BASE → sparse INDEX → dense, parameters/NULL/type changes, `SET timestamp`, UTC and signed fixed zones, named zone fallback, SELECT limits and scheduling, schema/DDL retry, role/privilege changes, metadata freeze and EXPLAIN/ANALYZE/PHY. Compare complete rows, error class and warnings with IGNORE/fresh-plan controls. Snapshot `cw.plan` and logging before/after compile, failure and retry. Include prepared `SELECT 1`, subscription, metadata, percentile and EWM controls.
4. **Distributed and lifecycle:** run actual two-CN SQL with address/placement evidence, remote raw/folded filter and timezone/clock transport, fixed local candidate and denied/offload cases; preserve applicable transport parity. Exercise missing/changed relation, cancellation and panic, result metadata, message board, offset, warnings, process and resource cleanup. Run the relevant nonempty plan/frontend/compile/readutil/disttae/process tests through the repository CGo runner, applicable SQL integration and `-race`, plus normal formatting and static checks. Existing 6ba results do not certify a changed head.

For performance, freeze three exact binaries with identical toolchain, native libraries, fixture and probe: **A = latest main at measurement**, **B = 6ba**, **C = final implementation**. Use the existing seven scenarios and 1,000,001-row fixture, with 25 warmups and 100 timed executions per scenario, full-result IGNORE INDEX oracle and actual BASE/INDEX block evidence in every process. Run serial `ABCCBA` and `CBAABC`: 12 independent processes, 84 phase results and 8,400 timed samples. Record source/binary/native/probe hashes, every sample, p50/p95, CPU, allocations, host load/SMT and same-version controls. Report A→C and B→C separately; do not assume latest main has identical behavior to 5e. Sparse and sparse-again must retain a material scanned-block reduction versus BASE. Ordered, same-domain, dense and prepared controls must have no stable material regression. Two groups slower by more than 10% for the same metric, or either group slower by more than 20%, trigger a targeted investigation rather than repeated unbounded runs; the threshold does not excuse a demonstrated regression. Also measure actual frontend cold-planning allocations, path visits, range/fold construction and binary-prepared hit/build behavior.

Historical evidence is a comparison, not validation of the new head: E136 measured 5e→6ba shuffled sparse p50 improvements of 92.2% and 92.5%, with prepared +4.7% and +5.0% within observed same-version variation. An earlier dfc→de62 prepared comparison showed +42.5% p50/+47.9% p95 in one order and +4.1%/+0.5% in the reverse order; its cause remains unknown, and the binary prepared physical plan was not observed. Preserve this limitation in the final report rather than attributing or declaring it fixed.
