# Type dispatch tables: consolidating `switch typ.Oid`

## Scope and trigger

Issue [#10181](https://github.com/matrixorigin/matrixone/issues/10181)
("[Refactoring]: VFT of types").

MatrixOne decides what to do with a value by switching on its type id
(`types.T`, the `Oid` of a `types.Type`) all over the codebase. The issue
names two problems:

1. **Adding a type means editing many places, and missing one fails
   quietly.** A new `T_` constant falls into whatever `default:` branch each
   switch has. Depending on the site, that is a panic, an "unsupported type"
   error, or a wrong result.
2. **Some switches run once per row.** The cost of a switch whose type is the
   same on every row is small, but these sites usually also box values into
   `any`, which is the larger cost.

This document measures the problem, proposes a design and lays out a
step-by-step plan. It changes no code; each implementation step will be its
own PR.

## Measurements

The numbers come from `optools/oidscan`, a `go/ast` scan of every non-test
`.go` file under `pkg/` (skipping `testdata/`), at commit `5e3893a298`. A
"type switch" is any `switch` statement with at least one `case` naming a
`T_*` constant. To reproduce:

```
cd optools/oidscan
go run . -root ../..                     # the summary below
go run . -root ../.. -loops              # every switch inside a loop
go run . -root ../.. -loops -invariant   # only those whose type is fixed for the loop
```

Counts drift as `main` moves; the tool gives the current numbers.

### How many and where

| | Count |
|---|---|
| Type switches | 949 |
| Switches with a `default:` branch | 636 |
| `case types.T_…` lines (grep) | ~7,500 |

The 949 switches by number of `T_` constants named in their cases:

| Cases | Switches | Usual purpose |
|---|---|---|
| 20 or more | 225 | Full physical dispatch: "for each Go representation, call `f[T]`" |
| 4–19 | 450 | A family of types: numeric, temporal, string-like |
| 1–3 | 274 | A special case: "if JSON then …", "if decimal then …" |

Packages with the most switches having 20 or more cases: `sql/plan/function`
(59), `frontend` (21), `sql/plan` (18), `container/vector` (18),
`vm/engine/readutil` (10), `sql/compile` (9), `sql/colexec/aggexec` (9),
`vm/engine/tae/containers` (6).

### Switches inside a loop over rows

128 switches sit inside a `for` or `range` in the same function. Most of
those loops run over columns, arguments, plan nodes or schema fields, so the
switch runs once per batch or once per plan and costs nothing worth
measuring. The ones that run once per row:

**Hot paths**

| Site | Path |
|---|---|
| `common/hashmap/strhashmap.go` `fillNullableStr` | Hash join and group-by key encoding, per row and per key column |
| `frontend/mysql_protocol.go` `appendResultSetTextRow2`, `appendResultSetBinaryRow2` | Every result row sent to a client, per column |
| `frontend/export.go` `constructByte`, `constructJSONLine` | `SELECT … INTO OUTFILE` and JSON export, per row and per column |
| `sql/plan/function/func_cast.go` `jsonToNumeric`, `castToJSON` | Cast evaluation |
| `sql/plan/function/func_unary.go` `NormalizeL2Array` | Vector-function evaluation |
| `sql/plan/function/func_builtin.go` internal metadata functions | Function evaluation (rarely called) |

**The type does not change inside the loop; move the switch out**

- `sql/colexec/multi_update/insert.go` `checkZeroTemporalInStrictMode`
- `sql/colexec/preinsert/preinsert.go` `checkZeroTemporalInStrictMode`
- `sql/colexec/postdml/postdml.go` `runPostDml`

**Switches hidden in helpers called once per row**

A loop scan misses these because the switch sits in the callee:

- `vector.AppendAny`
- `containers.UpdateValue` (TAE)
- `getNonNullValue`, which exists twice, in `vm/engine/tae/containers/utils.go`
  and `sql/colexec/deletion/types.go`
- The `Get`, `Append` and `Update` methods of the TAE vector wrapper, built on
  the helpers above

For a switch whose type never changes inside the loop, branch prediction
hides most of the cost. The measurable overhead at these sites is boxing
every value into `any` and the call made for each value. The fix is therefore
"resolve the type once per vector, then run a typed loop", not only "remove
the switch".

### What already exists

`TestTypeSwitchFamilies` (`pkg/container/types/typeswitch_test.go`, described in
`pkg/container/types/testdata/README.md`) already enforces completeness for two
families, float (`T_float*`, `T_bf*`) and vector (`T_array_*`): a switch, `||`
chain or type list that names some members of a family must name all of them,
or one whole subfamily, or carry `// typeswitch:partial <reason>`. Switches that
predate the check are listed in `typeswitch_baseline.txt`, which may only
shrink. This is the same idea this design needs for the switches that stay,
already accepted in the repository, so the design extends it rather than adding
a second mechanism.

## Goals

1. When someone adds a `T_` constant, every place that must handle it fails
   to build or fails a test until it does. Nothing is silently left out.
2. Physical dispatch (picking the Go representation and the generic
   instantiation for a type) lives in one table per package, filled in in one
   file.
3. No type dispatch runs once per row on a hot path.
4. No change to stored formats, the wire protocol or plan encoding.

## Non-goals

- Moving every type switch into one file. About 700 of the 949 encode meaning
  specific to one feature: planner coercion rules, the cast matrix, function
  overload resolution, MySQL wire types, parquet and arrow mappings, charset
  rules. Gathering them in one file would give one very large file with the
  same number of places to forget. Goal 1 is met for these by checking
  completeness, not by moving them.
- Changing how functions are registered or overloads resolved in
  `sql/plan/function`. That framework already looks implementations up in a
  table. Its internal switches are covered by the completeness check.

## Design

### Why the table is indexed by `Oid` and not stored in `types.Type`

The issue suggests putting a `vft *VFT` pointer inside `types.Type`. That
does not work as stated:

- `types.Type` has a fixed 16-byte stored layout (see the comment on the
  struct). Object, vector and catalog codecs write it out as raw bytes, so a
  pointer field would break the format or be lost when decoding.
- There are about 570 non-test `types.Type{…}` literals, and many more `Type`
  values come from decoding bytes. Any of them would carry a nil `vft` unless
  every construction path set it.

Indexing a global array by `Oid` gives the same "call through the table"
model without either problem:

```go
// pkg/container/types/traits.go
var traits [256]typeTraits // indexed by T; T is uint8

func (t T) IsFloat() bool { return traits[t].flags&flagFloat != 0 }
```

The lookup is one bounds-check-free index operation, and works for a `Type`
built any way at all.

### Layer 1: the traits table, facts with no dependencies

Lives in `pkg/container/types` (`traits.go` for the mechanism,
`traits_table.go` for the rows). One row per type id holds:

- `flags`: the families the `T.IsXxx()` predicates report (signed and
  unsigned integer, float, low-precision float, decimal, date-related, MySQL
  string, fixed-element vector, block-scaled vector, ordered);
- `typeLen` and `fixedLen`: what `T.TypeLen()` and `T.FixedLength()` return;
- the default size and width that `T.TryToType()` returns;
- the names `T.String()` and `T.OidString()` return.

```go
var traits [256]typeTraits // indexed by T; built by a package-level initializer

func (t T) IsFloat() bool  { return t.is(flagFloat) }
func (t T) TypeLen() int   { if l := traits[t].typeLen; l.ok { return int(l.n) }; panic(…) }
```

- **Flags, not one `Family` value.** The existing predicates overlap and
  have exceptions (`IsSignedInt` leaves out `int128`, `IsFloat` includes the
  low-precision floats, `IsOrdered` cuts across families), so a single family
  value per type could not reproduce them.
- **Zero means "absent".** A size left out of a row means "no size": the
  method panics, as it did for an unlisted type, instead of silently
  returning 0. The same goes for the default type (`TryToType` reports
  false) and the names.
- **Unexported for now.** The predicates are the API. The row type is
  exported when a caller outside `types` needs it. `AllOids()` is exported
  for the completeness tests of other packages' tables.
- **Index by value, not pointer.** `traits` is an array of values, so a
  lookup is one load with no nil check; `T` is `uint8`, so there is no
  bounds check either.

### Layer 2: per-package operation tables, for code that `types` cannot import

Operations that take a `*vector.Vector` cannot live in `types`: `vector`
imports `types`, so the reverse import would be a cycle. Each package that
does physical dispatch keeps its own table, indexed the same way and filled
in one file:

```go
// pkg/container/vector/type_ops.go
type TypeOps struct {
    AppendAny   func(v *Vector, val any, isNull bool, mp *mpool.MPool) error
    GetAny      func(v *Vector, row int) any
    CompareRows func(a *Vector, i int, b *Vector, j int) int
    // … chosen from the Step 1 inventory, not guessed now
}

var typeOps [256]*TypeOps

func init() {
    typeOps[types.T_int32] = fixedOps[int32]()
    typeOps[types.T_date]  = fixedOps[types.Date]()
    typeOps[types.T_varchar] = varlenOps()
    // … one line per type
}
```

Go generics are resolved at compile time, so a table cannot hold "call
`f[T]`" as a pattern. It holds the already-instantiated function values
(`fixedOps[int32]()` returns closures built for `int32`). This is the same
technique `sql/plan/function` already uses for overloads.

Expected tables: `container/vector` (pilot), `vm/engine/tae/containers`,
`common/hashmap`, `vm/engine/readutil`, `sql/colexec/aggexec`, and
`frontend` for wire encoding.

### Making completeness a test failure

- `types` exports `AllOids() []T`, the canonical list of type ids. It is
  checked against the `T_` constants by a test that parses `types.go`, so it
  cannot drift.
- Every table has a test that walks `AllOids()` and fails for any type with
  a nil entry or a nil operation. A type that deliberately does not support
  an operation is entered explicitly as `unsupportedOp(oid, "AppendAny")`,
  which returns a typed error. Nil is never allowed.

### Checking the switches that stay

Extend `TestTypeSwitchFamilies` (see "What already exists") instead of adding a
second mechanism:

- **More families.** Add integer (signed, unsigned), decimal, temporal,
  character string, binary string and JSON. Membership comes from the `T_`
  constants and the traits table flags, so a type added to a family is checked
  at every switch that names part of it.
- **An "all types" rule for dispatch switches.** A switch that names at least
  half of all type ids is treated as a full dispatch and must name every one,
  or carry `typeswitch:partial`. This catches the 20+ switches that today fall
  to `default:` for a new type.
- **Same workflow.** `typeswitch:partial <reason>` for intended omissions; one
  baseline per rule, which may only shrink.

Many partial switches are really "is this type in family X" questions. These
should be rewritten with the `IsXxx()` predicates (adding one, backed by a
table flag, where none fits) instead of being tagged.

The [`exhaustive`](https://github.com/nishanths/exhaustive) linter
(`default-signifies-exhaustive: false`) is the alternative. It is stricter
(every switch on `types.T` must list every value) and needs no project code, but
it flags every partial switch at once, has no notion of families, and duplicates
the tag-and-baseline workflow the repository already uses. Extending the
existing test is preferred.

### Hot loops

The rule for hot paths: look up the table entry or typed accessor once per
vector, outside the row loop, then run a loop that does not box values. For
example, for `fillNullableStr`:

```go
enc := keyEncoderFor(vec.GetType()) // table lookup, once per vector
for row := … {
    keys[i] = enc(keys[i], vec, row)
}
```

The `any`-based helpers (`AppendAny`, `GetAny`, TAE `Get`/`Append`/`Update`)
stay for slow paths (tests, tools, DDL) and go through the table, so they
also become complete. Hot callers move to typed accessors.

## Plan

Each step is a separate PR and leaves the build green.

| Step | Work | Size |
|---|---|---|
| 0 | This design doc | doc only |
| 1 | **Done.** AST scanner `optools/oidscan` (its own module, standard library only): switch counts, case-count histogram, switches inside loops, and which of those have a loop-invariant type. Its `-loops -invariant` output is the worklist for step 6. | small |
| 2 | **Done.** Move the type switch out of the row loop in `multi_update/insert.go`, `preinsert/preinsert.go` (both now share `colexec.CheckZeroTemporalVector`, which also removes a duplicated function) and `postdml/postdml.go`. Remove `deletion`'s incomplete `getNonNullValue` copy: it boxed the key and passed it to `AppendAny`, two type switches per row; it is now a typed `UnionOne` copy. | small |
| 3 | **Done.** The traits table and `AllOids()`. `String`, `OidString`, `TypeLen`, `FixedLength`, `TryToType`, the `T.IsXxx()` predicates and `Type.IsInt/IsUInt/IsFloat/IsDecimal` read the table. The old switches are kept in a test file as an oracle, compared for all 256 `T` values including panics. Further tests: every `T_` constant has a row, and the float and vector flags match the `TestTypeSwitchFamilies` families. Benchmarks: the table is as fast as or faster than the switches. | medium |
| 4 | Pilot: `container/vector` `TypeOps`. Move `AppendAny` and the large dispatch switches in `vector` onto it. Benchmark before and after. | medium |
| 5 | TAE: move `vm/engine/tae/containers` (`getNonNullValue`, `UpdateValue`, wrapper `Get`/`Append`/`Update`) onto the `vector` table. | medium |
| 6 | Hot paths: `strhashmap` key encoding, `frontend` result-row encoding, `export.go`, `jsonToNumeric`/`castToJSON`, with a benchmark for each. | medium, one PR per area |
| 7 | Extend `TestTypeSwitchFamilies` with more families and the "all types" rule; each new rule lands with its baseline, then the baselines are worked down package by package, starting with `container/*` and `vm/engine/*`. | large, many small PRs |
| 8 | The remaining physical-dispatch packages (`readutil`, `aggexec`, `hashmap/keycodec`, `compile`). | medium |

After step 7 covers all of `pkg/`, adding a type means: add a `T_` constant,
add one row to `traits_table.go` and one row to each layer 2 table, then fix
whatever `TestTypeSwitchFamilies` and the table completeness tests report.

## Testing

- Completeness tests for every table (above). These are the main guarantee.
- No change in behavior for steps 2–5 and 8: existing unit tests and BVT must
  pass unchanged.
- Benchmarks for every hot-path change in step 6, with results in the PR
  description; a change that is slower does not merge.
- A test that adds a fake `T_` constant in a test build and checks that the
  completeness tests fail, so the guarantee itself is tested.

## Risks

- **Baseline size.** About 630 switches have a `default:`; each new rule
  starts with a large baseline. Mitigation: one family at a time, and prefer
  family helpers to `typeswitch:partial` tags.
- **Indirect calls slower than an inlined switch in tight loops.** A
  function-pointer call is not inlined. Mitigation: hot loops use typed
  closures fetched once per vector, never a table call per row; step 6
  requires benchmarks.
- **Package init order.** Tables filled in `init()` must not be read by other
  packages' `init()` before they are filled. Mitigation: build tables from
  package-level variable initializers where possible; the completeness test
  runs after init and catches a nil.
- **Stored formats.** No `types.Type` layout change, no codec change. Nothing
  on disk or on the wire changes.
