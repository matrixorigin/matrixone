# Ordered pagination: one-shot scan cutoff

Status: approved for implementation
Issue: [#32061](https://github.com/matrixorigin/matrixone/issues/32061)
Design baseline: MatrixOne `ee2ba4185dd5b0a3c1678ab8f188a48ee81efb64`.

## Problem and goals

A large `ORDER BY ... LIMIT L OFFSET O` typically uses external `Order` followed by `Offset` and `Limit`. The planner already establishes an ordered scan and a `TopValue` message path for eligible leading columns, but `Order` has no producer of a cutoff. A 1.5M-row public SQL reproduction on the baseline fed all rows to `Order` for a primary key, a correlated unindexed column, and a random unindexed column. A two-CN, 5M-row reproduction showed the same behavior. Small K already uses `Top(K)`; raising its resident threshold causes per-worker K-sized state and can still fail to publish when no worker sees K rows.

Goal: reduce irrelevant scan and sort work for any eligible ordered column and eligible filter, independent of whether it is a PK or index, without changing SQL pagination results or evaluating expressions on fewer rows unless doing so is semantically safe. The mechanism must use the existing scan, sort and message ownership; not create a second scan, per-row heap, persistent index, global cache, or cross-CN rank protocol.

Non-goals: skipping the `OFFSET` prefix, promising work reduction for random/overlapping block ranges, or making K near the input cardinality cheap. Nullable leading keys, collation domains, source kinds, plan shapes or types whose ordering and visibility contracts are not proved use the existing path. In particular, a general NULLS FIRST solution requires a proof about NULLs in unread blocks; a runtime check of observed rows is insufficient. No query-level I/O optimization can also promise to surface an error from a block that the query no longer reads.

## Invariant and algorithm

Let K = L + O, computed only from proven-safe bounds with checked unsigned addition. For one source scope S, every observed tuple must have passed that scope's snapshot visibility, committed and workspace deletes, and semantic filters, and be accepted exactly once by its local `Order`. All S tuples must feed the same complete downstream ordering and pagination.

For ascending order, a cutoff T is valid after at least K distinct accepted tuples have leading keys <= T. For descending order, the inequality is reversed. At a valid cutoff, any unread block whose best possible leading key is strictly worse than T cannot contribute to the first K tuples: the K witnessed tuples precede it. Keep blocks at equality so secondary-key winners and ties survive. Unknown, incompatible or nonconservative bounds are read. Source scopes may establish independent cutoffs: a scope's K valid witnesses are also K witnesses in the complete input. No scope subtracts from O or assumes another scope's count.

Use one execution-generation summary per eligible scan scope: K, a count saturated at K, a conservative worst leading key, a small mutex, and an atomic collecting/published/disabled state. Workers observe a batch only after `Order.appendBatch` succeeds. This avoids counting a `pendingInput` twice when a run is flushed before that batch is appended. Compute extrema outside the mutex, then merge a copy of the batch's outward bound and add `min(batchRows, K-count)` while holding the mutex. The bound covers the complete batch even when its count is saturated. The worker that reaches K freezes the bound, marks publication once, releases the mutex, and publishes one existing CN-local `TopValueMessage`. No I/O, send, wait or callback occurs while the summary mutex is held. Other workers stop computing extrema after observing the atomic terminal flag. A batch already in flight can finish its computation and must not republish.

Only batches whose key representation and comparison are proved valid contribute. A non-null constant vector is summarized from its single physical value and its logical row count: `GetMinMaxValue`/`BatchUpdateZM` currently can index past a one-value constant vector. Empty, inconsistent, NULL or unsupported vectors fail closed before publication. Unread NULLs must already be excluded by a physical non-null proof, not by the sample. A summary's retained key is owned, never an alias into an input vector. For fixed-width supported values, use matching type and scale. For byte-ordered variable-width values, construct the point from the outward maximum for ASC or outward minimum for DESC; an unbounded truncated maximum cannot certify an ASC batch. Historical/truncated block bounds that cannot safely exclude a block must fail open. The exact supported domains are the intersection of total SQL comparison, vector-extrema and storage-zone-map contracts, not a PK/type-specific query rewrite. Float/NaN, decimal256, JSON, geometry, arrays, case-insensitive/Unicode collation and CHAR padding remain disabled unless separately proved.

## Ownership and integration

The planner's existing Top-to-scan lineage owns the association between the first sort key and one source scan. Reuse its expression/column mapping and the existing `PreparedPaginationTopInputSafe` total-and-effect-free scan/filter/project proof; require a direct, unambiguous physical leading key and a proof of non-nullness. A safe filter is supported because witnesses are observed after it; do not infer safety from determinism alone. Do not enable for joins, runtime-filter paths, lock/DML, rank/with-ties, effectful or potentially diagnostic expressions, non-preserving projection, ambiguous lineage, unknown source or unproved physical topology. Disable for the entire `SQL_CALC_FOUND_ROWS` statement. Unsupported/unknown cases retain the original operators, diagnostics, and reader behavior.

`compileSort` already owns LIMIT/OFFSET evaluation and the choice between small resident Top and external Order. Reuse a previously proven constant result, and generalize the existing prepared-pagination bound parser rather than evaluating a second expression. Parameter bounds must be derived freshly for each execution, use checked decimal arithmetic and every signed/unsigned source-domain limit, and never suppress the existing error or conversion path. NULL, zero, negative, noncanonical, overflow, unknown conversion or unbound values fall back. Preserve the existing resident Top threshold and existing Top behavior.

Prepared TP pipelines can be cached by parameter category and reused for different values. They therefore retain the existing path; AP prepared executions compile statement-owned physical scopes and may derive a fresh bound on each execution. Supporting cached TP plans later requires binding the hint during each execution, not retaining the first K in the reusable operator.

For an admitted external `Order`, carry K and the existing message tag as an optional execution hint to the exact scan scope. Construct a fresh scope-owned summary before its workers start and share it only among `Order` clones for that scan generation. A single-worker scope gets the same semantics. Readers keep the existing `SetFilterZM` and zone-map pruning path. Arrange a single tag/broadcast that is received by all associated workers without disturbing the existing per-worker `Top` tags; prove unique producer and matching receivers. Initialize ASC/DESC direction before a reader can consume a cutoff. Do not mutate shared range lists or cache a cutoff in the reusable logical plan.

For multiple CNs, each actual scan scope has its own summary, tag receivers and snapshot-bound witnesses. A remote `Order` must receive the optional checked K/tag through existing compatible `Instruction` fields; decoding must validate the hint and cannot make a query depend on it. `TopValueMessage` remains CN-local and is never serialized. Unknown, combined, partitioned, sharded or otherwise unproved source topology falls back. The current repository supports shutdown upgrades; this does not change persisted formats. Remote enablement is conditional on round-trip, remote-reader, cancellation/failure, and multi-CN snapshot tests, including cases with fewer than K candidates in one CN.

The source scope and its existing worker-join boundary own the shared summary. Worker `Reset` must not clear it while siblings may still run. Partial construction discards it with the failed generation; success, error and cancellation release it after workers are quiescent. A retry or prepared execution receives a fresh summary and message-board generation. A failed witness worker causes the query to fail through the existing pipeline; no successful result may rely on witnesses whose delivery was lost. Sending to a closed board is handled by the existing nonblocking message boundary. The summary and message-board mutexes may contend, but the design does not wait for another worker, acknowledgement, remote operation or I/O; it sends only after releasing the summary mutex. It introduces no goroutine, timer, background task, new persistent state or user-facing setting.

## Cost and admission

Before K is reached, extrema inspect at most K qualifying rows plus the crossing and already-in-flight batches; when K is not reached, they inspect all qualifying rows. Reuse the reader's ascending sorted-vector metadata to take the first/last values instead of scanning an already sorted key batch; this remains ascending metadata for a DESC query, and const, NULL, representation and outward-rounding checks still apply. Unmarked vectors retain the full extrema pass. Each observed batch takes one short lock; each source has O(1) shared memory, one fixed-size scratch bound per active worker, and one broadcast. After publication the cost is a cheap atomic check per batch. Variable-length comparisons additionally cost bytes examined. Memory must use the existing query accounting/admission model where applicable; the bounded state and owned keys cannot outlive the attempt.

There is no hardcoded `N >= 4K` or issue-specific cardinality threshold: a real 1.5M-row/K=500005 experiment showed useful pruning despite failing that proposed gate. Reuse existing estimates only for transparent cost choices, never correctness. Avoid a second metadata scan just to predict benefit. The admitted path must be measured against unchanged Top/small-limit, no-OFFSET, random-key/no-pruning, high/deep OFFSET, K >= N, selective-filter, different DOP, one/multiple CN, cold/warm and wide-row controls. If it materially regresses common ineligible or no-pruning workloads outside noise, revise admission or decline enablement rather than claim a win from one case.

## Alternatives

A gate-only `Top(K)` change retains K references per worker and does not help when each worker sees fewer than K rows. Metadata-based suffix pruning requires a complete snapshot-safe upper bound on all relevant deletes and a proof that physical counts survive filters; object sort-key metadata also does not cover arbitrary sort columns. Exact prefix pruning like DuckDB's row-group approach needs exact visible, filter-qualified prefix counts, global order proof and a synchronized OFFSET adjustment; it can improve very deep pages but is a separate complexity and product decision. These alternatives do not meet this change's generality/complexity balance as the first step.

## Verification and acceptance

- Unit tests compare the cutoff invariant to an independent full-sort oracle across ASC/DESC, duplicate and secondary keys, variable batches, K boundary/overflow and no-publication, const vectors, type/scale, outward string truncation, missing metadata, and pending-input flush/replay. Prove every candidate tuple is counted at most once.
- Typed plan/compile tests prove actual admissibility, exact scan/order/tag association, safe comparison filters, unsupported operators/expressions and `SQL_CALC_FOUND_ROWS` fallback, bound parameters with source-domain/overflow/reuse, and unchanged small-K Top. Public SQL tests compare exact rows against full-sort controls and include NULL/unsafe/error-producing fallbacks.
- Lifecycle and race tests cover one/many workers, skew, each worker < K but scope >= K, scope < K, concurrent publish/board close, error, cancellation, partial construction, reset/retry and prepared reuse. Validate cleanup after the last worker, not just no panic.
- Local and distributed SQL tests cover both coordinator placements, independently scoped CNs, committed/in-memory/workspace deletes, old snapshots and compaction, remote tombstones and unknown blocks. Include remote encode/decode and actual local/remote reader consumers. Fault injection must prove failure propagates rather than returning a partial page.
- Derive final incremental SCA and UT/race scope from the full delivery diff. Run focused and owning-package checks, affected consumers and public-path tests with terminal statuses; record selection, toolchain and source fingerprint. Compare paired performance with identical data and config, recording latency distribution, rows/blocks/bytes, allocations, peak memory, spill and metadata I/O. A loaded host's exploratory samples are not release-quality latency proof.
