# Exact COUNT(DISTINCT) optimization backport to 4.2-dev

Owning issue: [#27672](https://github.com/matrixorigin/matrixone/issues/27672).
Source implementations: [#27693](https://github.com/matrixorigin/matrixone/pull/27693), commit `dfef35f7dd94de507d40dd18082b64e7f4b84e40`, and [#28431](https://github.com/matrixorigin/matrixone/pull/28431), commit `98171c28dbeb7ad1291ce9b0eb5beff7a84cbc32`.
Implementation: the combined backport PR from `XuPeng-SH:codex/backport-27693-28431-42` to `matrixorigin:4.2-dev`; its URL will be recorded on publication.
Design base: `db0a7e76881bba94c2a86504ed8e3b2463fc6835`. This document is committed and reviewed in a distinct design-only phase before production implementation.

## Problem and scope

Mixed SUM/COUNT/AVG/COUNT(DISTINCT) aggregation retains an exact argument set that can be much larger than its final group table. The target costs only the latter and forces every DISTINCT aggregate to one worker/CN. Its ordered skiplist also rebuilds retained keys during fixed-size arena growth and performs ordered lookup per candidate. These are the mechanisms addressed by the two source optimizations; their original timings do not establish performance on 4.2-dev.

Preserve exact SQL counts, NULL handling, group ownership, public errors, cleanup, and legacy aggregate serialization. Port the core fixed-width state and DISTINCT-aware shuffle optimizations using the target's existing owners. Do not transplant unrelated later-main aggregate accounting or DISTINCT-spill features. The target already provides the MPool allocation ceiling. The missing cached-Inserter correctness and floating signed-zero prerequisites are included only at their necessary contract boundaries.

## Chosen branch-native closure

### Planning and compiler ownership

1. Add one shared planner predicate like upstream `RequiresSingleStageDistinctAgg`: identify the base overload after masking DISTINCT and return true if **any** DISTINCT is not COUNT. COUNT is mergeable because `countColumnExec.BatchMerge` unions saved arguments; non-COUNT DISTINCT stays on the target's existing one-CN/one-worker path. Mixed COUNT-DISTINCT plus another DISTINCT inherits the conservative path. Use the same predicate in `CalcNodeDOP`, planner shuffle eligibility and compiler fallback; do not retain the existing blanket `AnyDistinctAgg` decision for COUNT. Preserve the target's ordered `GROUP_CONCAT` and protocol checks.
2. Adapt #27693's distinct-state cost rule to target planner APIs: only mergeable COUNT-DISTINCT argument NDV contributes; cap by input rows and apply valid selection estimates; reject non-finite/missing values; preserve the standard path where the new rule does not apply; demand at least 64 estimated surviving logical group owners and supported integer/string distribution keys. Low state/input ratio, missing stats, and unsupported keys preserve the existing topology.
3. A grouping-set key that `GroupingFlag` makes inactive is replaced by a rollup constant inside Group, so never distribute on it. An empty grouping set has no safe key. This condition applies to both ordinary and new DISTINCT-driven shuffle selection, not only the new threshold. Explicitly clear stale shuffle for a non-mergeable DISTINCT node.
4. At compile time only skip a **normal** shuffle if scheduling exposes one physical aggregate owner (one CN and DOP <= 1); preserve every input, and select the same ordered/single-scope/merge-group fallback as the non-shuffle path. Reuse a JOIN partition only for INNER joins; NULL extension on an outer join can collapse different preserved-side partitions into one logical NULL group, so those plans require a fresh group shuffle. Proven reused shuffles retain their existing placement; multi-CN at DOP 1 still provides multiple owners. Pipeline delivery is `producer -> shuffle/dispatch -> receiver -> Group -> result`, with reset/error/cancel/close following existing operator cleanup. Equal logical group keys must always select the same owner; no final merge may be omitted unless that invariant holds.

### Branch-native exact fixed-width state

1. Use the target `aggState` and its existing 8192-group chunk ownership; enable the index only for true `COUNT(DISTINCT ...)` of exactly one fixed-width argument, width 1..8 bytes, on sufficiently large physical chunks (the source uses a 1024-group-capacity activation threshold). Unsupported, variable-width, wider, multi-argument, and order-sensitive states remain on the skiplist. A one-group state may retain the old path. No query-wide preflight or accounting framework is required.
2. Adapt the source columnar open-addressing index: slots store the **complete** local group number and canonical value bits, not a hash fingerprint. Probe and compare both fields, use power-of-two capacity with <70% load, and cap probes at the table length. A malformed/full table returns a bounded invariant error; collisions cannot change cardinality. Maintain a per-group log of values for iteration/serialization/merge. The full group identity includes the state-chunk selection (`getXY`) as well as the local group; batch dedup must use the original full group ID, never the local uint16 alone.
3. Each state chooses one authoritative representation before first key publication. An optional index whose initial allocation fails may revert to the existing empty skiplist, after freeing any partially allocated columns. A published index may not silently switch; an inability to grow returns an error. Use `mpool`-allocated arrays and the existing pool/global allocation caps; allocate all necessary slots/log space before publishing each key. Check integer/slot/log/count bounds before publication, and release all partially allocated replacements on failure. Set the slot, group log, and `argCnt` only as one successful per-key commit. A failed batch or merge can retain **earlier** successfully published keys, as in the target API, but every retained count and representation must still agree; the query error must not cause retry of a partially applied batch. Do not claim upstream's all-batch/query-account admission guarantee.
4. For fixed-to-fixed merge, copy complete values for the selected source group and deduplicate into the destination; for fixed-to-legacy and legacy-to-fixed merge use a common iterator or equivalent direct conversion. Read both source and destination chunk offsets explicitly. Never copy only count totals. Empty states, duplicate input, `GroupNotMatched`, NULLs, constant vectors, and repeated groups must behave like the current SQL contract. If source and destination can alias, keep source iteration valid through growth or handle that case explicitly; establish the call-graph boundary rather than relying on stale pointers.
5. Route `writeStateArg`, `readStateArg`, `appendFromStateArg`, `iter`, merge, and `free` through representation-aware helpers. Write exactly the target's existing per-group count plus fixed-width raw-value payload, with no new external tag; count-DISTINCT result is set-based so log order is not contractual. Read old skiplist-produced payloads into either representation and allow the old format to read current output. Consume the declared number of payloads even if normalization coalesces keys, and derive retained count from unique successful insertions. Reject malformed/truncated widths, invalid groups, non-terminating/corrupt index structure, and overflow as controlled errors; test the public unmarshal path, including cleanup (the target's deferred magic check currently needs careful review). Preserve legacy non-DISTINCT encoding and ordered aggregates unchanged.
6. Release each index buffer, legacy arena, counts, and any partial replacement exactly once on normal `Free`, deserialize error, reset/reuse, cancellation, and operator close. Clear the actual stored state rather than only a copied `range` value; repeated cleanup must be safe. The producer owns state until an explicit transfer; no old iterator, index column, or inserter may access a freed/reused generation.

### Floating-point key policy

The target currently feeds `Vector.GetRawBytesAt` directly into distinct saved keys, so unlike the source PR parent it lacks #27434's signed-zero normalization. Adopt that narrow prerequisite consistently for all affected DISTINCT input paths, including single and composite keys, the fixed index, and legacy skiplist. Treat +0 and -0 as the same key; retain all other raw bits, including individual NaN payload identities. The normalization helper must handle constant vectors and copy rather than mutate input. Decode legacy fixed and composite payloads with the same policy, coalescing a legacy +0/-0 pair and recomputing the retained count while consuming the complete record. Ensure legacy-to-fixed, fixed-to-legacy, reload, and merge have identical equality. This is a deliberate correction to a pre-existing target behavior, not evidence the old branch already implemented the source contract.

### Skiplist merge and relocation

1. Port the seven-line #27688 `findSplice` cached-successor equality check and a deterministic overlap regression **before** using a cached Inserter in sorted legacy merges. The target has `Inserter.Add` but lacks that equality check; otherwise a cached successor can be inserted twice. A source fixed-index log is not sorted, so do not apply a monotonic-target assumption to it.
2. Relocation must be before `Add`: `Arena.alloc` increments `n` even when it returns `ErrArenaFull`, while source `GrowArena` rejects that poisoned size. Before insertion, with exclusive aggregate-state ownership, validate key length and compute `Arena.Size + arenaskl.MaxNodeSize(keyLen, 0)` in a wider type. If insufficient space, first recognize duplicate keys without allocation; then allocate an independent geometrically grown arena, cap by `mpool.MaxAllocationSize` and uint32 arena bounds, copy/rebind offsets, publish the new arena, and only then free the old one. A smaller chunked candidate at least as large as the true requirement may be retried only for classified pool capacity pressure, not invariant, ownership, or allocator-limit errors. If an already-poisoned list is nevertheless encountered, the source list can only be rebuilt by iterating its published links into a valid replacement; never claim direct relocation of a poisoned arena succeeds. Error paths retain a valid cleanup owner.
3. `GrowArena` requires no live `Iterator`, cached Inserter, or external Arena handle and no concurrent reader/writer. Close/recreate or reseek any monotonic target iterator around a growth; clear the cached Inserter immediately on relocation. Source iterators must similarly remain valid if source and destination alias. Sorted-skiplist merge can reuse a cached Inserter and, if a target iterator is added, it must only move monotonically over sorted candidates between relocations. Avoid any second generic preflight framework.

### Compatibility, resources, and alternatives

- The target explicitly disables group spill for DISTINCT (`group/types2.go:157-168`, with the existing ordered-group-concat exception). #28431's later `distinct_spill.go`, hard aggregate-account, drain/rehome, and transactional batch-preflight changes depend on independent features absent here. Retain this branch policy: this work does **not** enable or backport DISTINCT spill, does not claim its spill recovery or bounded hard-account semantics, and does not change existing non-DISTINCT spill. Group and MergeGroup create operator-local pools with zero configured capacity; on this target that maps to a nominal 1 PiB pool cap, not evidenced per-query or tenant admission. The proven bounds are the configured shared global off-heap cap, single-allocation ceiling, actual allocator availability, and checked cardinality/integer limits. Allocation errors remain authoritative; no new query-account guarantee is claimed. This is a material behavioral difference from main, not a test omission.
- All index and growth memory is owned by the aggregate chunk and allocated off-heap through its MPool (`mpool.MakeSlice(..., true)`), so it participates in the shared global off-heap cap. Any transient Go scratch is bounded by the current batch size and accounted for separately in the cost model. Retained memory consists of `10*slots + 12*logCapacity + 4*groupCapacity` bytes plus Go slice metadata and any retained legacy arena/count buffers; geometric replacement temporarily retains old and new buffers. Load threshold <70%, uint16 group limit, int32 log-link and uint32 count limits, checked arithmetic, single-allocation ceiling, and pool/global caps bound the data structures. With spill disabled, a high-cardinality DISTINCT can exhaust the shared global off-heap budget and fail, affecting other users of that global budget; operators must close and release memory on that error. In a non-shuffle parallel COUNT-DISTINCT plan, one value can be retained in several worker states while a merge destination is also live, so peak state memory can scale with worker count and overlapping merge ownership. This is an accepted branch limitation, not isolated admission or a spill guarantee. No new goroutine, queue, disk file, or wait is introduced.
- Upgrade/rollback is by full service shutdown; intermediate aggregate state is query-local, not persistent user data. Preserve the target wire/intermediate payload to support old and new representation readers and ordinary group serialization; no invented mixed-version live-upgrade gate. Existing non-DISTINCT on-disk spill behavior and compatibility remain unchanged. There is no catalog, configuration, authorization, or tenant-trust boundary change. Group partitioning applies per execution, while memory admission remains the target's existing operator-pool/shared-global model; no per-query or tenant-isolated bound is asserted. No new global mutable state or unbounded labels/logs are introduced.
- Alternatives: (a) status quo is safest but retains serial Q10 and skiplist costs; (b) transplant the upstream full aggregate account/preflight and #28003 DISTINCT-spill feature implements later-main behavior but expands architecture and compatibility scope well beyond these optimizations; (c) an independent radix DISTINCT pipeline could handle single-group/skew cases but adds a separate distributed representation and requires another design. The chosen path adapts existing group shuffle, exact state, and serialization and explicitly retains the target spill limitation. It does not promise better performance for a single group, severe skew, missing statistics, or variable-width arguments.
- Rollout/fallback uses the existing planner's non-shuffle topology for ineligible or unknown-stat cases and the empty-state skiplist fallback under allocation pressure. Diagnosis uses existing plans/operator stats and MPool metrics; no new global metric is necessary. A benchmark result is needed before a quantitative speedup claim.
