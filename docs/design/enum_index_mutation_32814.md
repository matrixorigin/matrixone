# Issue #32814: ENUM index mutation and legacy SET coexistence

Design author: `gpt-6.1-terra`, `max`, session `/root/enum_design_review`, 2026-11-16. Scope: both branches. This proposes a narrower alternative to globally changing SET index backfill and mutation; it requires independent versioned design review before implementation. No product worktree was modified.

## Evidence

* Official 4.2.8 on the same scripts: without an index, deleting the tested row affects 1; with an inline ENUM/SET index, 0; with an ADD-built index, 1 (`release428-enum-index-delete.*`, `release428-set-zero-delete.*`). The current 42 physical-backfill candidate makes the ADD case affect 0 (`42-enum-index-delete-prepatch.*`, `42-set-zero-delete-candidate.*`). This is a concrete regression, although inline failure predates this PR. The 42 plan joins the old image to the hidden index by `serial_full(display(e_or_s), pk)`, so a raw-encoded backfilled key cannot match.
* `42-enum-set-index-update-prepatch.out` shows tested ENUM inline/ADD updates affect 1, whereas SET inline affects 1 and ADD 0. Do not generalize one UPDATE's path to DELETE or another column/domain. Main pre-SET candidate's ENUM inline/ADD/no-index DELETE each affects 1; SET inline affects 1 and old bad ADD 0 (`main-enum-index-delete-prepatch.*`, `main-set-zero-delete-prepatch.*`). Main target base already normalizes DELETE old images (`bind_delete.go`, commit `1a24bdbc7f50`) and has `physicalMySQLSpecialRefs` for the sequential UPDATE route. 4.2 does neither in DELETE. The target proto on both branches lacks `enum_collation`, so a supported pre-feature catalog cannot author the new nonzero plan identity through that field; validate the actual upgrade/wire conversion before relying on that fact.
* Historical ADD and inline/post-insert rows can coexist in one index with display-string and physical keys. A plain catalog index name or relation ID does not reveal individual row provenance. Labels are non-injective: ordinal 0 versus a valid empty ENUM member and SET bitmaps 0 versus 1 can have identical display. Casting a display label back to its SET domain cannot recover the old bitmap; the existing numeric cast can also validate/mask bits, so it is not evidence of a lossless old-row transfer.
* A genuine main identity-0 old catalog created by 8e8708 and upgraded to the candidate retains legacy SHOW/LIKE behavior, but ADD of the same ordinary ENUM prefix changes hidden bytes from display strings to ordinal-derived strings (`main-oldbase-enum-prefix-hidden.out`, `main-prefix-oldcatalog-prepatch-hidden.out`). This proves a legacy catalog regression. 8e8708 is not the exact f491 target baseline, so retain that additional comparison.

## Compatibility options and decision

**Recommended scope:** correct physical index construction/mutation only for an index that actually depends on the new nonzero ENUM identity. An index depends on it when any key part or its base primary-key payload/serialized PK component is a resolved ENUM whose persisted `EnumCollation` is nonzero. Include named PK components behind a synthetic composite PK, not just `IndexDef.Parts`; use resolved source types, schema generation and actual index algorithm. Other ENUM identity-0 or SET-only indexes follow each target branch's historical ADD and mutation behavior, including the already-known defects. This is per index, not per table: adding an unrelated new ENUM column must not change an old SET-only index. This scope decision does not claim pre-existing SET or legacy ENUM bugs are corrected.

For an index with new nonzero ENUM dependence, all special-type key/PK components required by the chosen writer, including SET and identity-0 ENUM in the same compound key, use the same physical values and serializer as inline DML. Preserve ENUM identity, domain and encoding; SET retains its bitmap. This prevents a new `(new_enum, set)` ADD index from reintroducing the mixed string/bitmap failure. Initial conservative admission rejects an identity-0 ENUM **prefix** mixed with any nonzero ENUM key or PK in the same affected index until raw-prefix inline/ADD/UPDATE/DELETE equivalence is independently proven. This narrow mixed case has no old-format compatibility claim. A nonzero ENUM prefix remains subject to the separately reviewed rejection. Other old identity-0 prefix-only indexes keep the existing prefix policy. MASTER/other index algorithms require separately approved algorithm-specific writer and PK semantics; if the classifier cannot prove them, reject just the affected new combination before publication.

The tradeoff is explicit: this avoids forcing repair of historical SET/identity-0 indexes merely to ship ENUM collation identity, but leaves their observed ADD/inline/read/mutation inconsistencies as existing limitations. A separately scoped SET fix may repair them later. Exact CREATE/ALTER, old SQL/metadata replay and error behavior for those legacy indexes must be compared with official and target baselines; changing an old index merely because a different index on the table uses the new identity is a regression.

This classification is sound only under an operational release boundary: pre-feature supported catalogs contain no nonzero ENUM collation field, all new authoring occurs with the accepted stopped-cluster/protocol floor, and no old writer rejoins. Validate old native type bytes, protobuf/catalog conversions, the supported stopped upgrade and historical snapshot instead of inferring identity from collation spelling. Current experimental/prerelease candidate catalogs can already contain mixed nonzero indices; they have no trustworthy provenance bit and are **not automatically covered** by this argument. Preserve access and provide an explicit tested rebuild/fail-closed path, or add a separately reviewed durable index-format marker/validator if such catalogs must be supported. The pre-existing 4.2→main new-format bridge hold remains in force.

## Two row-image representations, one mutation

The owner binds target rows and predicate/order/limit as before. For the planner-generated old target image only, carry a separate hidden physical projection with the exact source relation, column, domain, ordinal/bitmap and NULL; do not reconstruct it from the visible value or set a binder-wide raw flag. Main's generated `physicalMySQLSpecialRefs` is one possible mechanism, but a marked reference must be source/alias/type-checked and belong to the internal image, not a user WHERE, ORDER BY, RHS, subquery or public SELECT. Keep the original display projection available to every legacy index and to user-visible expression binding. Track both positions through PROJECT, SORT/LIMIT, target-row DISTINCT, materialization, sink/scan and remapping; optimizer pruning must retain exactly the required hidden columns. Reject an unproved source or a barrier that loses physical identity before mutation rather than recasting display. ORDER BY/LIMIT must choose the same rows as baseline; RETURNING must still bind labels, numeric expressions and NULL correctly. Do not simply append a second identical `alias.col` to the ordinary SELECT list: 4.2 `OrderBinder.BindExpr` searches `projectByAst` and can choose the last same-name projection, turning an ordering expression into the raw slot. Inject the internal tail after user ORDER binding or explicitly exclude it from alias, positional and `projectByAst` resolution, then carry it across the completed ordering plan.

For each affected new-identity index, build its old-key comparison from its physical image with the same full/partial key operation and serialization as its writer, including physical PK and NULL rules. For a legacy-only index, use its exact pre-change branch-specific old-key expression; do not assume the 42 DELETE path and UPDATE path, or main and 42, are identical. Where the same source column is present in multiple index roles, each index independently chooses the correct image. Existing hidden-index join/lookup, affected-row count, duplicate checks, locks and input row cardinality must remain correct: one matching base row is changed once, not once per index match. Preserve error and cancellation atomicity. In UPDATE, distinguish the old indexed value from the independently bound user RHS/new value: identity-aware assignment still converts RHS according to target semantics, while unchanged columns and old-index removal use the correct old image. Preserve generated/virtual, ON UPDATE, RETURNING, multiple source-table, alias/tenant and dedup semantics under their actual supported contracts.

This narrow design does not repair bad old indexes: for old-only indices it deliberately retains old behavior. A newly built new-identity index must never read an old broken secondary index as its authoritative backfill source; scope owner-only source-scan protection or prove the final physical plan uses the base relation. Ensure all index keys and PK payload are authored in the selected format before publishing the index.

Every transition that changes an index's classification or physical PK/key domain (including legacy→nonzero or nonzero→legacy ENUM changes, VARCHAR→ENUM, renamed/reordered PK parts and ALTER COPY/INPLACE) must atomically rebuild **all affected** hidden indices from the same authoritative base snapshot with the destination format, or fail the ALTER before any schema/data publication. Disabling/replacing/dropping an index in the same statement is resolved from final schema using the branch's accepted action-order semantics. Do not silently use old keys under a new classifier. SHOW/LIKE, typed dump, snapshot/restart, clone and backup recovery must either preserve a valid format and identity together or explicitly fail before publication.

## Why transparent universal fallback is not yet proven

A nonunique hidden table carries `__mo_index_pri_col`, so for a proven **lossless exact physical PK payload** a separate hash equijoin on that PK could find old display-tag and new raw-tag keys, including multiple stale entries, without enumerating exponentially many mixed key forms. Materialize target rows once, independently collect and delete distinct hidden rowids per index, then mutate each base row once; do not chain fan-out joins into a cross product. An orphan/missing index row must not silently drop a qualifying base row, NULL must not create spurious matches, and update insertion/constraint/error handling must remain atomic. It is not an unbounded nested loop, but may scan large hidden indexes and needs strict memory/spill/runtime-filter and selective-DML benchmarks. Existing `buildIrregularMasterDeleteByPk` is an example of PK-based independent index cleanup, not proof that the regular-index plan can be changed safely by a one-line join rewrite.

That route cannot be assumed universal. Old main ENUM or composite PK payloads may have been produced via display or hidden types without complete identity, so metadata type equality alone does not establish an injective physical PK mapping. A corrupted payload could associate a hidden row with the wrong base row; arbitrary stale keys cannot be repaired safely from display alone. Also, cleaning one affected row's UNIQUE entries cannot prove that all other base rows still satisfy a unique constraint when old hidden keys were collapsed or encoded incorrectly. A transparent UNIQUE fallback needs a separately validated authoritative base-table uniqueness check, compatible locking against concurrent INSERT/UPDATE/REPLACE and suitable isolation, or an atomic validated full rebuild/format marker; neither is established by this proposal. If required outside the supported pre-feature/feature boundary, fail the affected operation before effects and provide a tested explicit authoritative-source rebuild, preserving base rows and reporting errors. Do not silently return 0, drop an index, or call an operator-only warning a runtime safeguard. Rebuilding an inconsistent unique domain must report duplicates without publishing an invalid replacement.

## Required tests before design acceptance and final delivery

1. Produce real 4.2.8 and exact 42/main target-baseline fixtures with inline and ADD SET/legacy ENUM indexes, rows inserted before/after ADD, restart and stopped upgrade. On one table combine those old indices with a newly added nonzero ENUM and newly built nonzero ENUM+SET index. Check old/new hidden bytes and exact `ROW_COUNT`, remaining rows, UPDATE old/new values, physical 0/empty member/NULL and cleanup. Compare each legacy-only index to that branch's prior behavior; prove valid new-identity indices match their writer.
2. Exercise single/compound ordinary and UNIQUE indexes, PK suffixes and composite PKs where supported, repeated values, binary A/a and CI controls, SET 0/1/2/3/NULL, ENUM 0/valid-empty/1/2/NULL, numeric-looking members, post-update and delete/reinsert. Include a user RHS copied from another source/domain, plus changed and unchanged special columns. Ensure all matched index keys are deleted once and neither orphan nor duplicate base mutations remain.
3. Exercise DELETE/UPDATE predicate, explicit string/numeric casts, ORDER BY/LIMIT, JOIN/UPDATE FROM duplicate source rows, supported multi-target behavior, RETURNING labels and numeric results, generated columns, default/ON UPDATE and cancellation. Verify public SELECT/subqueries never inherit raw binding, target old-image source IDs and aliases are proved, and distinct/sort/projection pruning keep the hidden raw tail without changing row choice.
4. Verify index-format classification and target schema consistency under inline CREATE, ADD/CREATE INDEX, ENUM/non-ENUM MODIFY/CHANGE, PK identity conversion, drop/add mixed ALTER, failed duplicates, restart, snapshot, LIKE/clone and backup replay. Check catalog and bytes before/after failure, partial publication, tenant/temp table and remote plan. For pre-release nonzero mixed catalogs, exercise the chosen fail-closed/rebuild policy rather than claiming automatic repair.
5. Test INSERT, REPLACE, ON DUPLICATE and foreign-key/cascade paths that delete or rewrite regular index keys (`bind_insert.go` and branch-specific DML planners); no new writer may use physical raw while an old-key deletion route still recomputes display, or vice versa. Prove uniqueness and its concurrent enforcement for new-identity UNIQUE indexes. Compare plans, affected rows, hidden entries and base data after rollback/retry; benchmark representative small/selective and bulk DML for the new classification.

This is a proposed tradeoff and algorithm, not implementation/release approval. The full SET-backfill design submitted at SHA `9240f959...` assumes a broader correction and must not be mixed with this narrower decision without revising and re-reviewing the versioned design.
