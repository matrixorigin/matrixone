# CDC target identity and interrupted admission — PR #28521 rev6

Status: proposed; exact-version approval required before protocol implementation. Date: 2026-09-25. This amends the approved [rev5 generation design](20260925-cdc-target-generation-reset.md). Rev5's no-new-column claim, automatic destructive reset/replay on source replacement, immediate deletion of every predecessor epoch before first acknowledgement, and schema-only target verification are superseded here. Other rev5 invariants remain where consistent with these explicit changes.

## Why rev5 needed another review

Reviewing individual comments and unit tests established source-generation fencing but did not test the independent *target* generation. A real embedded run dropped and recreated the target with the same columns after a source replacement: three source rows became one target row and schema verification accepted it. The type verifier also rejected real, valid `YEAR`, `FLOAT(5,2)`, and `DOUBLE(6,5)` metadata; its mock covered only simple types. The mode-2 collision guard re-read every watermark for every admitted table. Finally, a generation-zero first attempt could delete its only durable epoch before target acknowledgement, leaving recovery to guess. Several tests called old restart-classification helpers that production no longer calls. The common mistake was treating a local state bit or structural equality as a durable cross-system fact.

The acceptance unit is now the complete transition tuple: durable source generation, target identity, replay boundary, owner claim, and pending attempt. Every crash boundary must either retry from this tuple or stop with a specific recovery action. Real sink metadata and target rows, rather than helper return values, are the oracle. Validation must include a cost bound for every added catalog or target query.

## Product contract

1. Once a target generation is durably acknowledged, the CDC task must detect its replacement by an identically shaped table before publishing a new reader or writing another target transaction. The target's physical identity is persisted. If a MySQL sink cannot expose a trustworthy identity, including missing `PROCESS` privilege for `INFORMATION_SCHEMA.INNODB_TABLES`, the task pauses with a capability diagnostic. An external row edit remains unsupported. Ordinary watermark updates are already buffered for asynchronous batch persistence; per the approved product boundary, identity is checked before every new target transaction and on resume. An already buffered old-target timestamp may flush after external DDL; a stronger atomic exclusion guarantee would require redesigning the checkpoint hot path and is outside this revision. During the first CREATE-to-ACK window, there is no prior acknowledged target identity; an uncoordinated external DROP/CREATE in that window cannot be attributed and is outside this identity guarantee.
2. If the source changes while any task is awaiting its first target acknowledgement, the task pauses for explicit recovery. First ACK must therefore re-read the live source table ID under a source catalog guard held through the synchronous watermark ACK commit; a stale detector result is insufficient. A NoFull or explicit StartTs target may contain prefilled data, so CDC must not erase it by inference. A same-generation retry uses its original boundary. As approved in the product decision, an already acknowledged source replacement requiring destructive target reset also pauses for explicit rebuild. Automatically clearing a large target row by row would preserve its ID but is an unbounded cost, while compare-then-DROP cannot exclude uncoordinated external DDL.
3. Existing tasks whose target identity was never persisted cannot be silently assigned the current identity. They pause and require an explicitly rebuilt or recreated task with a clean target. No automatic migration may claim that current schema or row count proves continuity.

## Durable state and ownership

Add two nullable fields to each `mo_cdc_watermark` row: `pending_source_table_id` and `target_identity`. `NULL` pending means no admission attempt; a positive pending value names the source generation selected before *any* target DDL. When `source_table_id>0`, `target_identity` is the acknowledged target ID. When `source_table_id=0` and pending is set, it records the pre-DDL target ID or an explicit `absent` sentinel; no other reuse of a target with a null identity is allowed. At acknowledgement, atomically replace that value with the post-DDL physical ID, and clear pending. The string includes sink kind and an unambiguous backend identifier. For MySQL 8 InnoDB, use `@@server_uuid` plus `INFORMATION_SCHEMA.INNODB_TABLES.TABLE_ID` for the exact escaped schema/table name. For MatrixOne, use the tenant target table's `mo_tables.rel_id` and pin the task to its configured target cluster; changing its endpoint/cluster requires a fresh task and clean target. Transparent rebinding of the same endpoint to a distinct MatrixOne cluster is outside this identity contract and must be prohibited operationally until a durable SQL-visible cluster ID is available. Reject missing, duplicate, zero, non-InnoDB, inaccessible, or otherwise ambiguous identities. `CREATE_TIME`, schema hash, target name, and a process-local cache are not identity proofs. [MySQL's InnoDB metadata documentation](https://dev.mysql.com/doc/refman/8.0/en/innodb-information-schema-system-tables.html) shows `TABLE_ID`; [its privilege documentation](https://dev.mysql.com/doc/refman/8.0/en/information-schema-introduction.html) documents `PROCESS` for `INNODB_` tables.

The cluster bootstrap DDL and a new versioned `ADD_COLUMN` upgrade must agree. The current upgrade head is 4.0.8 and protocol head is v96; add a new 4.0.9 upgrade and v97 writer barrier rather than editing completed 4.0.6 offsets. The upgrade uses explicit column lists and a protocol gate after all writer binaries understand the columns. Persist a new `generation-aware-v2` task option in existing task metadata on every new creation path, gated by v97 and the presence of both new catalog columns. The rev5 `generation-aware-v1` marker and minimum v58 cannot distinguish an old unacknowledged row `(source_table_id=0, pending=NULL, target_identity=NULL)` from a fresh v2 task. At executor startup, reject every task without v2 before reading or creating its per-table watermark, including old v1 tasks with acknowledged generations. Only v2 may transition `NULL→pending`; task option and catalog capability are checked both at creation and execution. Existing rows remain `NULL`, never guessed. Mixed old/new CN execution remains outside the approved rollout scope: pause tasks and drain old executors before changing the table and enabling the new contract. Downgrade requires pausing v2 tasks. Drop/orphan cleanup removes their pending state with the row.

## Admission and checkpoint sequence

The task owner claims its watermark row first. A first attempt observes the target's physical identity or absence and writes `(pending_source_table_id=g, target_identity=preDDLIdentity)` under its owner fence before storing a full-snapshot epoch or touching the target. The observation and pending write must be protected against a concurrent external DDL, or a second identity check before any effect must detect the race. For an existing prefilled **NoFull or explicit StartTs** target, verify structure and the recorded pre-DDL identity, skip CREATE, and synchronously ACK the same identity under the target guard. An initial full task with a preexisting target pauses: its snapshot cannot prove that unrelated target rows are absent. For an absent target, use `CREATE TABLE` without `IF NOT EXISTS`; an already-exists error must pause rather than adopt that table. In the **same live attempt**, only a definite successful CREATE permits reading its new physical ID. Hold the target metadata guard while comparing that ID. Before the synchronous ACK, begin a fresh pessimistic read-committed source transaction, acquire shared `mo_database.__mo_cpkey_col=serial(accountID, db)` and `mo_tables.__mo_cpkey_col=serial(accountID, db, table)` row locks, in that order and in the tenant lock group used by source DDL, advance to a fresh read-committed snapshot after locking, re-read the current source table ID by database/table name, require exactly `g`, and hold that transaction through the separate fenced catalog ACK commit. The existing callback snapshot and `InternalExecutor` one-shot query are insufficient for this guard; the implementation needs an explicit multi-operation transaction path. A disappeared or changed source pauses without ACK. Acknowledge `(g, boundary, newID, pending=NULL)` with owner, pending-`g`, and prestate-`absent` predicates. An uncertain CREATE result, process restart, or target disappearance before ACK pauses; `absent→present` on a later attempt never proves CDC created it. This is the sole prestate-identity transition permitted at first ACK. Only the ACK starts the strict post-acknowledgement identity guarantee. On **retry** with a preexisting target, if `pending=g` and its pre-DDL identity is still unchanged, reuse the original epoch and admission timestamp; if it changed, pause. If `pending!=g` while `source_table_id=0`, fail closed with a recovery diagnostic. Do not delete or replace that attempt's epoch. In NoFull and explicit StartTs modes the original durable admission timestamp is preserved, including on same-generation retry. The full snapshot's epoch is immutable until its final checkpoint.

For a previously acknowledged `source_table_id>0`, a later source generation first stops and drains the old reader. Verify the recorded target identity under a target metadata guard. Preserve rev5's finite-EndTs exception: if a historical read proves the new generation was absent at EndTs and the owner-claimed old-generation watermark had already reached EndTs, verify the old target and complete without a reset. If that proof is unavailable or old progress is behind EndTs, pause. In every other case where a later source generation needs a destructive target reset, persist a specific recovery diagnostic and pause **without** target DDL, epoch creation, or watermark advancement. This avoids the compare-then-DROP race: a target advisory lock excludes CDC workers only, and a metadata guard cannot span a DDL statement that implicitly commits. The operator can explicitly rebuild into a clean target and create a fresh task with the desired full/StartTs/NoFull boundary. For generation zero, pending `g` is written before epoch creation; if an initial full snapshot is needed, insert one immutable epoch and retain it until the final checkpoint. A changed pending source pauses before creating another epoch, so retry failures cannot accumulate generations. Resolve an uncertain acknowledgement by rereading `(source_table_id, watermark, target_identity, pending_source_table_id)` under the owner fence; only the exact committed tuple permits reader publication. A stale owner cannot acknowledge or checkpoint.

At initial acknowledgement, same-version takeover, finite EndTs completion, and every reader start, compare the live target identity with the acknowledged or pending value; the one exception is the same-attempt definite CREATE from persisted `absent` described above. Keep the target metadata guard through the one-time fenced initial acknowledgement; that API writes durable SQL synchronously. Before each target DML transaction, acquire a metadata guard inside that transaction, compare the live identity, write, then commit. For MySQL, `SELECT 1 FROM target LIMIT 0` in the transaction acquires a shared metadata lock; query `INFORMATION_SCHEMA.INNODB_TABLES.TABLE_ID` on the same connection before DML. The [MySQL manual](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-performance.html) documents that a transaction's table metadata lock blocks DDL until commit. For MatrixOne, add a narrowly scoped target-side guard operation callable as one SQL statement inside the existing remote `database/sql.Tx`: derive tenant ID from the authenticated session, acquire shared `mo_database.__mo_cpkey_col=serial(accountID, db)` then `mo_tables.__mo_cpkey_col=serial(accountID, db, table)` locks in that tenant lock group, advance to a fresh read-committed snapshot after locking, re-read and return exactly one `rel_id`, and retain both locks until that transaction commits or rolls back. It must reject autocommit, ambiguous or absent catalog rows, and non-pessimistic transactions. The CDC sink calls this operation before each target DML batch, compares the returned ID, then writes on the same connection and transaction; it cannot call frontend `lockop.LockRows` directly from its remote SQL client. Implement it as a target CN SQL operation backed by the existing catalog lock helper, without adding a second out-of-transaction connection or a client-supplied tenant ID. A single-CN, system-tenant `FOR UPDATE` probe blocked DROP, but that SQL form does not prove the tenant lock group: the planner defaults to group zero, while DDL uses `accountID`. Reuse the explicit grouped catalog-lock mechanism already used by clone, or establish and test an equivalent. The source and target guards must protect the same name-to-ID mapping used by DROP/CREATE and DROP DATABASE, including absent/recreated rows. Tenant>0 cross-CN DROP/CREATE/TRUNCATE/RENAME barriers must prove that the exact guards exclude relevant DDL. If either backend cannot prove the guard, fail its strict capability check rather than skipping identity verification. If the source guard cannot be held through the synchronous ACK, pause rather than weakening the pre-ACK source-generation rule. On mismatch, cancel the reader, stop the updater's buffered work for this task, persist a specific diagnostic, and require explicit rebuild; no later target write may begin. Cancellation or owner loss releases the target transaction before retry.

The existing `UpdateWatermarkOnly` merely buffers progress; its return is not a durable checkpoint. The updater may persist previously buffered old-target progress after an external DROP/CREATE, even if no new target write begins. This revision deliberately promises detection on resume and before the next target write, not atomic exclusion of external DDL against asynchronous batch persistence. The task cannot silently continue writing to the replacement target, but the operator may need to rebuild it from source history. A stronger “never persist old-target progress after replacement” invariant would require a per-key guarded synchronous flush or a batch protocol that holds every target's DDL guard across the catalog commit; neither is in the proposed minimal repair, and either needs measured cost and a separate exact design approval. The target guard adds one SQL round trip and two catalog locks per target transaction, not per row; benchmark throughput and lock wait before delivery. If its measured cost is excessive, return for a new design decision rather than silently dropping the guard. A completed finite-EndTs task has no later write and must be explicitly verified on any requested resume.

For pending generation zero, a target DDL that committed before the fenced acknowledgement is ambiguous on a later attempt and pauses if the identity differs from its persisted pre-DDL value. The single live, definitely successful CREATE transition from `absent` is the exception. External DROP/CREATE between CREATE success and the first ID read cannot be attributed; this pre-ACK window is outside the post-ACK identity guarantee and is called out for exact-version design approval. A prefilled NoFull/explicit StartTs target may be retried only when its recorded identity is unchanged; it is never automatically dropped. Recovery is an explicit full rebuild with changed semantics or a fresh task and clean target at a new admission boundary; record the selected action. An old row with acknowledged generation but `NULL target_identity` uses the same explicit recovery path.

## Verification and cost gate

The mode-2 name guard builds one folded-key index from the task's watermark rows per detector callback, not per table. Add each candidate key to that callback index before an insert whose outcome might be uncertain; conservative rejection of a later alias in the same callback is safe. A retry gets a fresh catalog snapshot. This changes catalog reads from O(tables × watermarks) to O(watermarks) per callback and bounds memory to task watermark keys.

Use fault barriers before and after pending write, epoch write, target DDL, identity read, source re-read and guard acquisition, atomic acknowledgement, data commit, identity check, and checkpoint; repeat under same-version CN takeover. Assert source and target rows plus the complete durable tuple after retry. Required cases include same-schema target DROP/CREATE by an external actor, non-InnoDB/missing `PROCESS`, target replacement during data flow and while idle, wrong target structure, old rows with `NULL` identity, NoFull prefilled target with source change before ACK, source DROP/CREATE between definite target CREATE and first ACK on another CN, three source generations with repeated failed admission and bounded epoch rows, finite EndTs, explicit StartTs, split/atomic full, owner loss, cancellation, and catalog uncertain writes. For type verification use real MatrixOne `YEAR` and scaled floating columns, plus different scale rejection. For mode 2 use a many-table callback asserting one watermark-key scan and collision rejection even after an uncertain insert. Reuse existing embedded fixtures. Run focused unit and integration tests, owning-package race tests, repository SCA/vet, and a real sink BVT; inspect logs rather than relying on CI. Record exact commands, revisions, row assertions, and any unavailable MySQL integration as unverified.

## Rejected shortcuts

Schema comparison alone admits same-schema replacement. `CREATE_TIME` can be cached or change without proving a unique incarnation. Recording an ID only in memory fails on CN takeover. Reading identity only at startup misses replacement during streaming. Automatically assigning an ID to old progress cannot prove what target received that progress. Repeatedly resetting a changed generation-zero NoFull target can erase prefilled rows. A separate per-row identity query without a lock interval leaves a DDL race and raises the hot-path cost without satisfying the contract.
