# Composite secondary-index key sets: design review for #32567 / #32410

Status: proposed design for independent design-first review, 2026-11-12. Original head `b75b3e96a6e09e1f0e58e395fbb535b270163b2e`, merge base `1bde992bb5c7ee443af6442ad32c5821f25fcacd`, rebase target `6785b4bc8c5a34841ee7d6f161d145af47c51659`; rebased feature head before repair `2f27b60a72f03524972814e9b73ebb9e6b3a44a9`. The independent review decision and exact reviewed revision are recorded in the implementation PR.

## Scope, evidence, and contracts

The whole feature materially expands non-covering composite secondary-index access, adds 917 production lines and removes 28, and changes a hot planning path and its resource footprint. It meets G-FEATURE-DESIGN on size and hot-path/capacity complexity, independently of its bug-fix label. The design must be accessible at a stable versioned revision, linked from the implementation PR, and approved in a distinct phase. R3 applies to planner resource/performance; R2 applies to SQL correctness and index/scan ownership; fixture output is R1/R0. No new user-facing SQL syntax, persisted catalog/index format, RPC/protobuf field, concurrency model, long-lived cache, or configuration is proposed.

Exact-old-head QA (comments 6817438366, 6821329368) established that #32410's 5,000-row query went from 5,000 input rows to 3, with the same SQL result; its 60k-row small-key prepared case was ~22x faster. Same-environment 1k-row ordered prepared execution with 128 IN values was 23–27% slower. Shuffled performance is explicitly inconclusive. The 128 × 65,535-byte synthetic unique-key list used ~50 MB/op and 3.5 ms at head versus ~9 KB/op and 4.4 µs at base, excluding upstream parsing costs; B/op is cumulative allocations, not peak memory. CI run 43160846294 passed; it is not evidence of a CI failure. These figures are observations, not a general cost law.

Invariant: optional index access may prune only rows excluded by the original SQL predicate, and must retain original base-table residuals. Unique full keys use production `serial` encoding with exact, sorted, compacted IN; nonunique keys use `serial_full`/`prefix_in` because of the PK suffix. NULL/multiple-IN/unsupported/truncated-prefix cases must use a safe ordinary path. A selected access is published only after its filter is built, validated, and admitted. Failure/decline must leave the original scan, its stats, filters, limit and offset intact, then try other eligible candidates or the pre-existing equality/non-equality/scan path. Prepared values must not be captured before their execution binding. Index hint filtering remains authoritative.

Change map: `apply_indices.go` implements scan routing, candidate comparison, hint filtering, scan preparation/publication, residual pushdown and the associated prefix-metadata guards. `index_keyset.go` owns classification, cardinality/ranking support, production-serializer use, tuple allocation, and exact/prefix lowering. Seven `index_keyset_*_test.go` files cover bounded counts, encoding, fallback, cost/ranking and benchmarks. `index_hint.sql/.result` cover public SQL/hints/residual/parameter/prefix/nonunique behavior, while `unique_keyset_large.sql/.result` covers a real-statistics 60k competitor/NULL/exact-key oracle. The prefix-index guards are a correctness dependency: a newly declined key set can otherwise fall back to an unsafe full-value probe of a truncated key. They should not be detached without proving the replacement fallback safe. Target-base changes in runtime filters make blanket reuse of old BVT/race results unsafe until dependency equivalence is shown.

## Recommended admission and budget

1. **Automatic non-covering multi-point break-even.** Apply the same helper to each candidate during `getMostSelectiveIndexForPointSelectWithKeySets`, before it can displace another key set or equality candidate, and to each candidate in the broad-scan `applyBoundedUniqueKeySet` route, before preparation/publication. Leave covering scans, ordinary equality, primary-key ordering, non-key-set range/scan choices and their existing stats guards unchanged. For a candidate with more than one raw IN element, cost `rawCount` index probes conservatively; admit only when `rawCount <= 0.1 * scanCost` and the existing applicable cardinality/scan or exact-unique guards also pass. This deliberately does not rely on a selectivity estimate to claim that a nonunique prefix produces at most one row per key; a nonunique lookup can fan out. The 0.1 factor is established planner precedent: `applyIndicesForJoins` rejects an automatic index join whose build rows exceed `leftChild.Stats.Cost * 0.1`. `calcScanStats` sets scan Cost to table count times estimated block selectivity. Thus cost 1,000/128 probes rejects, and cost 60,000/128 passes. This is a cost heuristic, not a universal guarantee; it also preserves sorted-scan preference.

   Use finite positive non-default scan Cost when available. For nil/default/nonfinite/nonpositive stats, do not claim to know the table size; use `DefaultStats().Cost` (currently 1,000) only as a conservative fallback policy, yielding 100 raw points. This keeps the important 3-point unknown-stats case eligible and rejects the measured 128-point small-table regression. Existing unknown/default routing must otherwise remain unchanged. Stale but numerically valid statistics cannot be detected reliably here; decisions remain estimates, and FORCE is the escape hatch. Raw count intentionally overestimates duplicate probes: that is conservative, avoids expensive dedup just to reject, and must not alter SQL correctness. If a rejected key-set candidate has a valid equality prefix, evaluate it as an equality candidate; rejection of one index must not mask a cheaper different index. Retain stable tie behavior. `FORCE INDEX` bypasses this performance gate just as it bypasses existing scan costing, and must still respect hint restrictions and all safety constraints.

2. **Pre-materialization work budget.** Introduce a separate, named candidate-encoded-work budget of 1 MiB per scan rewrite invocation (including all attempted key-set materializations); the choice is an explicit conservative resource policy, not a measured break-even or a heap/peak bound. The observed 8 MiB raw input and 50 MB cumulative allocation violate it by a wide margin; ordinary 128 small fixed-width keys fit. Keep the existing 128-point and 80 MiB raw-wire guards as independent safety checks. Charge failed attempts too, use overflow-safe subtraction/multiplication, and continue to a smaller remaining candidate instead of letting a failed or over-budget candidate hide it. Do not allocate/copy the encoded keys or publish a node to perform this check. A cheap `len(IN literal Data)` rejection should run before vector unmarshaling/hashing; still validate accepted vector bytes with `UnmarshalBinary` and apply checked type/NULL/count validation.

   For each candidate, bound un-compacted tuple work as the sum of the IN component's encoded bounds over every logical row, plus `N` times the bounds for each equality operand, plus conservative per-row vector/plan-envelope overhead. Count duplicates and repeated equality values because these are processed before compaction. For each preparation, conservatively charge at least three times the single-pass tuple bound: the first-tuple fold, a partial or complete fast encoding, and the possible full folding fallback may all run in one attempt. This budget constrains accounted encoded work, not all CPU, parser work, or heap allocation. Use `function.SerialEncodedValueSizeBound` for actual decoded IN values, including embedded NUL escaping; obtain a proven operand bound from the actual safe literal (including its actual string bytes) or `compositePointValueSize` / `SerialEncodedTypeSizeBound` where the expression's runtime representation is established. Never assume the base-column width bounds the runtime equality expression. For dynamic operands, use a static type bound only if the producing expression is proved to enforce that bound: `compositePointScalar` already identifies a narrow text-to-CHAR/VARCHAR cast and rejects unconstrained raw parameters. `ParamExpressionExecutor` accepts parameter bytes directly, so raw `Expr_P.Typ.Width` is not a proven bound. A literal with `Src` can refer to a parameter or volatile source: bound the proven source expression, never its current literal bytes as a future-execution bound. A size bound alone does not prove it is safe to capture a dynamic or volatile source in a prepared key vector: unless the source is independently proven stable for that plan lifetime, decline this lowering. NULL or an unbounded/unknown source declines optional lowering without speculative evaluation. A previously bound literal with no source is charged at its actual bytes. Note that the current `foldKeySetTuple` calls constant folding with `varAndParamIsConst=false`, and `TestIndexKeySetFailedLoweringDoesNotPublishScan` confirms an unbound parameter already declines; a size check does not create runtime-param key-set support. Prove the application-shaped 3-point prepared behavior against the pre-repair head. If the head obtains a key-set after binding, preserve that path; if the head itself falls back, record the existing performance limitation instead of silently claiming a prepared speedup. A constant vector must be charged for every logical row, not merely its one physical payload. Bound calculations themselves must stop early and be shared per IN filter when possible. One ledger must span ranked and exhaustive fallback so fallback cannot reset the budget or multiply full-key work without limit. This constrains encoded work attributable to this rewrite, not SQL parser input, baseline fallback costs, whole-query memory, other scan nodes, nor actual peak allocation.

   Apply the structural budget regardless of FORCE; FORCE overrides cost, not eligibility/resource safety, as with existing 128/80 MiB bounds. The existing implementation (`filterRegularIndexesByScanHints`) limits eligible named indexes, while `TestCompositeIndexKeySetFallbacks` permits fallback for FORCE with 129 points or NULL and `TestCompositeIndexKeySetPrefixFallback` expressly expects no index scan when the forced leading component is truncated. Thus the established behavior is a restriction on which indexes can be chosen, not a guarantee that an unsafe or unsupported key-set probe is selected. On budget decline retain the filtered hint set and the ordinary safe fallback; a forced unique composite index with no eligible equality-only or other legal path may fall back to a base scan. Budgeted small FORCE cases without an incompatible ORDER/GROUP requirement must still use the named index; explicitly exercise over-budget FORCE, compare SQL results, and prove no disallowed alternate index is selected. The rebased 2f27 head already gives a base scan for unscoped FORCE `uq_ab` plus `ORDER BY payload`: the unscoped hint also applies to ORDER, the ordered index cannot satisfy payload ordering, and the force-order pass protects the base scan before ordinary index rewriting. Do not use that query as an assertion that the cost gate ignored FORCE; test the gate without that conflicting ordering as well. Do not add an unproved full-index backfill, especially when unique indexes omit NULL keys.

3. **Keep proven mechanisms; remove duplication only when justified.** Earlier 8-candidate exhaustive lowering consumed ~632 MiB/op, versus one full materialization by ranked selection; retaining cheap ranking prevents a concrete amplification. Keep ranked and exhaustive if necessary for unproved inputs, with one shared admission/scoring policy and one shared work ledger; never require numeric equality of estimate and actual without the existing exhaustive correctness fallback. A wholesale exhaustive-only simplification can reintroduce the verified amplification. The fast serializer delegates to `NewSerialValueEncoder`, verifies first-tuple equivalence and falls back to authoritative folding, with tested scratch ownership/error cleanup. Older QA showed ~79 MB/5.67 ms before that change and ~50 MB/3.51 ms after, but for wide inputs the new cap would decline both; this is evidence of a wide-workload improvement, not proof that the fast path helps admitted narrow workloads. Keep it for this repair unless same-mode benchmarks of admitted representative 8/128-point inputs justify removing it without losing the real execution benefit. Do not duplicate the production encoding format. Factor duplicated policy, not different fallback semantics, if the change remains small and tests prove candidate/tie/failure equivalence.

Alternatives: status quo preserves access but retains measured regressions; a blanket 128-point limit alone permits the wide allocation; lowering the point count alone loses profitable 60k/128 access; unconditional 30% selectivity admits 128/1,000; a full new optimizer cost model or second serializer is disproportionate to the evidence. The scoped 10% rule plus a separate encoded-work policy addresses different costs with correctness-preserving fallback.

## Verification and acceptance

- Focused deterministic planner tests: 3/1,000, 100/1,000 and 101/1,000 at the 10% boundary; 128/1,000 rejection and 128/60,000 admission; a very cheap sorted scan; unknown/default, nil and nonfinite/zero cost; valid but stale estimates acknowledged as unknowable; equality/singleton unchanged; FORCE bypass; competing candidates where an initially preferred set is too expensive but a smaller set or equality remains; unique and nonunique; two simultaneous IN dimensions, NULL, duplicates, casts, unsupported types and prefix-length/malformed metadata; failure before publish with stats, residual, limit/offset unchanged. Assert plan plus SQL behavior where each is necessary, not helper call counts alone.
- Budget tests: below/equal/above limit and overflow; over-budget IN data, narrow IN with a wide repeated equality component, many equality components, duplicates/constant vectors, escaped NUL/UTF-8, vector wire validation failures, distinct candidate ordering, failed candidate followed by affordable candidate and ranked-to-exhaustive cumulative accounting. Verify no partially published nodes or retained pool memory. Test actual production `serial`/`serial_full` equivalence and encoded ownership with the existing byte-oracle suite; do not hard-code observed timing into unit tests.
- Public SQL/BVT: original 5k fixture must still yield 3 input/3 result under normal stats policy; equality and IGNORE INDEX results agree; separately compare pre-repair and repaired plans and real results for the application-shaped 3-key prepared query with both leading values as `?`, repeated with changed values and NULL; preserve any pre-repair bound-parameter key-set benefit and explicitly record an existing raw-parameter fallback if observed. A non-covering small 128 ordered prepared query selects the intended fallback; same forced query honors named-index semantics; the 60k 128-small-key case remains key-set and gives the same result; include multiple candidates, residuals, DML, NULL, repeated prepared parameter values including NULL, and legacy/truncated prefix fallback. If default stats prevent the original fixture, fix the policy rather than weaken the oracle.
- Re-run one controlled same-environment AB/BA performance comparison for 1k ordered prepared, 60k prepared and ad-hoc 128 small keys; record plans, scan costs, result equality, sample counts, medians and variance. Expect removal of the systematic small ordered regression and retention of large benefit, not a promise of a fixed percentage. Benchmark wide 128 × 65,535 unique/nonunique with one/eight candidates and a wide equality literal; record ns/op and B/op, no parsing included, against old head and new; show early fallback rather than claiming any absolute peak memory bound. Include forced-wide semantics and cost. If resource conditions prevent a controlled SQL comparison, mark it pending rather than declaring regression fixed.
- Run the focused tests, changed owning package and relevant incremental static checks using the prescribed CGo wrapper; prove nonempty selection. Run public optimizer BVT and targeted race for independent builders/reset/prepared reuse because a hot planner path and scratch ownership are affected. Exact-old-head CI is useful history but changed code/test/runtime-filter input is not a valid exact-head pass for the repair; rerun affected evidence. Do not start duplicate builds/services.

## Compatibility and decision

All lowered expressions use pre-existing plan operators and production persistent-key encoders. No storage migration or version-specific catalog read/write is introduced; restart, backup/restore and rollbacks carry no new persisted state. Mixed-version execution is limited to the existing plan/operator compatibility contract and must be verified if a changed target dependency introduces a new operator requirement. Plans and performance can change for stale/missing stats or wide keys; SQL results and hint restrictions must not. No new externally configurable switch or monitoring is needed for a planner-local heuristic; existing EXPLAIN and per-operator rows provide diagnosis. Reverting the change restores prior scan choices. No new trust boundary, privilege, or tenant state is introduced; per-scan work admission limits one optimization's amplification but is not a general denial-of-service defense.

The review decision is recorded against an immutable revision in the implementation PR. The 1 MiB threshold is an explicit conservative policy, not a measured optimum; the stated tests and performance comparison determine whether it needs revisiting.
