# Main design: bound CN spill runs before object serialization

Issue: [#32146](https://github.com/matrixorigin/matrixone/issues/32146). This is the `main` follow-up to the `4.2-dev` fix [#32155](https://github.com/matrixorigin/matrixone/pull/32155). The original evidence used `main` commit `36c99836498293e5ada615a017908832e99072af`; this revision integrates PR [#32188](https://github.com/matrixorigin/matrixone/pull/32188) with `main` at `9e67b078e14482137797010719b3a9bb59d3a71b`. Results measured before this rebase are historical where the affected dependencies changed.

## Classification, evidence and decision

Treat the complete change as a **major lifecycle/ownership change** for the mo-dev design gate, even if the final diff is small. Multiple spills change the timing and number of persistent files across the sinker, async workers, CN writer and transaction publication boundary, and change the capacity and CPU costs of a hot path. This is a concrete crossing of ownership boundaries and change in failure blast radius; line count is not a waiver. Material deviations require the affected design decisions to be reviewed again.

At the main base, a real writer and readback over an in-memory FileService show the following behavior. At 128 MiB, two 96 MiB values yield one decoded 201,326,648-byte block and mpool peak 403,111,936 bytes, with either chunk-policy setting. Object metadata verifies actual stored column algorithm 1, legacy LZ4, in both cases. At the same base, two 800-byte values form one 1,656-byte decoded block at a 1 KiB threshold in sorted/unsorted × sync/pipeline. Main's current result does **not** establish the old-build 2 GiB failure, or that one query caused OOM. The memory FS, compressible inputs and one process per run limit peak/RSS inference. Earlier 4.2 results motivate the choice but are not evidence that main passes.

**Selected contract.** For ordinary CN data and tombstone writers without `allMergeSorted`/`dedupAll`, and for data writers only when `flushOnSync=false`, a run/object's conservative materialized payload charge is at most its positive configured threshold, except that one indivisible row whose own compact charge exceeds the threshold is alone in an immediately spilled object. A threshold of zero is interpreted after existing defaults; `flushOnSync`, `allMergeSorted`, `dedupAll` and unrelated general sinker clients keep their existing behavior. Per object, all blocks except the last have 8192 rows. Every accepted row occurs once with its original value and nulls; existing transient metadata is preserved through the FileSinker input boundary, while persisted metadata follows the existing object format; each sorted object is sorted, and synchronous unsorted order remains input order. Async object completion order is not promised. This is a logical byte budget for staged and subsequently materialized row data, not a hard cap on encoded bytes, allocated capacity, total pipeline backlog, input memory, RSS, or an individual oversized row.

## Integration with workspace cleanup ownership

On current `main`, workspace spill reserves capacity per object before
persistence and transfers unpublished objects to the transaction's existing
asynchronous cleanup owner. That owner and the bounded-run cleanup in this
change must not both delete the same object. A transaction-bound sinker uses
an explicit workspace-owned cleanup option together with its capacity hook;
the option follows the current workspace when a retained writer is rebound or
cleared. An unbound sinker keeps the local cleanup and retry behavior described
below.

After a bounded write or sync fails, both modes select the operation error,
cancel and drain sibling writes, release staged memory, and prevent reuse of
the failed generation. A workspace-owned sinker retains the names of all
persisted or commit-ambiguous objects without deleting them. An owning caller snapshots and hands those names to the transaction owner before close;
the sinker must not call back into that owner while the transaction lock may be
held. Cleanup and reservation accounting then follow the existing workspace
publication, rollback and asynchronous cleanup paths. A successful sync only
hands results to its caller: it does not prove that downstream metadata was
recorded.

Workspace dumps resolve their source tables before staging and retain each raw
entry, key index and accounting until all replacement stats for that table are
recorded. Cancellation after table resolution or during persistence leaves the
unrecorded source unchanged; every persisted or ambiguous replacement name is
retained and converted from its reservation to the transaction cleanup owner.
Cancellation or failure after a successful record cannot undo that record: the
caller reports the table as published and retires its source once, even when
close subsequently fails. Other tables retain their source until recorded.
Record every returned object stat, not just the first object name.

The sinker policy is explicit, not inferred from the presence of an arbitrary
capacity callback. The transaction's existing `SinkerCapacityOption` installs
both per-object admission and workspace-owned cleanup on its writer; clearing or
rebinding a cached writer updates both for the current workspace. The owner
receives names through existing transaction-lock-held retention on internal dump
and compaction paths, and through existing deferred recording/epoch-aware
retainers on operators where metadata may still be recorded later. The clone
materializer binds the destination transaction: its reservation map owns each
name before persistence, successful record converts the reservation, and a
failed statement or terminal drain retains and hands off unresolved names.
Remote names follow the existing fragment-to-workspace transfer. No new format, service protocol,
background worker, or second persistent registry is introduced.

For transaction-bound writers, a failed generation is drained and its snapshot
is taken before close. Persistent multi-update writers with pending objects are
retired after the handoff and rebuilt; a clean writer can be reset and reused.
A synchronous delete under the transaction lock would block admission and
rollback on storage, while retaining and independently deleting the same name
would create two cleanup owners; neither alternative is valid. For an unbound
writer only, the original local retry and explicit terminal-drop limitation
remain. A selected worker or operation error retains precedence over subsequent
cancellation or cleanup failure; successful result handoff is not retroactively
invalidated by late cancellation. None of these paths promises an I/O deadline
when a worker or FileService does not cooperate with cancellation.

Validation must cover cancellation after resolve, during write and around record;
real write/sync/close and metadata failures; a deletion that blocks despite
cancellation while the transaction lock is held; multi-object reservation and
retention; a later recording epoch and duplicate-cleanup exclusion; successful
and failed Reset/rebind; destination-clone and remote consumers; independent
unbound retry; and public SQL readback plus rollback. Use deterministic barriers
and prove source entries, exact names, capacity ownership and durable SQL
results. Re-run affected tests and representative performance controls against
the rebased base; the pre-rebase timings do not prove post-rebase performance.

## Source flow and the reason for admission

`multi_update` projects input into a `CNS3Writer` (or owns a clone via `WriteOwned`); `insert` and disttae also construct the same data writer. `s3util.go:newCNS3DataWriter` supplies the threshold, tail cap 0 and off-heap option; `newCNS3TombstoneWriter` uses the same sinker with a rowid sort key and potentially variable-length primary-key column, but does not set off-heap. The merged 4.2 design and tests explicitly apply this same run budget to tombstones. Enable it on both main constructors without changing their allocation modes. `Sinker.Write` currently copies through `Batch.UnionWindow` into 8192-row buffers, stages them and only then checks physical `Batch.Size()`. `WriteOwned` may stage one full unique-owned batch. For each spill `trySortInMemoryStaged` sorts input batches; `MergeSortBatches` either heap-merges via `UnionOne` or, if key ranges are disjoint, concatenates via `UnionWindow`. Both fill 8192 rows before the callback. The unsorted path writes staged buffers directly. Pipeline jobs own their transferred batches and produce separate objects, with sorted jobs grouped at 128 MiB. Thus a byte boundary solely in either merge branch misses unsorted input and a partial-block callback within a still-open object breaks readers.

`syncFileSinker` accumulates stats, then successful `Sync` moves them to `result.persisted`. `ExpandObjectStatsToBatch` iterates *all* objects, and `objectio.StatsBlkIter` without block metadata assumes every block except the last is full. `disttae/txn.go:writeFileLockedWithAutoIncrEpochKnown` registers every object in the stats vector; its separate `fileName=stats[0]` is a non-empty entry marker, while `GCObjsByIdxRange` iterates the stats vector. `table_meta_reader.go:readWriteHelper` likewise counts every stat. Tombstone expansion emits one stats row per object; `multi_update` uses the first object ID as a delete routing name while passing the complete stats batch. Test data and tombstone consumers with >1 object, including that routing boundary: do not rely on the first-name observation alone. No storage or wire-format change is needed. Partial runs end an object, so all existing readers retain their block-row contract.

The live chunk policy in `s3util.go` requires a service runtime and MO protocol >=29. In `objectio/writer.go:addBlock`, the whole vector is prepared and serialized to `sbuf` **before** the chunk policy/encoder decision. The encoder declines nondisjoint varlena and an unchunkable single row; in the reproduced sorted path, `ShuffleWithBuf` clears the disjoint proof and the persisted algorithm really is LZ4. Chunking can also allocate per-window data after the full buffer exists. It is not an admission bound. Preserve the live gate and format semantics; verify both a true chunked case and a real fallback rather than equating policy=true with actual encoding.

## Charge and admission algorithm

The first owner is `Sinker`; bound a complete staged run, not just a merge output. A conservative charge is the sum across columns of logical fixed-width slots (including each 24-byte varlena descriptor) and, for each varlen column, an upper bound on **both** retained area and live non-inline payload after materialization. Full-source/owned input needs the per-column maximum of physical area and the sum of live non-inline lengths, not `max` applied only once to the whole batch: dead area can be in a different column from aliased payload. Each constant is charged per logical row and each repeated/aliased descriptor for every logical materialization. Null and inline values have no external live payload; null/grouping/provenance/string-domain metadata, object headers and capacity are explicitly outside the logical charge. Respect `Vector.Size()` on main: it includes some sidecars and is approximate; it does not prove this bound and must not replace a carried charge. Test transient metadata correctness at the FileSinker input boundary even though it is outside the charge; persisted object readback checks only metadata actually encoded by the existing format. Use checked multiplication/addition and saturating comparisons where only `>budget` matters; never wrap. If an actual required size cannot be represented return a normal error.

For a whole source the cheap proof `VarlenaAreaIsDisjoint()` bounds live payload by its area without scanning. Non-disjoint and constant vectors need live payload calculation. Borrowed backing can keep an entire parent area, and a full disjoint owned source can retain dead bytes: either charge bytes actually copied or compact the selected rows. Main's `unionBatchContiguousVarlenRange` may copy a full owned, disjoint source area, dead bytes included; a proper partial window scans live spans and the general path materializes live rows. A multirow full-window selection whose live charge fits but full physical area does not must be copied as non-whole windows, while a singleton uses `UnionOne`; do not call a small live row oversized merely because dead area was retained. Confirm this against actual source/backing behavior in tests, including borrowed windows and null slots carrying stale descriptors.

Maintain per-staged-batch bounds and the current partial buffer's bound, aligned with existing pop/push/put-back ownership; run total is their checked sum. A whole-input fast bound can admit a whole fitting input without a per-row scan, preserving append-built disjoint and fixed-width fast paths. For an aliasing varlen vector, the physical area length times the logical row count is also a conservative upper bound on total live payload, since no valid row can reference more bytes than the area contains; use this cheap bound only to prove that the whole source fits the remaining budget, otherwise fall back to exact live-payload measurement. Do not carry this loose proof as the run charge: after copying, account for the destination’s per-column change in logical slot bytes and actual area length, plus the logical expansion of any constant payload. A regular non-disjoint UnionWindow copies live non-inline payload into the destination, or copies a non-overlapping contiguous range; a constant can broadcast one descriptor and therefore needs its separately computed expansion. This retains a conservative bound across partial refills without repeatedly charging dead or unreferenced source area. Validate this claim with near-all-null, inline and mixed-column alias counterexamples, multiple Writes and object counts. Exact-base ABBA showed a 20–23% CPU regression for aliased inputs from the extra full descriptor scan, and a CPU profile attributed 16.7% cumulative time to materialized-size calculation, so this arithmetic proof avoids a demonstrated repeated scan without changing vector preflight or publishing state early. Otherwise find the largest next prefix that fits *the carried conservative charge*, before copying; equality fits. Precompute fixed-width cost; scan live varlena only when needed. If no row fits a nonempty run, push a nonempty current partial, spill explicitly even when its charge is below threshold, and retry the same source offset. If no row fits an empty run, compact-copy exactly one row, stage and spill immediately. Advance or spill a nonempty run on every iteration; never merge or persist an empty batch. Once a push itself spills, do not spill the now-empty run twice. Preserve carried bounds across partial-buffer refill, staging, sorting and sync. Release current, pending and staged buffers exactly once on every returned error.

`WriteOwned` retains its current contract: reject borrowed/nonunique vector backing as main currently does; do not silently transfer it. Direct transfer only for an exactly full block with no prior partial, a conservative bound that fits the remaining run budget, and a representation safe for sorting/merging; constants in sorted inputs may use the copying/materializing fallback. Because direct transfer has no post-copy size delta, non-disjoint owned vectors must retain exact live-payload accounting (or use the copy path); the loose admission-only proof must never become their carried charge. Otherwise invoke the same copying admission path. `owned=true` means transfer took place even when a subsequent spill returns an error, and the caller must drop its reference first. A panic before returning `owned` has a pre-existing ambiguous caller/sinker ownership window: avoid introducing new expected panics and do not claim it is closed absent a deterministic fix and test. `Write` source remains caller-owned.

**No 4.2 hint port by default.** Main's `PreExtendSelectedBatch` both mutates/reserves destination capacity and stores a one-shot proof for the exact flags and `UnionBatchPreflighted`; it rejects destination/source aliasing and covers sidecar/provenance admission. It is not a read-only prefix size oracle and cannot be invoked speculatively without changing allocations and publication behavior. Existing `UnionWindow` already uses `UnionBatch`'s contiguous/disjoint fast path and performs its own pre-growth. Use those existing APIs first, without new vector/batch payload-hint APIs, metadata caches or compatibility wrappers. Main's selection preflight does not by itself eliminate a duplicate sizing scan for non-disjoint input; if representative exact-base profiling shows material overhead, design one minimal reuse at the existing vector preflight boundary, preserving allocation-account selection, COW, sidecars and no-publication-before-success, then re-review that change. Do not import 4.2-wide hint APIs merely on precedent.

## Ownership, cancellation, failure and reuse

An eligible run is sinker-owned until successful `Sync`, including objects from successful earlier spills during the same run generation. `pushStaged` takes a batch even if spilling returns an error. Pipeline `Submit` owns/frees job data even on enqueue failure; workers own transferred batches and their file sinkers. On sort/fetch/copy/sink/sync/submit failure, cancel the current pipeline and drain **all** siblings before taking a final cleanup snapshot; a sibling can persist after the first error. `trySpill` currently installs its staged cleanup defer only *after* sorting, so this closure must also cover sort failure. Release current and staged buffers exactly once; do not recycle anything still owned by a worker. Preserve the caller's `WriteOwned` ownership bit on errors.

Reuse main's existing `DeletePersisted` snapshot/deletion implementation, with a private selection that excludes handed-off results; its public inclusive contract remains unchanged for checkpoint and other clients. Add the following narrow operations, forwarded by `CNS3Writer` to its sinker:

- `PendingUnpublishedRuns() []string` returns a copied, normalized read-only snapshot of the current generation's known `staged.persisted`, `staged.unpublished`, and `pipe.result.persisted/unpublished`, never `result.persisted`. It is safe against worker updates, but is complete only after drain. It performs no deletion or ownership handoff.
- `RetryUnpublishedRuns(ctx) (names []string, err error)` is a local-delete API: for an unbound writer it cancels the generation, drains workers, snapshots the same pre-handoff names, and calls the shared deletion primitive with the **supplied context**. It rejects a workspace-owned writer rather than deleting or reporting a transfer that did not happen. It returns the exact post-drain snapshot on success and failure, and retains references if deletion fails. A batch delete can return `ErrFileNotFound` before touching later names. The shared deletion helper therefore retries each member of a multi-name batch individually on that response; a single missing name is success, and any other error retains the full snapshot. All attempts for one batch share its existing deadline. This exceptional path can issue up to 1000 additional calls; it changes no object format. The public helper preserves its existing behavior of passing canceled contexts to storage, including the engine's detached shutdown attempt. Bounded-run retry instead checks cancellation before each batch and each single-name fallback, without promising a deadline if an in-flight file-service operation ignores it. It has no authority over previously handed-off results. The method is also the explicit retry API; it does not start a new generation.

For an unbound sinker, an eligible `Write`/`WriteOwned`/`Sync` error attempts the same staged-only cleanup with its original operation context, bounded as below. A workspace-owned sinker cancels and drains but preserves the snapshot for its transaction owner without synchronous deletion. Return the original operation error unchanged, including its direct `*moerr.Error` type and `context.Cause`; **do not use `errors.Join(primary, cleanupErr)`**, because `moerr.IsMoErrCode` and `ConvertGoError` require a direct `*moerr.Error`. On cleanup failure retain the names and report the cleanup error and exact snapshot in structured diagnostics, separately from the operation error; the explicit retry/snapshot APIs expose them while the writer remains live. A cleanup error may be returned by a terminal error-returning scope only if there is no primary operation error. No existing callback, mutable error detail or logging claim is treated as a durable owner.

After an operation failure, subsequent Write/Sync is rejected until cleanup succeeds, or a workspace owner accepts the snapshot, and `Reset` starts a fresh generation. `Reset` has its existing void signature and does no implicit network I/O: it cancels/drains and releases generation buffers; if pending deletion remains, it preserves the staged/pipeline name references and the failed-generation gate. After `RetryUnpublishedRuns` succeeds, a subsequent `Reset` clears that gate, discards the drained pipeline context and permits reuse. Repeated retry and Reset are idempotent. `Close` keeps its existing context-free signature, cancels/drains and releases batches, pools, arenas and output batches **even when deletion failed**; it performs no unbounded implicit deletion. A caller needing retry must take the snapshot before `Close`, and, if retaining the writer, retry before closing it. Closing/dropping the final writer without successful cleanup or an actual handoff loses its in-memory retry owner. Report the exact remaining names and error before a terminal drop; logging is diagnostics only. A final storage failure, expired deadline or dropped snapshot may leave orphaned objects, exactly as in the accepted #32155 limit; there is no promised durable retry, worker or registry. Noneligible general sinker clients retain existing behavior.

**Concrete CN owners and teardown policy.** An unbound owner invokes `RetryUnpublishedRuns` before Reset/Close when abandoning a generation, including abandonment caused by an upstream error before its own Write/Sync failed. A workspace-bound owner instead transfers its snapshot to the existing transaction cleanup owner before Reset/Close and does not retry deletion on this path. For unbound writers, a synchronous teardown helper takes the actual operation context, creates the separately bounded finalizer context described below, calls Retry, captures its names/error, and always calls Close when retiring the writer. Workspace-bound Close/Reset must not call this delete helper; the owning caller transfers names first and may then close and rebuild an aborted writer. Error-returning local scopes return their primary error unchanged and separately log cleanup failure with names; absent a primary error they return the cleanup error. This applies to `multi_update/s3writer_delegate.go:sortAndSyncOneTable`, `deletion/types.go:container.flush` (including the local writer at line 258; use per-partition lifetime rather than accumulating loop defers), `disttae/txn.go` dump insert/delete writers, `txn_table.go:rewriteObjectByDeletion`, and both `table_meta_reader.go` local writers. Carry each function's actual operation context into Write/Sync and its finalizer; do not silently widen a tighter caller deadline.

`insert/types.go` Reset/Free are void: retain every bound ordinary and partition writer's names in the workspace before closing; finalize unbound writers synchronously and report exact names on failure; they cannot return cleanup errors through the operator terminal API. For retained unbound multi-update sinkers, `s3WriterDelegate.reset` runs the retry **before reuse**: on success it calls Reset and keeps that writer; on failure it records the names/error, closes and retires that writer. `ensureInsertSinkers` must initialize each missing table writer so the next execution gets a fresh generation rather than a permanently poisoned writer. `MultiUpdate.Reset` ignores `writer.reset(proc)` today, so the reporting/retirement happens inside that owner, not through an assumed return. `s3WriterDelegate.free` and `PartitionMultiUpdate.freePartitionWriters` likewise report before terminal drop; those void call paths cannot propagate an error. If a retired writer's deletion failed, the reported snapshot can be retried by a caller holding the FileService via the existing `DeleteUnpublishedObjects`, but no production persistent handoff is implied. A retry after retirement is not automatic. This bounded terminal-drop limitation is accepted; it is distinct from retry while a writer remains live.

Successful `CNS3Writer.Sync` returns cumulative `result.persisted` to its caller, while `FillBlockInfoBat` reads the sinker's retained copy. These objects leave the sinker's pre-Sync cleanup set, but workspace-owned objects remain unrecorded until the transaction or downstream consumer records their stats; the existing workspace retainer handles that later ownership window. `SyncAndTakeResults` removes stats before `SyncAndFillBlockInfoBat` expands them. For an unbound writer, an expansion failure or an error after successful Sync but before output reaches a recording owner is a pre-existing post-handoff orphan gap outside this admission fix. For a workspace-bound writer, the reservation map or epoch-aware retainer must own those objects until they are recorded or queued for cleanup. Workspace rollback after registration iterates all object stats; no claim is made for remote output loss, process death or crash before registration. Main's `WithBeforePersist` is not invoked by current pipeline workers, so it is not a restart-safe CN guarantee. No cross-consumer acknowledgement protocol is added.

Operation contexts retain caller cancellation and deadlines. Check cancellation before work and between bounded admission/spill steps. Pipeline derives its context from the first Write; a later Sync-context cancellation must cancel the generation, drain workers, and preserve the first operation/worker cause without leaking a waiter. Define terminal selection once, with synchronization: an already selected worker error stays the result if cancellation races it; cancellation observed before successful Sync selection aborts the generation; once successful Sync has selected and completed its result handoff, a later racing cancellation cannot retroactively turn it into failure or make its objects eligible for deletion. A later worker failure cannot replace an already selected cancellation. The exact selection point and callbacks must be race-tested. Automatic deletion is bounded by the operation context plus a total 10-second cap, never a fresh background context. An unbound synchronous CN teardown owner may outlive cancellation, using `context.WithoutCancel` **only for teardown**, retaining context values and setting its deadline to the earlier of the original operation deadline and finalizer start + 10 seconds. If there was no original deadline the 10-second finalizer cap applies; if the original deadline already passed, skip deletion and report/retain the snapshot; never renew it. An explicitly authorized later retry may receive its own fresh bounded context. Cancel these contexts and start no detached goroutine. All timing bounds depend on FileService/worker context cooperation; drain cannot be guaranteed to end on time if they ignore cancellation.

**Q1–Q3:** Q1: current buffer, staged slices, pipeline job and unpublished names each have a named owner; the final failed-delete/drop limitation is explicit. Q2: clear the sender's pointer before push/submit, and clear name references only after successful delete, actual handoff or a clearly reported terminal writer drop; handed-off results are excluded. Q3: every prefix iteration advances or spills; cancel before waiting, retain original deadlines, bound cleanup, retire failed retained writers before reuse, and add no worker/queue. Diagnostics do not establish deletion.

## Single-row and retained-memory behavior

A single row above the target is isolated, not artificially rejected merely for crossing the soft target. Its source, staging/merge copy, full serialization, LZ4 scratch and compressed data can still exceed memory limits. The speculative round-up fix (#32052) does not make a compression bound larger than `mpool.MaxAllocationSize()` allocatable. Add a checked path at `objectio` compression: validate overflow/format limits and return the original allocator error when the required LZ4 bound is not representable/allowed, rather than panic from `WriteArena.CompressBuf`. That exported method is a released main API: preserve its signature and established behavior for existing callers, factor the common allocation into a private error-returning method and use that method from the object writer. This is preservation of a released API, not an intermediate PR compatibility shim. Update direct tests and do not replace the original mpool error identity with a generic error. Handling this known-impossible scratch request belongs in the issue because an isolated oversized row otherwise still takes the preexisting panic path; broader recovery from every allocation failure is separate. For a single-row legacy column, reject a provably impossible compression bound before growing the full serialized buffer where possible; do not reject a multirow column which a genuinely enabled/eligible chunk encoder can represent. Real alloc failure, Go buffer growth and fatal process OOM remain possible; this does not promise recovery from all OOMs. Test arithmetic through an injected/synthetic size limit, not multi-GiB allocation.

Main's `BatchFreeList.Putback` clears lengths but deliberately retains all allocated vector capacity, including oversized rows, until its owner closes; multi-update can share it across Reset. Do not claim otherwise. In eligible mode avoid parking a batch whose allocated capacity exceeds the run budget; clean it instead, including when returned after failure. This is a per-batch guard, not a total pool-size cap. `FSinkerImpl.Reset` keeps its arena; `WriteArena.Reset` can retain large compression scratch, while `PutArena` drops serial buffers >16 MiB but may retain compression scratch in the bounded-count arena pool until its idle reaper. Measure immediately after success/error/cancel and after subsequent small writes/close; if retained compression scratch dominates, identify a focused main-specific eviction with benchmark evidence, rather than promise existing Reset frees it. Pipeline global queue/workers also multiply peak: bytes in inputs + staged run + merge output + serialized column + LZ4 capacity + retained buffers + concurrent jobs; chunking can add further window copies. The target bounds only one term.

## Minimal change map and alternatives

- `pkg/objectio/ioutil/sinker.go` plus a small private run-sizing helper: opt-in data-run admission, aligned charge ownership, compact copying, error/cancellation cleanup, existing delete helper reuse and generation handling. Preserve generic `DeletePersisted` behavior. `sink_pool.go` only if required to propagate cancellation/drain without new goroutines or duplicate ownership.
- `pkg/sql/colexec/s3util.go`: enable the behavior for eligible CN data and tombstone writers; preserve `flushOnSync`, sort/dedup exclusions, existing allocation mode and public handoff. Add the explicit retry/snapshot APIs and the concrete teardown/reuse handling under `insert`, `multi_update`, `deletion`, and disttae as specified above. No unneeded change to `mergeutil`, object stats, file format, vector allocation APIs or SQL protocol.
- `pkg/objectio/writer.go` and direct tests for checked compression/allocator error while preserving the released `CompressBuf` API, as above. Sinker, writer, colexec/consumer and SQL tests cover their respective boundaries. Production use of a custom FileSinker without active names cannot support the automatic deletion guarantee; do not enable it merely by setting a general option without the matching factory/fileservice contract.

Alternatives: status quo is cheapest but the reproduced oversized runs disprove the target. Byte flush inside merge fails unsorted and risks underfull middle blocks unless each partial forces an object rollover, and duplicates general/disjoint logic. Stream/chunk serialization can reduce scratch and may be valuable separately, but current chunking starts too late and falls back; a format/reader change is disproportionate here. Exact optimal row packing requires extra scans and complex area tracking; conservative prefix packing can create more objects but preserves the established fast path and consumer contract. A new general cleanup worker, global cache, durable marker protocol or transaction-wide acknowledgement framework is not justified by this local admission fix; such a change would require its own ownership and recovery design.

No new format, catalog, security or tenant boundary; objects remain in the existing format and use the existing transaction access rules. Feature is on by default only in eligible CN data and tombstone writers, with no additional configuration or rollout gate; an operational rollback is reverting this code. More objects, metadata and I/O are expected, especially for skew/large rows. Existing metrics and spill debug log show counts/timings; record object count and threshold in validation rather than introduce high-cardinality metrics. Shutdown upgrades read existing formats normally; no new mixed-version requirement or restart guarantee is introduced.

## Validation and acceptance matrix

All tests must record exact base/head, selected nonempty test names, build/toolchain/native provenance, terminal result and logs. Use existing fixtures and the prescribed CGo wrapper; scope gofmt/vet/lint to changed owning packages plus real consumers. The base reproductions are pre-fix counterexamples, not final validation.

1. **Readback/invariants:** real FileService write/read, sorted/unsorted × sync/pipeline; verify every value/null/type, row multiset, persisted sort and object/block metadata; independent charge oracle over the *whole object*, equality/below/above, partial refill across multiple Writes, zero-fit with nonempty run, singleton oversized between small rows, and no empty object/infinite loop. Validate actual metadata-free `StatsBlkIter` rows vs real block metadata, with both a full-block+partial object and multiple partial objects. Cover heap-overlap and disjoint-range keys, fixed-only, constants including const-null, inline boundaries 22/23/24/25, aliased descriptors, borrowed input, null slots with stale descriptors, dead area across different columns, whole/split windows, `WriteOwned` direct/fallback/rejection and checked overflow. Assert intended cases fail at the exact base (including the 1 KiB four-mode witness); the new implementation must pass. Separately use a recording FileSinker to assert grouping, prepare-parameter provenance, string-source provenance and runtime string-domain sidecars at the pre-serialization boundary after admission/copy/sort/merge. `Vector.MarshalBinaryPlan` and chunked windows do not persist these sidecars; this change adds no persistence for them. Add tombstone variable-length-PK readback, all-stats delivery through the delete consumer, failure on a later object, and rollback; retain the tombstone's existing allocation mode.
2. **Failure/cancellation/lifecycle:** inject sort/fetch/preflight/copy/sink and pre/post-persist Sync failure, enqueue failure, cancellation while workers are blocked, and successful sibling after another fails. Use gates/channels, not sleeps. Assert original error/cause, all buffers once, no worker left, all pre-handoff known object names included, fail-then-retry delete retained, Reset does not lose names, new generation cannot inherit stale jobs, and already Sync-handed-off objects survive a subsequent failure. Through `CNS3Writer`, test failure → cancelled cleanup → read-only snapshot → explicit retry → Reset/reuse; exercise the real retained multi-update owner for both successful retry and failed-retry retirement/reconstruction.
