# 4.1.6 pipeline terminal delivery repair

## Scope and design decision

Base: `v4.1.6`, `3c7eb8de7f2388de84624fdaf719cc218f8078dc`.
Implementation branch: `fix/4.1.6-pipeline-terminal-delivery`.
Owner/request: the local customer mo-dump investigation and its authorized fix.
There is no published implementation PR yet.

This is a backport of an existing execution contract, with R3 concurrency and
resource-lifecycle risk. The complete backport crosses process, spool, operator,
and compiler ownership boundaries, so design review precedes implementation.

Design review, 2026-10-21, self/delivery mode: **PASS for implementation**.
The reviewed decisions are recorded below before any production edits. This is
not implementation approval; delivery still requires the validation closure.

## Problem and evidence

An unmodified official 4.1.6 service reproduces terminal loss with real SQL and
with the actual mo-dump client. A slow consumer fills the data notification
channel. Connector cleanup times out sending its final notification, exits, and
leaves the parent query live. When consumption resumes the remaining data is
read, but `PipelineSignalReceiver.listenToSingleEntry` still expects an end.

The mo-dump reproduction uses 262,144 rows containing 64 MiB of payload. Pausing
only the client for 75 seconds near the end of output produces default 30-second
terminal-send failures. Two post-resume dumps show the same
Output -> Merge -> receiver wait with no producer cleanup goroutines. The
immediate-consumption control completes. There is no OOMKilled event.

Preserved baseline evidence:
`/tmp/mo-416-real-repro-evidence-20261021.tar.gz`. The customer incident's original
backpressure trigger and its full memory composition remain unproven.

## Contract

1. Every completed producer records a terminal outcome independently of data
   channel capacity. Every terminal receiver can observe that outcome without
   requiring another successful enqueue.
2. Normal completion consumes already published batches before synthesizing a
   missing End. A shared edge completes after all expected producers finish.
3. Error and abort preserve the execution cause. A cleanup fallback or sibling
   cancellation must not overwrite an independent execution error or deadline.
4. A consumer may retain its current spool batch until ReleaseCurrent. Abort
   releases pending work without freeing a current consumer's memory.
5. Graceful spool reclamation follows paired receiver cleanup. Failed batch
   admission returns every unpublished slot/cache checkout. Slot reuse detaches
   old batch references before publishing either pooled resource.
6. Reusing a compiled scope starts a fresh terminal generation and releases
   abandoned signal resources. Reuse occurs only after the previous execution's
   workers and receiver cleanup have stopped.
7. The normal query has no cleanup-only execution deadline. Terminal publication
   cannot wait behind the data channel it terminates.

## Alternatives

* Keep the legacy protocol and increase deadlines: a finite deadline can still
  discard a notification, while an unbounded wait recreates the original cleanup
  deadlock. Neither establishes an observable terminal outcome.
* Fail the whole query when terminal enqueue times out: bounds the hang but turns
  a healthy slow consumer into an execution failure. This is insufficient for
  normal large exports and risks broad cancellation of shared producers.
* Backport the established edge terminal protocol with its relevant follow-ups:
  chosen. It has explicit ownership and deterministic component tests for the
  failed boundaries. This has a larger but bounded source change and requires
  compiler, operator, and receiver changes together.

## Ownership and transitions

`PipelineEdge` owns a bounded terminal record, expected End count, first fatal
cause, and Done/Abort notifications for one execution generation. WaitRegister
uses that same record. Terminal publication linearizes while holding the edge
terminal mutex. Enqueue is an optional nonblocking fast path. Receiver selection
drains queued signals, synchronizes with publication, rechecks the queue, and
then synthesizes only undelivered terminal events.

An open edge accepts data. Each producer's End advances the expected count; the
last End closes Done. A fatal terminal closes Done immediately and prevents
new data admission. Existing terminal cause wins over cleanup fallout. Repeated
publication after completion is idempotent. Before shared completion, each
producer must publish End exactly once: the edge counts producers and does not
identify individual senders. Prepared scope reset creates a fresh generation only at
the existing quiescent compile-reset boundary.

The spool owns copied/cache batches until publication and final receiver release.
Its Abort owner reclaims unconsumed slots; an already popped slot remains valid
until its receiver releases it. Normal typed End does not manufacture a legacy
nil batch inside the spool. The producer pipeline cleanup owner sweeps the
byte cache after its own paired receiver cleanup has returned. Published and
current downstream batches keep their memory; releases after the sweep free
directly instead of returning bytes to the closed cache.

Query cancellation and child pipeline cancellation keep distinct ownership. This
backport preserves the 4.1.6 remote cancellation contract and error identities;
it does not import unrelated remote StopSending/connection lifecycle redesigns.
Any adaptation must retain real query deadlines and substantive error leaves.

## Bounds, performance, and compatibility

New terminal state is O(1) per existing edge, not per row/batch. Multi-input
receiver selection retains O(input count) state. Spool capacity is unchanged.
There are no new background workers, retry loops, unbounded terminal queues, or
query-ID maps. The existing typed protocol adds synchronization to edge/spool
ownership; no throughput improvement is claimed. Normal operation must not
depend on 30-second cleanup timers.

The protocol is internal to one CN process. Keep remote pipeline protobuf,
batch encoding, End/Error wire responses, SQL syntax, catalog, and on-disk data
unchanged. Existing remote terminal responses are translated to local edge
outcomes. A mixed old/new CN pair still exchanges the existing wire messages;
the old CN's local terminal bug remains possible until it is upgraded. Rollback
uses the previous binary without a data migration. New process instances start
with fresh transient state. There are no new privileges or tenant-visible APIs.

## Change and validation map

| Closure | Owners/consumers | Risk | Required evidence |
| --- | --- | --- | --- |
| Edge publication, receiver selection, reuse | process, compiler construction/reset | R3 | full queue, expected producer counts, data ordering, fatal wakeup, <=8 and >8 inputs, reuse; race |
| Spool admission, abort, current batch, reclaim | pSpool, Connector, Dispatch, pipeline cleanup | R3 | failed copy rollback, broadcast and current ownership, double cleanup, zero outstanding pool memory; race |
| Scope cancellation and error propagation | compile, remote forwarding, operators | R3 | real errors vs sibling cancel, query deadlines, original remote failure; dependent tests |
| Public completion | frontend, mo-dump/SQL sessions | R3 | same real mo-dump workload resumes successfully with complete CSV; lock-backpressure SQL completes and releases locks; prepared execution twice |

Reuse imported component fixtures rather than add a second protocol harness.
Run focused tests first, then affected owning packages normally and under race.
Use exact individual concurrency tests for bounded adaptive repetition. Preserve
the stock-image failure evidence and verify the fixed source using a freshly
built 4.1.6 binary with that version's own native dependencies. Use real SQL and
the actual mo-dump client for the externally visible contract. A component pass
alone is insufficient. Mixed-version proof follows the changed wire boundary;
there is no new wire encoding to migrate.
