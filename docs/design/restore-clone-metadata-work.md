# Remove unused DDL work from clone-based catalog restore

Owner: frontend snapshot/PITR restore. Tracking: [#29562](https://github.com/matrixorigin/matrixone/issues/29562). Implementation: the PR containing this document, together with initial-role-privilege-inserts.md.

## Evidence and contract

All three restore families (snapshot, PITR, cross/dropped-account timestamp restore) use the compile-time constant CREATE TABLE CLONE format. Their recreate-table functions still test that constant with a regular expression, leaving three permanently unreachable manual CREATE fallbacks. System catalog restore fetches SHOW CREATE for every copied table although only that unreachable fallback consumes ordinary table createSql; clone owns source schema/data resolution. The UDF catalog instead restores through its existing current-schema owner. dropClusterTable likewise retrieves every catalog CREATE definition despite consuming only name/type to issue DROP or DELETE.

Remove the unreachable fallback blocks, their sole-purpose regexp and commented old INSERT formats. At each system-catalog restore owner, obtain createSql only for sequences, whose existing restoreSequence consumer actually needs it. Retain the original sequence lookup and every other source/target/context/identity/protocol/transaction/cleanup check. For dropClusterTable, enumerate directly through existing showFullTables and retain the exact cluster-table selection, two view-metadata DELETE exceptions and sequential error propagation.

Historical user-table enumeration remains unchanged: its CREATE SQL is still needed for durable FK topology and view planning, even when execution later clones ordinary tables. There is no global lazy-DDL mechanism, new inventory/cache, schema/persistence/protocol change or fixture change. No read of current target identity or live lifecycle state is reused. System tables are still recreated, not overwritten in place, preserving user/role generation semantics. Empty objects must not be skipped. Whole restore commits or rolls back at its existing transaction owner.

## Alternatives and failure boundaries

Keeping the dead fallback requires unnecessary SQL and a false compatibility branch. A generic lazy metadata provider or account inventory cache adds lifetime/identity state for a local ownership cleanup. Reusing user-table inventory is a separate candidate with view-preflight/ordering risks and is excluded here. Selected: remove the obsolete path and unused work at the existing consumer boundary.

The clone executor must still surface source-resolution failures and existing preflight/runtime protocol checks must still apply; no error is suppressed to make this optimization pass. Snapshot recreateTable currently tolerates ErrNoSuchTable naming a different object for user FK restore. Restrict that existing tolerance to user databases: catalog cloning must propagate this failure and stop, because every copied authorization/catalog object is mandatory. PITR and cross-account timestamp cloning already propagate it. This is an owner-based error policy, not a table-name whitelist. Source enumeration failure, sequence lookup failure, cancellation and downstream DROP/DELETE/CLONE failures retain the existing terminal error and transaction rollback paths. DROP IF EXISTS remains safe for stale listed objects; view metadata DELETE retains its lifecycle-gated owner and a missing special table or other DELETE error must propagate, including corrupted stale listings. Validation must explicitly check this closure rather than assuming that fewer SQL statements implies equivalent behavior.
