# Consolidate catalog upgrades for 4.1 and 4.2 sources

Status: design reviewed; validation is required for the final change before delivery. Issue: [#31490](https://github.com/matrixorigin/matrixone/issues/31490). Main base: `f84780380228`; source controls: v4.1.0 `c58a0e62c382`, v4.2.6 `71498157cc21`, and 4.2-dev `86a45d39df3d`.

## Scope and observed behavior

The requested source is a stopped, intact deployment whose current released version is 4.1 or 4.2. Direct upgrades from 3.x and unreleased 4.3 intermediate catalogs, downgrade and mixed-version operation are out of scope. This boundary does not erase older data: a 4.1 or 4.2 source can contain snapshots created before that release. The migration must preserve data, existing snapshot records and retention. Ambiguous historical snapshot ownership must follow the user's explicit decision: pause and obtain administrator confirmation by snapshot UUID; do not guess from the snapshot name alone.

The target catalog version is `4.0.7`, above published 4.2's `4.0.6/5`; its offset follows the existing handler metadata contract and is fixed when the final entry set is frozen. Freeze the released 4.0.6 effects; place necessary subsequent effects in 4.0.7, preserving the existing version/tenant task owners and recurring maintenance. Do not register the unpublished 4.0.8–4.0.17 identities as new upgrade steps. Preserve unrelated current-main behavior and existing maintenance owners.

On a v4.2.6 source, unmodified main reached 4.0.17 and retained the sampled user rows, but lacked foreign-key metadata columns and UDF `arg_types`: main had appended them to the already-consumed 4.0.6 handler. On a freshly initialized v4.1.0 source, first startup on PR head timed out waiting for query-ready CN inventory while the older upgrade route had not yet created `mo_view_refresh`. On one unmodified restart, the route created that table and the CN appeared in query-ready inventory about two seconds later. The source fixture had working indexed/FK tables, a function, a procedure and account snapshots. After the resumed upgrade, table/tenant rows and FK enforcement remained, but the function, procedure and restoring the 4.1 account snapshot all failed because `sql_mode` was missing; historical table reads still worked.

Both released 4.1 and 4.2 snapshot catalogs have `kind`, so the direct 3.x missing-column bootstrap and snapshot-catalog self-swap are not required simply to start from these source versions. Nevertheless, a real 3.x-origin branch protector had already been marked `user` by a released 4.1 and remained so after 4.2. An old user can also create the identical canonical internal name, parent and timestamp, so those fields alone do not distinguish owners. The earlier user decision remains applicable to genuinely ambiguous inherited records.

There is a separate SQL-semantics issue: on a fresh v4.1.0 source, both `select '1'||'2'=12` and a function with that body returned `10`; the same body on current code with `PIPES_AS_CONCAT` returned `1`. Adding a default `sql_mode` alone must not be represented as preserving all legacy routine semantics.

## Design decisions

The existing bootstrap framework remains the owner of catalog routing, tenant tasks and final readiness. A ready 4.1 source follows the 4.0.2–4.0.6 route before the new 4.0.7 step; a ready 4.2 source starts at 4.0.6. An interrupted published 4.1-to-4.2 route must finish using its recorded target, step states and flags before 4.0.7 begins. Interrupted routes whose physical source is 3.x are deferred with direct 3.x upgrades. Do not replay a completed 4.0.1 step merely because newer code added work to it. The current 4.0.5 handler deliberately uses an intermediate COLUMNS view definition compatible with earlier catalog columns and a writer protocol gate; preserve that prerequisite ordering rather than mechanically substituting release source linked against newer view constants.

Restore the 4.0.6 cluster and tenant effects to the published 4.2 handler. Move the later additions, including custom FK and UDF migration, into 4.0.7 along with the necessary 4.0.7–4.0.17 effects. Deduplicate successive information-schema refreshes to the final definition where prerequisites permit. Preserve dynamic index-provenance migration, ongoing VIEWS maintenance, orphan-privilege maintenance, and all distinct upgrade oracles when removing superseded handlers. Refresh COLUMNS and TABLES through the 4.0.7 tenant upgrade. New accounts install the complete current information-schema definition set in the account transaction; unavailable or insufficient capability aborts initialization instead of committing predecessor views with a 4.0.7 marker. The target offset follows the existing metadata convention and is frozen when 4.0.7 is released. The paged account-version marker cannot represent offset-only progress: reject a 4.0.7 offset mismatch before any catalog mutation, and assign later migrations a new semantic catalog version.

Information-schema reconciliation preserves logical object identity and every existing exact-object privilege row. Shared definition checks accept only the authored `CREATE VIEW` and corresponding `CREATE OR REPLACE VIEW` forms and look up both stored name cases. Existing views use replacement; the three released table-to-view conversions read the old identity and reuse the existing `WithKeepLogicalId` executor option inside the same DROP/CREATE transaction. Startup and recurring view maintenance use this same guarded entry owner. Failed work rolls back; an already matching definition causes no DDL.

The unsigned-flag backfill remains a raw `mo_columns` update: checkpoint tooling and catalog queries consume that stored flag. Catalog cache replay recognizes a column-only update as a no-op only when the first visible older table has the same physical identity and a complete, internally consistent schema, and every incoming column has an identical cached attribute projection. It uses the existing column decoder and projection owner, keeps the published table version unchanged, and retains the existing error for a failed proof. The normal exact-timestamp path also checks the physical table identity and tombstone. No synthetic table version, protocol field or durable progress is introduced.

This cache proof relies on the existing intact logtail contract: committed DDL delivers its table and column events together; the dispatcher applies tables before columns, and reconnect applies delayed updates in FIFO order after its catalog snapshot. It is not recovery for lost DDL events or arbitrary privileged catalog writes. The unmatched path scans the prior schema and changed group, costing O(cached columns + changed columns); a wide table spanning several backfill pages repeats that schema work. Normal exact-timestamp DDL does not enter the fallback. Raw partition replay still retains the updated unsigned flag.

Before ordinary admission can require the view metadata fence, bootstrap must synchronously and idempotently establish `mo_view_dependencies` and `mo_view_refresh` in a committed system transaction, using the existing checked DDL and existing version lock with current visibility and retry on conflict. It must not wait on the same admission it enables. Bootstrap and nested internal SQL need local TP/AP_ONECN placement until the final version is ready, including the precondition and schema initialization; this avoids dependence on a remote worker inventory that may still be closed. Existing protocol-discovery control RPCs remain available. The actual bootstrap execution path and lock order require independent review.

The 4.0.7 tenant reconciliation must check and add missing UDF and procedure `sql_mode` columns without replacing explicit stored modes, and apply the required FK and UDF signature migrations. A snapshot/PITR restore or database clone must inspect the historical source account's catalog shape at the snapshot timestamp, then project its rows into the current target shape. Missing 4.1 `sql_mode` uses the released 4.2 default; UDF argument types are derived by the existing backfill rule. Other changed copied catalogs need the same source/target schema analysis. Errors other than a verified missing historical column must not be treated as a missing column.

The parser precedence difference has been verified on both released binaries: the example above is `10` on 4.1.0 and `1` on 4.2.6, and is not introduced by this PR. Do not claim arbitrary 4.1 SQL definitions preserve results merely because `sql_mode` is populated. The catalog repair preserves stored definitions and uses released 4.2 behavior; a general historical SQL execution mode is a separate capability. Document the concrete limitation and verify ordinary routine behavior as well as the counterexample.

Before ordinary work is admitted, inspect system-account snapshots. Published writers create internal protectors as system table-level snapshots with canonical names `__mo_branch_<decimal child ID>`. A canonical row already marked `branch` retains that classification. A canonical system table-level row marked `user` is ambiguous even if its parent and timestamp match a branch edge, or if there is no edge; the user chose an administrator decision keyed by snapshot UUID. Other user snapshots remain unchanged. Do not fabricate a protector for an unrelated branch whose pin was already absent, rename snapshots, or claim to recreate history that has already been collected.

On ambiguity, a bootstrap-only diagnostic reports undecided UUIDs, complete snapshot preimages and any corresponding edges, including explicit `null` for an absent edge. The administrator stops and drains all CNs, publishes `SHARED:/catalog-upgrade/4.0.7/decisions.ndjson` using the offline command, and restarts them. The manifest is UTF-8 JSON Lines: a format/target header followed by records sorted by canonical snapshot name. Each record contains the catalog account ID, UUID, name, timestamp, scope, account/database/table names, object ID, expected `kind=user`, nullable edge fields and the decision `user` or `branch`. Compare nullable fields as null rather than coercing them. Decimal IDs and timestamps are strings; input is decoded with a 256-KiB per-record cap and never interpolated as SQL. A missing file is acceptable when no ambiguous rows exist. The publication command validates the complete input first. DISK uses its atomic replace operation; object services without replace delete and write the whole object while every CN is stopped, and a failed write must be repaired before restart.

All CNs read identical immutable contents with existing file-service caches bypassed; the shared backend must provide consistent reads of the atomically published object. Missing, duplicate, unknown, stale or conflicting decisions fail closed with an actionable diagnostic. A previously applied branch decision is compared against the same preimage except for its already changed `kind`. Replacing the file requires all old CNs and transactions to be drained first; a retry with invalid input never undoes already committed pages.

The existing cluster-upgrade worker performs a full bounded-page preflight of the immutable manifest and candidates before writing. After the preceding released route is durably complete, it commits at most 128 decisions and 4 MiB per transaction, locking the existing version/step and SNAPSHOT lifecycle rows in that order, then rechecking the step and every row and edge preimage under current visibility. Only `user → branch` selected by UUID changes data. An exact previously applied branch decision is a no-op, a user decision leaves its row intact, and a contradictory branch-to-user reversal after partial commits fails closed for restore from backup or deliberate manual repair. Omission of a previously committed decision after manifest replacement retains that committed classification; omission cannot revoke it.

Final validation streams bounded pages outside the ordinary route transaction. With all other snapshot/lineage writers gated and every worker reading the same input, concurrent workers can only apply the same monotone decisions. A worker with a complete validation pass may proceed with the separately committed 4.0.7 cluster entries; before every such entry and before publishing tenant-task availability it reacquires the relevant locks and rechecks that the step is pending. If another worker advanced it first, stop without writing. Earlier cluster-entry commits are not rolled back by a later failure. The existing `newUpgradePass` must commit a preceding step before this prephase and may not hold its encompassing transaction open while separate page transactions run. After a crash the worker rescans; no additional durable cursor or phase is introduced. An unbounded number of restarts or a fixed deadline shorter than a full scan can prevent completion, so the overall wait is cancellable rather than fixed-duration; individual operations still have bounded attempts and actionable failure.

The page cursor uses the existing snapshot-name primary key and a Top-N query; the UUID remains the decision identity. A synthetic 30,000-row comparison took about 195 ms for 235 name pages and 518 ms for UUID pages, versus 18 ms for a single UUID-ordered stream. This is a small local measurement, not a production performance estimate or proof of linear work. Bound decoding and page bytes, validate ordering/collation and actual query plans, and measure the real catalog. Repeated keyset scans can do more work than a seek, and the page bound does not establish a bound for the ordinary cluster or tenant effects.

### Ordinary upgrade work, failure and resource boundaries

Keep `mo_version`, `mo_upgrade`, `mo_upgrade_tenant` and `mo_account.create_version` as the only durable upgrade-progress owners. Account membership and all catalog inputs relevant to this phase are frozen by the admission fence. For new `Created` steps, enumerate tenant IDs in primary-key order in transactions containing at most 128 IDs, producing the existing nonoverlapping ranges of up to 16 accounts. The step lock serializes insertion. Read the last committed range *after* acquiring that lock, using a pessimistic read-committed transaction, and atomically insert the next ranges and add their actual account count to `total_tenant`. Current-step task rows are never removed while enumeration is incomplete. The initial task set is empty for its upgrade ID; each transaction extends the same complete prefix. Once a current locked read finds no remaining account, the cluster entries are complete, and all prerequisites hold, transition the step to `UpgradingTenant`. A transaction whose commit result is unknown is retried by reading the committed ranges and counters, not by trusting process-local state. A published step already in `UpgradingTenant` retains its original task rows and counters; it is not re-enumerated. Reject counter overflow or a malformed/non-prefix task set instead of guessing.

For the consolidated 4.0.7 cluster work, execute each independently idempotent entry in dependency order as its own transaction while the step is `Created`; keep each inseparable `PreSql`/DDL/`PostSql` group together. Before each transaction lock and recheck the current version and step; on retry replay and verify the precise required final state, not merely that an object name exists. Recheck under the same lock before publishing task availability. A worker that sees the step has advanced stops without further writes. The released 4.1-to-4.2 route keeps its historical entry behavior and any already-created tasks; bounded enumeration must not reinterpret an in-progress published task or its offset.

For 4.0.7 tenant work, use the existing task range and account-row locks to serialize concurrent work on the same accounts, while allowing disjoint ranges to run concurrently. Each transaction applies at most one schema entry, one complete FK child-table group, one metadata-table DDL, or one bounded data-backfill page. Input tables are enumerated in stable, unique catalog-key order, not physical row IDs. For FK reconciliation, retain all columns of one child table together when deriving constraint ordinals and referenced keys; `referenced_index_name=''` is a possible correct final result, not a completion sentinel. Index reconciliation checks the expected definition and uniqueness; for indexes represented in `mo_indexes`, it also checks that the single referenced physical table exists. The task tables do not populate that catalog and are checked against their relation definition. Physical-table existence does not prove the index contents of an already corrupted catalog; normal transactional index creation is the completion guarantee for intact deployments. Re-run the complete ordered reconciliation after restart; neither a successful page nor an empty value is evidence that an unfinished tenant is complete.

Background, manual and login upgrades share one 4.0.7 tenant walker and the same per-statement page/object limits. Service-owned work releases its planning transaction before opening each operation transaction. A caller-supplied transaction retains ownership and atomicity: no hidden commits or completion cache publication occur, and its aggregate workspace remains caller-owned rather than bounded by a per-result limit. On-demand completion publishes only the account version; existing task reconciliation accounts for it. A ready 4.0.7 account is a no-op even on a restarted CN, while historical published offset semantics are unchanged.

Each page locks the relevant account range and rechecks that the account still needs this step before writing. After a complete successful pass over frozen input, publish the account's `create_version` and increment `ready_tenant` in the same transaction under the step lock. Mark the task ready only after checking every live account in its range under the same account locks; keep the existing deleted-account reconciliation for accounts absent before the freeze. Paged enumeration and tenant completion share `UpdateVersionUpgradeTasks`, which now updates only counters and does not change the step state when the counters match. The cluster step owner performs the separate `UpgradingTenant → Ready` transition under the step lock only after a current read proves enumeration is complete, no task is unready, counts agree, and no asynchronous work remains. If a crash occurs after the final account commit but before task publication, a worker must still pick up and finish that task even when the counters already match. The final version becomes ready only after that step transition. The lock order is account range, then step for the short counter update, matching the existing tenant worker; the cluster side must not hold the step lock while waiting on account locks. A stale worker must recheck after acquiring its locks and may not write after account completion.

This deliberately does not promise durable per-page scan progress: an empty FK result can leave no distinguishing durable change. A crash can require rescanning the completed prefix, so completing a tenant requires a sufficiently long crash-free scan. A durable object cursor would avoid repeated rescans, but adds persistent recovery state and is not needed for safety under the stopped-writer contract; it can be added later only if measured restart/recovery requirements justify it. Unknown commits, repeated pages, cancellation, and two CNs racing on the same range must preserve the same final data and exact counters.

The migration owns bounded client buffering: key pages contain at most 128 identifiers and ordinary decoded decision/data pages at most 4 MiB. An indivisible FK group or `SHOW CREATE` definition has a separate per-worker object-input limit, default 64 MiB, exposed through one CN startup setting `upgrade-catalog-object-limit` in bytes. A positive value below 4 MiB is invalid. Before restarting an old deployment, set the same limit on every upgrading CN; a diagnostic names the tenant, object, operation and observed limit so the operator can provision memory, raise the limit on all CNs and restart. This setting does not alter catalog progress or the 4 MiB page bound. It exists so a valid large object is not permanently unupgradable merely because of a hard-coded page size.

Queries must constrain projections before materialization; a `LIMIT` on rows alone is not a byte or server-work bound. Where a single complete SQL result cannot be pre-sized, extend the existing internal SQL executor's result-collection owner with a per-statement logical payload ceiling and reject a batch before cloning it into the accumulated result; it must release any accumulated batches and roll back the transaction on error. The estimate includes cloned row storage, variable-length payloads and vector metadata; allocator capacity and NULL/grouping bitmaps are additional. The result ceiling is the page or object-input limit appropriate to the statement, not a new global executor default. The original producer batch, `SHOW CREATE` generation, SQL scans/sorts, physical DDL/index construction, parsing, transaction workspace and other Go allocations are separate from that retained-result ceiling. They remain subject to the engine/process limits and provisioned memory, and are not claimed to be bounded by the 4 MiB page size. The bootstrap SQL executor uses a shared CN mpool with no private upgrade cap; the frontend internal-executor session limit is not an upgrade quota. Measure these paths, cap migration-owned buffers before retaining data, and test partial-result cleanup and failure reporting before claiming the corresponding bound.

An object over the configured input limit aborts its transaction and reports a terminal error through startup; committed idempotent work remains behind the fence. A typed terminal decision rechecks current progress so another CN's already-committed success wins over a stale failure. Shared engine memory pressure is reported with operation context and retried at the existing paced interval: it can clear, or another CN can complete the work, so a finite number of failures does not prove the cluster cannot progress. Persistent pressure requires operator action. Operators must provision adequate resources for the largest individual operation; arbitrary object sizes and crash frequencies are not promised. As for other non-rollbackable catalog upgrades, operators retain a verified pre-upgrade backup.

During this phase every CN keeps public and special-user SQL, connection migration, ordinary remote pipeline execution and task runners closed until durable final-version readiness. Bootstrap and nested internal SQL use local TP/AP_ONECN placement; protocol discovery, cancellation and cleanup control RPCs remain reachable. Reject ordinary remote pipeline execution at its receiver while unready. The existing task runner gate and deferred optional lineage compaction prevent background snapshot/branch/PITR mutations; audit the remaining internal writers and prove the fence with multi-CN tests. Physical GC can continue only while retaining every existing snapshot row regardless of `kind`. A typed terminal operator-action error is delivered through the existing bootstrap/startup owner after a current-progress recheck; transient errors still retry.

Startup cancellation must be published before waiting for the CN, embedded cluster or embedded operator lifecycle locks. A short generation lock serializes registering a pending start with stop's cancellation: the operation that wins the lock defines whether the start belongs to the canceled generation, and a new generation is installed only after cleanup completes. The launcher propagates role cancellation. A completed cancellation joins the upgrade workers and closes ingress, or retains the owner for cleanup retry. On an old source configured with `auto-upgrade=false`, fail with an explicit instruction to enable automatic upgrade for the stopped migration and restore the setting afterwards; otherwise the existing manual SQL command would be trapped behind the closed ingress. Fresh or already-current installations retain existing manual-mode behavior. This restriction increases operational burden and must be tested and documented.

## Acceptance evidence

- Upgrade preserved copies of real 4.1.0 and 4.2.6 data in a single shutdown/start cycle, plus representative interrupted published routes and fresh tenants. Compare final cluster and tenant version, indexed and FK behavior, routine results, user and branch snapshots, old snapshot/PITR reads and restore, and internal index visibility.
- Verify ambiguity decisions by UUID, including real matching user-name collisions and inherited branch protectors, with restart, missing/stale/conflicting input and competing CNs. Never silently relabel or discard an existing snapshot.
- Verify startup, cancellation, admission and background mutation ordering for the actual selected migration, not only the nominal happy path. Exercise failure/rollback/retry and prove checks do not advance progress after failure.
- Measure incremental resource and upgrade work on the relevant path, including each 4.0.7 transaction and any snapshot scan. Avoid claiming production bounds from small local probes.
- Exercise tenant enumeration across several pages with two CNs, a crash and an unknown commit outcome; assert no omitted/duplicate range and exact counters. Exercise a published already-upgrading route without changing its tasks.
- Exercise multiple tenant pages, a legitimate empty FK result, a conflicting index definition, object-budget and engine-resource failures, cancellation, and a crash immediately before or after account publication, including after the last counter increment and before task completion. Check that disjoint tenants can progress concurrently, incomplete tenants stay unready, and a resumed pass produces identical visible results. Verify that an oversized object succeeds after increasing the configured limit, and that capped result collection releases partial batches without claiming an engine-memory bound.
- Run targeted affected unit/race tests and incremental static checks on the final diff; run the independent design and final code reviews required by the active workflow. Record exact revision, scope, commands and terminal results.

## Remaining design closure

Historical system-account and cluster restores fail before mutation if the source CDC watermark schema lacks current identity/generation columns. This avoids restoring the old 4.1/4.2 shape, but does not coordinate running CDC or validate an external target: operators must stop and drain CDC and reconstruct or independently verify targets before restoring. Historical Iceberg metadata that cannot be rebound is rejected; operators must stop and drain Iceberg operations and verify unknown remote commits before restoring. These are explicit restore limitations, not automatic cross-CN or remote fencing.

The page limit bounds retained migration result payload, not scans or sorting. FK reconciliation currently scans per child and can exhibit quadratic work and repeated work after restart; the observed 256/1024-child fixtures do not establish a production time bound. Provision upgrade time and resources accordingly. Review and validate the final incremental tests and concurrency/recovery evidence before delivery.
