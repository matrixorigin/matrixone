# Boolean existence MARK through hash membership

Design revision 1.2. Owning issue: [#31829](https://github.com/matrixorigin/matrixone/issues/31829). Implementation PR: [#31848](https://github.com/matrixorigin/matrixone/pull/31848).

Projected correlated EXISTS with nullable composite keys can scan a duplicate-heavy witness relation once for every outer row. Explicit DISTINCT can reduce that work, but adds an aggregation and its own high-distinct-cardinality cost. The existing planner already identifies predicates whose evaluation can safely move to hash keys and consumers that need only Boolean existence. Preserve that information through compilation and reuse the existing membership hash table.

The ordinary nullable composite MARK fallback is necessary: a partially NULL witness does not make every nonmatching row UNKNOWN, because another component may be FALSE. Ordinary IN, NOT IN, ANY and ALL therefore keep their current row-aware semantics and shuffle eligibility.

## Required result and proof

The reported owner is projected correlated EXISTS/NOT EXISTS; the planner also uses the same totalized witness marker when it reconstructs certain correlated scalar subqueries whose projected results depend only on the outer row and whose DISTINCT or LIMIT 1 proves at most one visible value. For each outer row and complete witness relation `B`, EXISTS is TRUE iff there is some `b` for which every conjunct is TRUE; it is FALSE for an empty build or if no such row exists. NOT EXISTS is the Boolean complement. Duplicate build rows do not change that fact, and duplicate outer rows remain duplicate outputs. NULL is not an output of EXISTS. In contrast, IN, NOT IN, ANY and ALL may observe UNKNOWN and remain under their original MARK contract. A single counterexample is `(outer.a,outer.b)=(1,2)` against `(1,NULL)` and `(3,2)`: TRUE exists only on an exact non-NULL match; a global build-has-null bit alone cannot recover full nullable composite MARK semantics.

`insertMarkJoin` identifies a Boolean witness consumer by `outerPred == nil`, uses `keepRawExistential` only after the existing `existentialJoinPredicatesAreTotal` and side-effect proof, and wraps the raw marker in `istrue` (NOT EXISTS applies NOT outside that wrapper). The scalar-projection normalization calls this same helper only when LIMIT 1 or DISTINCT eliminates multirow ambiguity; its CASE returns the outer-derived value when a witness exists and NULL otherwise. Boolean membership preserves that witness condition and leaves scalar output nullability and the single-row gate with the existing planner. For a conjunction composed exclusively of supported cross-input equalities, each true witness has all components non-NULL and equal. The existing equality hash map inserts/matches those complete keys and treats a NULL component and non-reflexive float NaN as nonmatching. Therefore `found non-NULL key` equals the EXISTS result. Global NULL facts are irrelevant to this Boolean result. This proof is not a license to emit Boolean false for unflagged MARK, to drop a residual predicate, or to hash fallible, side-effecting, or volatile operands.

## Decision and boundaries

1. At planning, record an explicit MARK `existence_only`/equivalent capability on the node only for `keepRawExistential`: the consumer requires a Boolean witness (projected EXISTS/NOT EXISTS or the existing scalar-projection reconstruction) and totalizes the marker with `istrue`. This is permission for Boolean physical lowering, not a promise that a legacy loop marker is already Boolean. It is not set for IN or a generic NULL-sensitive marker. Retain the generated `istrue` wrapper. Preserve the property on `DeepCopyNode`, including prepared/execution plan copying, and generated protobuf forms. A default-false field preserves old plans and all other joins.
2. At compile time separately recognize the *post-rewrite* candidate: MARK, flagged existential source, broadcast (not right join), at least two equality keys, every conjunct an actual cross-side equality with exactly one materialized direct column on each side and no residual, expressions/operands and column indexes valid. Require a supported equality/hash domain and matching physical type metadata on corresponding operands. The initial domain is same-type signed and unsigned integer primitives with an existing direct equality/hash contract; reject unknown, mixed-domain, floats, casts/functions/parameters, null-safe equalities, residual predicates and metadata mismatches. In particular, float/NaN stays on the previous three-valued path unless already eligible for ordinary hash MARK. Extend only with an established equality/hash proof and tests. The existing planner totality proof is mandatory even though direct-column checks provide an extra post-rewrite fail-closed gate. Keep `canUseHashMarkJoinWithInputs` and `canUseShuffleHashMarkJoinWithInputs`' ordinary nullable 3VL rules intact. Use the new path only when ordinary hash MARK would reject the nullable composite, so existing safe hash paths do not change.
3. Set a separate `HashJoin.ExistenceOnly` operator contract only for that proven physical path. `validateMarkJoin` admits nullable composite keys under this explicit flag; reject incompatible types, residuals, right MARK, or shuffle. Do not fake `NotNullable` in key metadata. On nonempty lookup, emit one non-NULL Boolean per outer row equal to `z != 0 && v != 0`. On truly empty build, emit FALSE even for NULL probe. Keep existing normal MARK's TRUE/FALSE/UNKNOWN behavior unchanged. The current `HashBuild` configuration creates a membership map, no group selections and no retained build batches at publication; duplicate non-NULL keys naturally share its existing map. Disable PK preallocation for this mode because distinctness of the build input does not prove distinctness of these key columns. NULL-key tracking is unnecessary in this mode; if removed, constrain that change to the new flag. Use the same selection and construction in regular broadcast and dependent join (the latter keeps its established same-lane ownership). Pair/dependent programs, unsupported shapes, and ordinary MARK retain their established path.
4. An estimated outer cardinality of zero/one, or missing/non-finite estimate, conservatively keeps LoopJoin on this new nullable-composite path: a single probe with an early TRUE can otherwise pay for a whole map. Do not invent a general statistics framework or claim that estimates prove an upper bound; verify that the public query remains eligible; if estimates are unavailable or the behavior is materially worse, revisit this decision with evidence before delivery. The performance acceptance is comparative, not an unconditional promise for every skew/estimate.
5. Propagate the physical flag through `dupOperator`, HashJoin pipeline proto and generated code, encode and decode. MatrixOne supports shutdown upgrade only: peers in a cluster run the same binary. Therefore do not introduce a per-feature MORPC version, capability gate, older-peer fallback or stream-floor check. The additive plan/pipeline field defaults to false, so the new binary preserves the behavior of plans persisted by an older binary. Existing unrelated gates remain untouched. Test same-version local and remote encode/decode, cloning, and the default-false old-plan input.

## Costs, resources, lifecycle

Existing HashBuild consumes the complete build before publication in both paths. The existing hash route first copies `N` input rows, then builds a map of `D` non-NULL distinct keys, releases copied batches after building, and probes `P` outer rows. Expected work is O(N + P), versus up to O(N*P) for the loop; peak build memory is O(N + D), not O(D), and the 8,192-row cardinality sample can overestimate D. The map uses the existing statement/CN allocation accounting and budget; an unfavorable high-NDV input can consume more memory or fail resource admission where batch-only LoopJoin previously fit. Stats are estimates and do not provide a hard extra-memory cap or eliminate early-match regressions. These are material tradeoffs to quantify on duplicate, unique and one-outer-row workloads, including peak/budget behavior. Do not claim memory-neutral, universally bounded regressions, or that the hash optimization adds spill: broadcast builds do not have the shuffle spill fallback.

No new per-query map owner, cache, join-message type, or lifecycle is introduced. Build errors/cancellation propagate through the existing typed JoinMap dependency; hashjoin must not convert producer errors to empty build. Existing reset/free release map references exactly once, clear generation-scoped probe state, and do not mutate shared JoinMap. Verify reset/reuse, cancellation, allocation rejection, multi-consumer refcount, and no leakage/partial result. Unsupported mode combinations fail at Prepare rather than silently applying an unproved behavior. Distributed builds retain the existing broadcast ownership and full-build visibility.

## Validation and decision gates

- Planner/compile typed tests: Boolean witness source flagged only after totality proof; EXISTS, NOT EXISTS and the existing scalar-projection reconstruction flagged; IN/NOT IN/ANY/ALL never flagged; direct cross-side equality (including commutation and nested AND) selects the new broadcast operator; missing/residual/inequality/mixed-side/computed/volatile-operand/fallible-operand/diagnostic/mismatched-type shapes retain LoopJoin; non-null composite and single-key normal hash behavior unchanged; clone/prepared plan preserves flag; null-sensitive shuffle still follows old checks; dependent path selection. Confirm any outer-cardinality gate with exact low, missing, NaN, and above-gate estimates.
- HashJoin/HashBuild unit tests compare boolean membership to an independent pairwise 3VL oracle on two and three components, NULL masks, empty/all-NULL/mixed build, exact true witness after unknown, unmatched rows, duplicate witnesses and outer rows, and both input batch boundaries. Assert marker non-NULL and exact row multiplicity. Test native float NaN, signed zero and other non-integer shapes as type-gate exclusions, preserving their original path and result; separately retain existing ordinary HashJoin key-contract tests. Validate `Prepare` fail-closed invalid mode, re-preparation/reset, cancel, producer error and resource admission cleanup with allocation-account/refcount terminal evidence.
- Public SQL test: explicit expected rows for projected EXISTS, NOT EXISTS and correlated scalar DISTINCT/LIMIT 1 reconstruction in a nullable composite fixture, alongside paired IN/NOT IN UNKNOWN and empty-input controls, aliases/commutation and duplicates, plus fallible or volatile join-operand controls showing the prior path/error behavior is retained. This black-box oracle must not be the implementation's hash helper; typed physical selection separately proves reachability.
- Same-version remote encode/decode and operator cloning preserve the property, default-false older persisted plans remain valid, and one real multi-CN endpoint demonstrates identical public results/NULL state. Local account/lifecycle race tests follow the MatrixOne operator protocol.
- Compare same base/candidate binary, fixture, configuration and topology on duplicate-heavy, high-distinct and empty builds; include one early-matching probe and many probes, report N, D, P, time and peak/accounted memory. Rerun the exact public seed-0 result against the independent oracle and bracket with the control. The fix is acceptable only if the public workload improves materially and unique/early/empty behavior is understood and proportionate. Bounded deterministic tests check physical/operator work or cardinality; timing is supplementary, not a correctness oracle.


## Alternatives considered

A generic nullable-composite hash MARK using `HasNullKey` is wrong. New producer-side dedup storage needs NULL patterns, exact representative/equality semantics, a bounded high-NDV fallback, allocation ownership, cancellation and remote propagation; the existing DML `IsDedup` path is not reusable as-is because it skips NULL keys and has different semantics. A planner-inserted DISTINCT adds a general rewrite/cost surface and may cause substantial high-NDV regressions. The Boolean existential consumer carries enough information to use the existing membership owner without either extra structure. All three-valued consumers keep their prior row-aware execution.
