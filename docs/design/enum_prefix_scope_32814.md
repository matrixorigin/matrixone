# Issue #32814: narrow ENUM-prefix compatibility decision

Design author: `gpt-6.1-terra`, `max`, session `/root/enum_design_review`, 2026-11-16. Both 4.2-dev and main. This addendum supersedes the broader reject-all-new-ENUM-prefix proposal in `design-enum-prefix-index-32814.md`. It is a proposed design, not a claim that the implementation or required tests have passed; a separately versioned revision requires independent review before implementation. It does not modify a product worktree.

## Established facts

* On both pre-index-fix candidates, inline `UNIQUE(e(1))` accepted `Alpha` and `Alfred`, while ADD UNIQUE over those rows returned duplicate `A`: `42-prefix-preindexfix.*`, `main-prefix-preindexfix.*`. Their SQL used the new binary identity, so they establish historical candidate behavior, not a released identity-0 oracle. 4.2's prior inline UNIQUE hidden ENUM table could itself report ordinal overflow (`42-old-prefix-hidden.out`). MySQL 8.0.44 rejects the prefix syntax with 1089 (`mysql-enum-prefix-oracle.*`), but that does not erase MatrixOne's prior extension or justify rejecting old catalogs.
* In 4.2 WIP, ADD UNIQUE for those two rows succeeds, a behavior change from that candidate; its regular prefix bytes are ordinal-derived strings and agree between the observed inline and ADD examples (`42-enum-prefix-unique-oracle.*`, `42-enum-prefix-hidden.out`). Main WIP's tested ADD still rejects the pair (`main-enum-set-prefix-controls.*`). No successful ADD or enforced constraint should be inferred from a script that continued after the ADD error.
* Both branches' generated ADD SQL forms a prefix as `substring(column, 1, n)` (`pkg/sql/compile/util.go`, `ddl_index_algo.go`). The current marker walker (`pkg/sql/plan/enum_index_backfill.go`) recursively marks a wanted ENUM by name even inside this substring; ordinary binding supplies display text, whereas a marked direct ENUM reference supplies its stored ordinal. DML's `makeIndexPartExpr` independently constructs a prefix over a typed column. Thus suppressing or applying a mark changes expression input and can change both duplicate precheck and backfill. Merely disabling the entire descriptor does not establish byte-for-byte or SQL compatibility elsewhere.
* Main's new hidden single-key schema copies `EnumCollation`; its pre-index-fix helper did not. For identity 0 that field remains 0, but nonzero prefix schemas can differ even with markers suppressed. 4.2's pre-index-fix helper already copied `EnumEncoding` and `EnumCollation`. Its exact target baseline already supports framed ENUM member encoding with identity 0; do not classify all framed domains as new collation identities. Other changes such as identifier quoting also require their own controls.

## Narrow admission and legacy binding

1. Do not impose a blanket ENUM-prefix ban. Use the resolved final column type and actual persisted prefix length, not the original SQL spelling or table default. For a prefix part of an ENUM with `EnumCollation != 0`, reject authoring or rebuilding that affected index until its key/UNIQUE semantics and restoration are separately designed. This is a deliberately narrow new limitation on the new identity. Cover inline CREATE/constraints, CREATE INDEX, ALTER ADD and any COPY/LIKE/clone path that must create or rebuild such an index. Reject unknown/malformed identity or invalid index metadata through existing validation rather than treating it as zero. An ordinary unprefixed ENUM and non-ENUM prefixes are unaffected.
2. A genuine identity-0 ENUM prefix remains admitted as before, including framed 4.2 domains. Existing identity-0 tables/catalogs, SHOW, ordinary DML and dropping the index do not gain an admission check. An exact typed copy or recovery is not required to present a newly invented prefix exemption merely to preserve this old definition. Test old SHOW→CREATE, CREATE LIKE, DUMP/LOAD and snapshot/restore paths under both branches; main's private legacy carrier must actually restore identity 0. If a particular already-supported recovery cannot reproduce it, do not claim that path is closed until repaired or explicitly limited. These legacy cases retain known historical prefix/index inconsistencies; the design does not promise their index contents or uniqueness were correct.
3. For an identity-0 ENUM prefix in internally generated backfill or its UNIQUE precheck, preserve the target branch's pre-fix display binding at the specific `substring` occurrence, including SELECT, WHERE and GROUP BY copies. Keep the old hidden-prefix type behavior for identity 0. This aims to preserve the historical result even when it is an incorrect false duplicate; it does not certify the ADD index is physically consistent with DML. Compare real base versus candidate output and key bytes; where a new common type helper or index optimization changes an old route, preserving the marker choice alone is insufficient.
4. Mark by verified AST occurrence and role, not by column-name membership alone. A compound index can have a legacy prefix and another unprefixed ENUM/SET part or an ENUM PK; the other component and PK must keep the previously approved physical treatment. The same column name may occur once in the prefix expression and again as PK/payload: keep the occurrence distinction. Independently regenerate and validate the expected index SQL and exact `substring` shape, source binding, literal length, tenant, source/target and complete relevant schema before choosing roles. Duplicate/repeated key parts must use the actual parser/catalog rules; if a reachable form cannot be mapped unambiguously, fail that operation before publication, not silently mark every occurrence. The trust boundary remains the documented trusted in-process Go caller model, not unforgeable identity claims.
5. When an index has no physical special reference after role selection, do not attach the descriptor merely because it contains a legacy ENUM prefix; the present nonempty-reference guard would otherwise cause an artificial error. If any other physical reference remains, keep the descriptor and all source/target/schema/protocol checks. Ensure the uniqueness precheck and insert receive the correct independently verified roles; a missing eligible reference or stale metadata fails before effects. Never disable SET handling for a whole mixed index as a shortcut.
6. Validate the **final** target of an ENUM column change and its surviving index definitions, in both copy and in-place paths. A change from identity 0 to nonzero while retaining a prefix must fail atomically, including implicit/default-derived identity, rename and mixed actions. A statement that validly removes the prefix before/while changing the domain can proceed when the resulting schema has no forbidden part; follow each branch's existing action-order contract and test all accepted clause orders. Do not publish an intermediate column or hidden index on failure. An unrelated operation on an existing identity-0 prefix should retain baseline support, subject to its existing execution behavior.
7. Existing nonzero-prefix catalogs generated by prerelease/candidate builds cannot safely be assumed absent. Do not reject catalog decode, table open, SHOW, ordinary reads or dropping an index solely on this rule. Keep data and metadata intact; reject an operation that would newly build or rebuild the unsupported nonzero prefix before publication. SQL SHOW→CREATE/LIKE/dump replay of such a catalog can therefore fail explicitly; document the affected prerelease scope and do not publish a misleading successfully restorable manifest. A faithful typed restore, if needed, requires its own design; never bypass the rule merely by reproducing user SQL. Verify release/upgrade claims against the exact supported old catalog population, not an assumption that all catalog nonzero values are impossible.

This is narrower than rejecting new prefixes for identity 0 and avoids introducing a new ordinary legacy SQL/dump restriction. It is also narrower than accepting nonzero prefixes whose current duplicate checks, physical keys and hidden type have no proven common contract. It intentionally does not resolve the pre-existing legacy defect; a general prefix semantics/migration fix belongs in a separate issue. Corrections to pure/mixed SET backfill are separately scoped and may independently change a mixed-index result, as documented in the SET design.

## Evidence needed before approval and release

* Create an actual identity-0 fixture with an exact target/release base, not just new-binary identity 2. On each branch run old versus candidate SQL for inline and ADD ordinary/UNIQUE prefix indexes, `Alpha`/`Alfred`, numeric-looking labels, padded/empty members, NULL and ordinal 0. Check errors, warnings, index catalog, hidden-key bytes, DML and the actual chosen plan. On 4.2 include identity 0 with framed comma-bearing and singleton-empty member encodings. Do not call a baseline failure a success.
* Test normal whole ENUM, ENUM PK where supported, normal SET and plain UINT64, all supported nonzero identities, mixed `INDEX(e0_prefix,e2_whole)`, `INDEX(e0_prefix,s)`, and the same ENUM used as prefix and PK where admitted. Observe select/where/group AST role marks; ensure an all-legacy-prefix-only spec is safely omitted and no unmarked other physical special component is lost. Compare actual rows and exact hidden keys with base behavior and DML; require a real index plan where that is the subject of the test.
* Verify rejected nonzero inline/ADD/UNIQUE and final-schema ALTER on both branches, preserving all data, old metadata, constraints and hidden tables on error/cancel/retry. Exercise drop-prefix plus modify in both accepted orders, rename, COPY and INPLACE as reachable, default-derived identities and protocol-floor checks. Existing nonzero prefix catalog controls cover table open, SHOW, DROP and explicitly failing rebuild/replay.
* On real old identity-0 catalogs, exercise restart, LIKE, SHOW→CREATE, supported typed DUMP/LOAD and snapshots/PITR, plus unrelated ALTER/COPY. Verify domain/encoding, rows and index metadata, not only statement success. Verify quoted names and old-vs-new generated SQL separately; prove current non-prefix index and SET controls remain valid.

The real identity-0 A/B and replay matrix are open. This document is a proposed scope and mechanism, not a final implementation or release PASS.
