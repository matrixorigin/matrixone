# ENUM collation identity and inherited-default marker — revised design for #32814

**Status: independently reviewed design and release constraints.** The 4.2-dev and main implementations use branch-specific representations and require the rollout and upgrade conditions below. This revision supersedes the earlier assumption that a marker and a nonzero generic default are always mutually exclusive. Intended series: one PR per branch.

The scope covers explicit column/table COLLATE assignment. Existing identity 0 remains EqualFold; 4.2 database-default inheritance, SET and CI duplicate ENUM DDL are explicitly excluded. The amended design received independent review before implementation; later implementation findings and their validation are tracked in the associated PRs.

## Problem and evidence

The member-lookup invariant: a new ENUM with an explicitly supported column COLLATE or inherited supported explicit table COLLATE assigns/remaps text according to the target ENUM identity. Binary `A` and `a` differ; CI uses its collation weights. A source ENUM's typed ordinal 0 remains 0, NULL remains NULL, and numeric/invalid input follows each branch's existing mode and diagnostic policy. Existing ENUMs lacking persisted identity use their existing behavior; never infer their identity from a label, current server, or CREATE SQL.

The defect is reproducible on released 4.2.8 and main for literal, prepared and reordered INSERT SELECT assignments. MySQL 8.0.44 supplies an independent reference for binary case distinctions, general_ci accent equality, trailing input spaces and invalid input. A related boundary is an unsupported table default: discarding it on a non-ENUM table would let a later unqualified ADD ENUM silently fall back to legacy semantics.

Earlier 4.2 code ignored table collations it could not execute. Main `collationForName`/`ResolveDDLCollation` intentionally map `utf8mb4_0900_ai_ci` to generic general_ci for compatibility, but native 0900 ENUM equality is not general_ci. A generic numeric default therefore cannot always identify the ENUM's declared fallback.

## Contracts and representation

Each ENUM column carries explicit `enum_collation` with `0` legacy, `2` utf8mb4_bin, `3` utf8mb4_general_ci; main also admits `10` for utf8mb4 Unicode CI; `9` is reserved and rejected for ENUM until utf8mb3 conversion is implemented. Unsupported or malformed identities are fatal, never narrowed to 0. The existing member payload and 4.2 encoding remain authoritative; 4.2 stores per-column identity in the existing T_enum `types.Type.Charset` byte and propagates `plan.Type.enum_collation=15` through vector, engine, catalog, TAE and manual copies. Main similarly stores ENUM-specific identity without redefining fixed-width T_enum as a string or consuming the native byte occupied by 4.2's enum encoding. All references, index columns, generated expressions, prepared/cached plans, branch/clone and protocol fields need the same logical identity.

Add the same **string** `enum_unsupported_default` to 4.2 and main `api.SchemaExtra` tag 23 and `plan.TableDef` tag 43, available at the reviewed bases. Recheck after rebase and generate both protobufs. It stores the parsed original table-level collation name, or the raw server fallback name actually consulted when the database has no stored default, when the table's effective ENUM inheritance cannot be represented by the ENUM identities admitted on that branch. Preserve the parsed identifier; use case-insensitive lookup and `sqlquote.Ident` on display. Empty means no such known unsupported ENUM default, not proof of a historical declaration. A string is necessary to render the declaration; a bool cannot faithfully replay it. Do not add an arbitrary new name limit beyond existing parser/request/catalog bounds; validate malformed catalog metadata before producing SQL or narrowing to an identity.

The generic table charset and the ENUM marker are **independent**:

| State | 4.2 | main | ENUM fallback when no explicit supported column COLLATE |
| --- | --- | --- | --- |
| generic 0, marker empty | historical/unknown | historical/unknown | preserve existing branch behavior; no historical inference |
| generic supported id, marker empty | explicit supported table default | supported exact default on newly authored strict-exact tables; historical id 3 may be a normalized alias | use the branch's recorded identity and historical compatibility behavior without claiming the original spelling |
| generic 0, marker name | explicit table default unsupported for 4.2 ENUM | possible bridged 4.2 split state, outside current supported upgrade | fail closed for unqualified ENUM; explicit supported column COLLATE wins |
| generic 3, marker `utf8mb4_0900_ai_ci` | not authored by the scoped 4.2 implementation | native main generic compatibility alias plus distinct ENUM restriction | fail closed for an unqualified ENUM; do not use generic general_ci |

More generally, main may have a nonzero generic default plus a marker if generic DDL intentionally uses an alias which is not semantically exact for ENUM. Thus `marker != empty => default_charset == 0` is a **4.2 authoring invariant only**, not a cross-branch wire invariant. Validate a main nonzero/marker pair against the actual generic compatibility resolver and accepted source provenance; reject impossible combinations, unsupported/corrupt metadata or an unknown revision rather than guessing. Preserve independent physical key-format/revision semantics (main `alter_table_charset.go:88–94` can retain revision 1 for V1 unique keys even with a legacy default).

The marker owns only ENUM inheritance. It does not retroactively rewrite existing ENUM or non-ENUM columns, and it does not imply a new generic text collation. For a new 4.2 non-ENUM table declared with an unsupported table COLLATE, retain marker and keep generic default 0; CREATE still succeeds. For a table with ENUMs, a supported explicit column COLLATE is checked first and overrides the marker; without it, reject before any metadata/data commit. This conservative nonempty-marker rejection also applies on main to a possible future bridged 4.2 Unicode marker even if main has a UCA4 implementation; automatic resolution there requires bridge design re-review. A column CHARSET alone does not prove an exact supported collation and does not bypass an unsupported marker. Explicit incompatible ENUM column options or unsupported column collation fail with the appropriate existing invalid/not-supported error. On 4.2, an incompatible table charset/collation pair fails when the final schema contains an ENUM. Ordinary tables retain the historical ignored table CHARSET behavior while an explicit COLLATE is recorded as the later ENUM default or unsupported marker. IGNORE never masks invalid schema metadata.

## Exact name admission

Resolve a column's original COLLATE spelling against a strict ENUM-specific mapping **before** generic aliasing. Admit only names whose implemented equality, padding, repertoire and version actually match; e.g. utf8mb4_bin, utf8mb4_general_ci and main's exact UCA4 utf8mb4_unicode_ci. All utf8/utf8mb3 ENUM collations are rejected until their three-byte conversion semantics are implemented. Explicit `utf8mb4_0900_ai_ci` and `utf8mb4_0900_bin` are rejected for ENUM until those exact ENUM identities and all boundaries are implemented; never map them to general_ci or legacy bin. Existing generic CHAR/VARCHAR/TEXT admission and 0900 compatibility aliases remain unchanged.

For a table COLLATE, preserve both outcomes: generic resolution for ordinary text and strict ENUM resolution. If the name is generic-only or unsupported for ENUM, retain the original name in the marker even when there are no ENUM columns, then reject only an ENUM that inherits it. A supported explicit column COLLATE may override it. On main, this means a new non-ENUM `COLLATE=utf8mb4_0900_ai_ci` table has generic id 3 plus marker 0900; a later unqualified ADD ENUM fails rather than silently inheriting id 3.

Historical metadata cannot tell whether an existing generic id 3 originated from general_ci or a 0900 compatibility spelling; preserve that stored compatibility behavior and do not assert 0900 equivalence. In particular, main `NormalizeDatabaseDefaults` in `pkg/sql/plan/database_defaults.go:81–128` writes normalized id/revision to `mo_database_defaults` and derives the name from the id. Database-level 0900 alias provenance is not recoverable by this table marker, including a newly authored DB default which is normalized before table creation. The coordinating agent explicitly adopted this scoped limitation: retain stored id-3 behavior, disclose it, and do not claim correct native 0900 ENUM inheritance through database defaults. Complete fail-closed database-level behavior requires separate durable DB provenance or a broader rule requiring explicit supported ENUM column/table COLLATE whenever the inherited id is ambiguous. When `GetDatabaseDefaults` is nil/version 0 and `tableDefaultCharset` actually reads the raw `collation_server` name (`build_util.go:744–759`), an unsupported exact ENUM spelling such as 0900 **does** produce the table marker and unqualified ENUM fails; if a stored DB default exists, do not consult the server or manufacture the missing DB name from id 3.

## DDL state transitions and atomicity

CREATE resolves a recognized explicit table default to its generic id/revision plus either empty marker (exact ENUM identity) or original-name marker (unsupported ENUM identity). On 4.2 an unsupported table default gives `(0,0,name)`; an existing table with zero/empty remains legacy. An ENUM with explicit supported column COLLATE always uses that column identity after validating charset compatibility, regardless of marker. Without explicit column COLLATE, nonempty marker gives a not-supported error; otherwise use the supported recorded table identity or the historical fallback described above. Apply the rule to parsed and generated columns, CTAS and ADD/MODIFY/CHANGE, not only an AST prescan that misses derived columns. A newly created supported 4.2 table default is persisted for later ADD. Old tables whose declarations were discarded cannot be repaired automatically; explicit ALTER or column COLLATE is required to opt in.

For main ALTER, compute the final table default from `alterTableCharsetDefaultOptions` and resolve both generic and strict ENUM outcomes **before algorithm selection and before binding any ADD/MODIFY**, independent of the textual order of clauses, consistent with current COPY/INPLACE behavior. Form the complete target tuple on a private evolving TableDef:

* supported exact new default -> new generic id/revision and clear marker;
* generic-compatible but unsupported ENUM name such as 0900 -> generic compatibility id/revision plus that exact-name marker;
* no default action -> retain the entire original tuple;
* unsupported or invalid requested generic default -> fail without mutation.

An explicit `COLLATE=utf8mb4_general_ci` replacing main `(3,0,0900)` is a **marker-only change** even though generic id/revision remain `(3,0)`. It must still publish a replacement schema. Include marker equality in `build_ddl.go:7604`'s change decision; carry the tuple in both INPLACE ReplaceDef and COPY and in all transaction preimages, cache/TAE replacements, and rollback paths (`disttae/txn_table.go:1994,2018,2127`). The new tuple and same-statement column actions share one transactional publication. Thus `ALTER ... COLLATE=general_ci, ADD e ENUM(...)` inherits general_ci regardless of clause order, while `ALTER ... COLLATE=0900, ADD e ENUM(...)` fails for unqualified e and leaves both old default and schema unchanged; an explicitly supported column COLLATE succeeds. Existing columns retain their own identities on a default-only change.

On main a generic-admitted 0900 default-only ALTER must succeed and publish generic id 3 plus marker if it has no affected unqualified ENUM action; a same-statement ADD with an explicitly supported column COLLATE also succeeds. Reject the unqualified ENUM action, not the otherwise supported generic default. On 4.2 the default-only ALTER implementation may reject an unsupported table-default transition before mutation rather than implement it in this PR, provided it never discards an existing marker. Table collation conversion has different semantics from changing the default: main `convertAlterTableCharacterColumns` currently handles only CHAR/VARCHAR/TEXT. Reject CONVERT that would require ENUM conversion until target-member remap, index rebuild, error/rollback and both branch paths are implemented. On 4.2, reject charset-only ALTER and CONVERT rather than report a historical no-op as a default change. Non-charset ALTER placeholders such as ENABLE/DISABLE KEYS retain their historical dispatch; their parsed kind must survive SQL formatting and reparse, including partition children. Non-ENUM MODIFY/CHANGE charset handling retains its previous failure. Any failed mixed ALTER must leave the original marker, default, column set and rows intact.

## Replay, SHOW and clone

4.2 SHOW CREATE must emit a known marker as the original safely quoted table COLLATE, and each explicitly collated ENUM column must emit its own collation. CREATE TABLE LIKE and other internal clone/copy paths carry the original tuple and per-column ENUM identity directly through trusted typed metadata; do not infer from `rel_createsql`. A legacy-zero ENUM combined with an unsupported marker has no ordinary SQL spelling for legacy EqualFold: if such a state is reachable, public SQL replay must fail clearly or use an explicitly designed legacy replay carrier; it must not silently select the table marker. Do not allow default ALTER to create an unrepresentable state while claiming SHOW replay works.

On main, a native `(generic 3, marker 0900)` state is publicly replayable only if SHOW emits the original `COLLATE=utf8mb4_0900_ai_ci`, the new parser reconstructs both generic id 3 and marker, and every ENUM column's actual identity is explicit. Existing identity 0 is rendered with the reserved ENUM-only `__mo_enum_legacy_main_v1` spelling, which is not a MySQL collation. For an ordinary table with generic default 0, empty marker and a visible legacy ENUM, SHOW also emits `__mo_table_legacy_main_v1` so a later unqualified ADD has the same default. The table carrier requires a final ordinary non-temporary schema with a visible legacy ENUM and no CHARACTER SET, is used only on CREATE/replay, is rejected for ALTER and is not admitted as a generic database/session/column collation; the column carrier rejects CHARACTER SET and is rejected on non-ENUM columns. A user may explicitly request it; it is not evidence of source version or authorization. LIKE must bind the preserved default before any default/generated expressions, while retaining existing legacy text normalization. The schema-hash representation for existing legacy schemas remains unchanged; newly authored nonzero ENUM identities remain distinguishable. These spellings are MatrixOne-specific and are not portable collations. In particular, 4.2.8 can silently ignore unknown COLLATE names and subsequently use legacy semantics, so main-to-older-4.2 SQL replay is not safe and is not supported by this change. 4.2 keeps its existing SQL spelling and branch-specific legacy behavior. Legacy tables without a visible legacy ENUM retain existing generic SHOW/LIKE normalization, so future ADD after replay can differ; external table grammar cannot carry the table default. Do not claim those boundaries are fully replayed.

A 4.2-bridged `(generic 0, marker name)` pair cannot in general be represented by ordinary main CREATE TABLE: emitting `COLLATE=name` changes the generic default; omitting it loses the marker. The current `normalizeLegacyTextCollationForCreateLike` also changes generic 0 to utf8mb4_bin, and `effectiveTableCharsetForShowCreate` may choose a display default. **Minimum safe restriction:** return a clear not-supported error for public SHOW CREATE and CREATE TABLE LIKE on such split-state tables, before publishing a different schema. Ordinary data access is not rejected merely because SHOW/LIKE cannot reproduce the metadata. Internal backup/restore must use a typed representation or fail closed, never silently normalize the pair.

A future fuller bridge can support LIKE/copy using a trusted typed replay carrier for the source generic default, revision, marker and every affected column identity. Apply this carrier before table/column binding, generated/default expression binding and schema publication; a generated SQL skeleton is only a parser aid. Verify source and resulting typed metadata match before commit, and preserve this pair through snapshot and rollback. Until the carrier exists, the restriction is explicit and limited to nonrepresentable split states. New native main states must not be rejected if ordinary SQL can faithfully reconstruct them.

### Legacy CRC32 expressions on main

When an unchanged legacy CRC32(JSON) DEFAULT or GENERATED expression is carried across an ENUM domain change, preserve its old computation only after authenticating the original assignment wrapper, ordered domain, overload and unchanged SQL source. Rebind the current source without evaluation and compare the complete typed tree and column scope. Normalize only the newly inserted JSON-to-TEXT cast paired with the corresponding old JSON CRC call and the non-execution column table labels. Restrict the proof to function, column, literal, list and target-type nodes; unproven forms fail closed. Do not remove an explicitly authored conversion. On proof, bind a new ENUM assignment around a deep copy of the old computation. Preserve same-domain trees; cross ENUM/non-ENUM conversions, folded values without a recoverable source and other unprovable shapes fail before publication. Apply persisted-expression authoring and protocol gates. SQL DUMP/replay must independently prove that the stored expression can be reproduced, or reject before publishing the manifest.

## DUMP manifest and replay boundary

`DUMP TABLE` must not reuse `rel_createsql` for an eligible ordinary table: 4.2 could persist a spelling whose table or ENUM identity differs from its effective schema. In particular, released 4.2 could persist an ENUM as identity 0 despite a binary COLLATE in its original CREATE SQL. Reconstruct the manifest DDL from the typed table definition, retaining each ENUM identity and its representable table default. On main, normalize legacy text columns for replay without replacing an eligible legacy ENUM table default; if a table requiring this reconstruction cannot be faithfully reconstructed, fail before publishing a manifest. Keep the historical schema hash for unambiguous domains. The legacy hash renderer conflated ENUM backslashes with control characters, replaced invalid UTF-8 with the replacement rune, and lowercased SET members. Exact-domain classification must cover both sides of these collisions, including Unicode lowercase mappings outside simple case folding. For affected domains, include exact typed member bytes in the hash; new archives remain replayable, while old ambiguous archives must be restored on their original compatible release and then upgraded. The old text-hash fallback cannot distinguish an ignored old COLLATE from newly authored metadata, so DUMP and LOAD reject identity- or framed-domain-bearing tables when only that fallback is available. The optional manifest CREATE SQL is omitted for unverified legacy fallback schemas, mode-sensitive syntax, explicit non-NULL defaults, generated or ON UPDATE expressions, and CHECK constraints when replay context cannot be proved. Recreate such targets under an equivalent creation context, including SQL mode. The historical hash includes default SQL rather than the evaluated default value, so it does not prove that separately recreated defaults are equivalent. For an existing ordinary-table archive, recreate the old effective schema (including omitting options 4.2 ignored) and let LOAD verify the remaining hashed schema. If an old text-hash archive cannot match a safely reconstructed target, restore on the original compatible release and upgrade the restored data; do not bypass the fingerprint. Validate real DUMP, manifest CREATE, LOAD and subsequent writes; do not infer these from SHOW alone.

The main table replay carrier is intentionally emitted only while an ordinary G0 table still has a visible legacy ENUM. A G0 table without such a column, including one after dropping the last legacy ENUM, retains the earlier generic SHOW/LIKE normalization and may have a different future ADD default after SQL replay. All 4.2 SQL exports, including those from the new 4.2 branch, lack the main-specific replay carriers; replaying them on main needs version-aware translation or same-branch restoration and is outside the stopped on-disk upgrade tested here. Native Unicode markers, aliases, and explicit empty charset/collation must be validated before persisting or replaying ENUM metadata. On 4.2 an explicit empty table charset is rejected when the final schema contains ENUM; ordinary tables retain their historically ignored table charset behavior. Repeated table charset options use the final option.

## ENUM index backfill and uniqueness

> The per-index compatibility boundary in `enum_index_mutation_32814.md`
> supersedes unconditional statements in this section: legacy-only indexes
> retain their branch's historical behavior, while indexes depending on the
> new nonzero ENUM identity follow the reviewed physical-key contract.

An index populated from existing rows must use the same physical ENUM ordinals and complete domain as later DML, including error ordinal 0, valid empty members and NULL. For the internal SQL generated by the owning index build, carry a statement-local trusted descriptor of the exact generated statement, source relation and ENUM key/primary-key references. Correctly escape legal identifiers. Parsing must yield exactly one statement; validate its complete relevant AST shape for the generated operation, and its bound current tenant, source/target relations and ENUM types. A name match or generic internal-executor identity alone does not authorize the binding, and mismatch fails closed. Bind only the proven direct references as typed ENUM storage; do not change user SQL, SET or unrelated expressions. Apply the same physical-key semantics to UNIQUE duplicate prechecks and backfill before using `SkipPkDedup`. Preserve the original transaction, account, cancellation and index locks, and discard the descriptor after each statement.

On main, hidden typed ENUM index keys and ENUM primary-key payloads retain the complete member domain and ENUM collation identity. Do not change non-ENUM hidden schemas or introduce a new durable key format. Indexes populated by older code may already contain display-encoded or misidentified keys, including UNIQUE indexes that failed to enforce their intended domain. This change does not repair them automatically: identify and rebuild affected indexes from the base table with fixed code; resolve any true duplicates before a UNIQUE rebuild. The scope and safe repair procedure for supported released catalogs must be established before release.

Validate inline-index DML against ADD INDEX after existing rows, subsequent writes and restart; compare actual selected index reads with scans for binary `A`/`a`, case-insensitive domains, 0, legal empty and NULL, single/composite and unique/nonunique keys. Verify failure atomicity, statement-marker isolation, main ENUM primary-key payloads and 4.2's rejected ENUM primary-key control.

## Runtime lookup and migration

Keep existing function IDs and legacy two-/three-argument meanings. New conversions use an unambiguous four-argument `(payload,value,encoding,identity)` overload, or an equivalently reviewed branch-specific overload that cannot collide with the existing internal boolean form. Validate/decode constant domain and identity at most once per batch; dynamic metadata retains row/NULL/selection behavior. All literal, 4.2 IGNORE fast path, prepared, UPDATE, INSERT SELECT, default, LOAD/CSV validation and append, Hive, Parquet and branch import paths must use the target identity while preserving their existing branch-specific strict/IGNORE/error/warning rules. In particular, existing external input validation may remain strict rather than inheriting SQL INSERT IGNORE behavior.

For identity 0, keep each branch's existing EqualFold, whitespace and numeric rules exactly. For new identities, use the chosen collation's **non-padding** equivalence. If input ends with ASCII U+0020, first compare its original bytes only with stored member labels that themselves actually end with ASCII U+0020; the first equivalent member in declaration order wins. This is MatrixOne's padded-member extension and has precedence over the next pass. If that restricted pass fails, remove trailing ASCII U+0020 from the input and search all original members in declaration order. If the input has no trailing ASCII spaces, search all original members once. Never trim stored members or strip their trailing collation weights. This preserves the existing `['a ', 'a']` cases while implementing MySQL's normal trailing-ASCII-space input behavior; pre-existing padded member declarations are an explicit MatrixOne compatibility extension. For utf8mb4_bin the comparison is case-sensitive bytes; unmatched input never falls back to case folding. For general_ci use pinned MySQL weights, including malformed-byte rules, with the same non-padding key in linear and indexed paths; A and á match a. For utf8mb4 UCA4, form each comparison key from the valid UTF-8 prefix before the first malformed byte, as independently observed in MySQL; keep the original bytes for padding and numeric fallback. Use the non-padding primary weight stream, including the pinned U+FFFF correction; `Domain.Key`'s PAD SPACE encoding is not a member lookup key. A trailing NBSP may have the space weight but is not ASCII U+0020: `a` plus NBSP must not become `a` merely because the padded key strips trailing weights. Build indexes from untrimmed member keys and retain a separate eligible padded-member index; apply the same restricted-raw-first and trimmed-input-second passes as the linear path. Test these rules against an independent MySQL oracle where MySQL admits the same declarations, and separately preserve MO padded-domain behavior. The current thresholds are 64 rows and 8 labels; 4.2 counts decoded members, not commas in framed payloads. No new long-lived cache, goroutine or shared mutable state is needed.

On a proven typed source, same identity and equivalent ordered domain may transfer raw ordinals; otherwise decode source label and look up in the target while preserving ordinal 0 independently of a valid empty label. Apply the appropriate non-padding definition comparator, rather than an indiscriminate padded value key, to that optimization. Existing legacy-domain shortcuts keep their old rules. Update optimizer/type equality, provenance, hidden index columns and ALTER no-op checks; typed ordinal preservation must not cross DISTINCT/set operations where visible values are not injective.

#32808's `distinctSpecialStorage.canonicalValue` uses `_enum_display_to_index` to recover the first **byte-exact SOURCE-domain** label from a visible DISTINCT output, then preserves the source type in `value.Typ`; `bind_insert.go` subsequently applies destination `funcCastForEnumType`. Preserve that exact recovery and its existing three-argument overload: folding it using source or destination collation can collapse visible `A`/`a`. Preserve source EnumCollation/encoding through `boundary.enumType`, `sameTypeMemberDomain`, typed copies and projection provenance; only the subsequent destination assignment applies target collation. A reversibility optimization is allowed only with a proven injective display-to-storage relation; conservative false remains safe.

A user may reauthor a 4.2 legacy column via explicit ALTER MODIFY with the same ordered domain and supported COLLATE, preserving existing stored ordinals while committing new metadata and updating dependent index metadata; changed domains require checked target remap and transaction rollback on error.

Lookup remains O(rows × members) for linear batches and expected O(members + rows), plus key construction, for eligible constant batches. The per-batch index is bounded by existing member-count, input and memory budgets and owns no long-lived global state. Retain the existing allowance for ENUM payloads larger than 64 KiB. Compare same-toolchain pre/post allocations and throughput against recorded baselines; investigate a reproducible regression of 10% or more on an unchanged legacy path and correct it or record an approved measured tradeoff.

## System bootstrap, branch transfer and CDC

Main bootstraps system tables before the distributed catalog authoring floor
opens. The built-in system ENUM columns therefore use the MatrixOne legacy
carrier explicitly and retain identity 0. Only trusted internal executor DDL
for a system database omits a marker derived solely from the raw server
default; an explicit table COLLATE or a nonzero ENUM identity still requires
the ordinary authoring floor. Ordinary SQL in a system database and internal
DDL in a user database retain normal server-default handling. Test a 0900
server fallback, explicit options, initial system bootstrap and tenant setup.

Main DATA BRANCH LCA probes must project physical ENUM ordinals as unsigned
integers, not reconstruct them from display labels. Endpoint schema admission
includes the ENUM collation. OUTPUT AS keeps the exact source domain and
transfers stored ordinals through an internal typed expression, including zero,
which ordinary SQL numeric assignment must not accept in strict mode. The
background executor borrows that AST without freeing it; caller cancellation,
planning failure and transaction rules remain in force. Other branch apply
paths must preserve typed ordinals or fail before publishing partial effects.

CDC SQL sinks write ENUM ordinals as unquoted numbers: an ENUM label can equal
the text form of a different ordinal. Since an ordinal-zero error value cannot
be safely recreated by an ordinary strict SQL sink, INSERT and DELETE both
fail explicitly for that value instead of guessing or silently changing data.
Main publishes known ENUM collation identity in the existing metadata
classifier while keeping legacy identity 0 as NULL. A main source with a
known ENUM identity requires fenced target admission and exact member order and
collation verification; a target that reports no collation fails closed. Old
target versions and older persisted metadata views that cannot report the
identity are not silently treated as matching. On 4.2-dev, target schema
verification is not yet available: operators must supply a target that
supports the same identity and has exactly the same members in the same order,
and fence incompatible consumers, including older 4.2 binaries. `CREATE TABLE
IF NOT EXISTS` is not proof of this condition. SQL replay across incompatible
versions remains subject to the release hold below.

## Persistence, deployment and upgrade

The marker and generic default must survive `engine.PlanTableDefToDefs` / `engine/types.go`, `api.CloneExtra`, `disttae/cache/catalog.go`, `disttae/txn_table.go`, `plan/deepcopy.go`, `tae/catalog/table.go`'s manually reconstructed SchemaExtra, TAE checkpoint serialization/recovery, metadata-only ALTER and transaction rollback. Manual SchemaExtra/TableDef copies must preserve both `DefaultCharset` and the marker. Persist the full replacement atomically; failed ALTER cannot leak one half of the tuple.

The supported 4.2 deployment contract is the stopped-cluster procedure already required by `docs/design/enum_member_encoding_42.md`: back up, stop and drain old CNs/workers and incompatible CDC/subscription consumers, then start the new version. Old binaries must not rejoin or reopen a catalog once nonzero ENUM identity or marker metadata has been written; rollback requires the pre-upgrade backup or an explicit compatible export/recreation. MORPC 12 on 4.2 and 135 on main are the next free slots at the reviewed bases, subject to reallocation on rebase. Gate creation/replacement of the marker itself, including a table with no ENUM, and marker-dependent DDL, copy/replay, schema publication, new ENUM authoring/execution and overloads. A lowered floor makes new binaries fail closed on these feature paths; legacy tables without marker and identity remain unchanged. On main, include persisted-expression read/authoring floors and remote on-stream confirmation, as well as metadata authoring/admission. These are supplemental gates, not a claim of cluster-wide enforcement: the 4.2 runtime protocol is service-local, may initialize to latest, and old binaries cannot reject fields they do not understand. The deployment controller must enforce the stopped procedure and old-node fence.

Main's documented `docs/guides/upgrade-4.2-to-main.md` covers stopped upgrades from **released** 4.2 versions, with existing data and snapshots. Release v4.2.8 and its hotfix have no ENUM plan tag 8 and use a reserved native type byte; exercise real release fixtures. Post-#32723 4.2-dev data is **not** presently a supported main upgrade: its ENUM encoding uses plan tag 8, native byte 3 and marshaled offset 6, conflicting with main charset/revision interpretation and validation. The new marker has a further loss risk if main does not know the API/plan field or a manual SchemaExtra reconstruction drops it.

Before **releasing** any future 4.2 release that can author #32723 framing or the marker, deliver the version-aware main bridge and snapshot/replay support, unless the existing release-compatibility contract is separately authorized to change. Main's guide covers released 4.2 data and snapshots; a temporary development-time rejection is safe but does not satisfy that release promise. The bridge must preserve marker independently of generic default, port/validate the framed decoder, disambiguate T_enum native/20-byte type encoding using authoritative source-version provenance, translate persisted 4.2 plan tag 8 and typed expressions, and handle restart, snapshots and restore. Adding marker fields to main now prevents one field from being silently ignored, but does not by itself solve framed ENUM compatibility or authorize claims of post-#32723 upgrade support.

The future bridge must also address the **supported** 4.2 table defaults 2/3: 4.2 uses `default_charset` for ENUM inheritance, while its base `build_alter_add_column.go:60–65` ignores that default for ADD VARCHAR. Main uses the same field as a generic text default, so blindly carrying 3 over would change the behavior of subsequently added non-ENUM columns. Preserve the split through separately typed ENUM-default provenance, or explicitly authorize and validate that future-column behavior change; do not turn supported default 2/3 into an unsupported marker that causes new ENUM additions to fail. The bridge's own design review and upgrade/snapshot tests must close this before the release hold is lifted.
