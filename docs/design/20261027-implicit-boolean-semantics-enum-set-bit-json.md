## 1. Problem, evidence, and invariants

### 1.1 Observed defects (facts, with evidence)

- **#30931 (ungrouped truth).** On the reported base `d4c37f4d` and the assigned base `5fe08a3307`, `IF(e,1,0)`/`IF(s,1,0)` return 0 for nonzero ordinals/masks, and `WHERE e`/`WHERE s`/`e AND 1` fail with `ERROR 20301 "invalid input: 'a' is not a valid bool expression"`, while `e+0`/`s+0`/`IF(e+0,1,0)` are correct.
- **#30931 (grouped).** Above `GROUP BY`, truth re-read display text; for declarations whose ordinal-0 sentinel and a valid member display identically (`ENUM('')`, `SET('')`), grouped truth cannot distinguish them, and base silently merges rows MySQL keeps separate (recorded INSERT..GROUP BY 2 -> MySQL duplicate-key 1062).
- **#30930.** `b'1'`/`b'0'` BIT value literals evaluate through the raw-byte text truth path instead of their numeric payload; BIT columns stay with #30922.
- **#30932.** `IF`/`CASE WHEN` reject JSON scalar conditions MySQL accepts; the table-path CASE evaluator cast branch condition vectors to `[]bool` (panic/error when a T_json condition vector reached it).
- **Probe-confirmed preserved-binary defects** (revision-2 receipts, the pre-repair red baseline): F1 - `WITH ROLLUP` merges the empty-label groups and returns IF=0 on all rollup rows incl. active groups (non-rollup control correct 1/0/1); F2 - `WHERE j`, `j AND 1`, `CAST(j AS BOOL)`, `j IS TRUE` error 20203 [JSON -> BOOL] on non-ParseBool strings while IF/CASE return the conditional vector; F4 - `IF(CAST('"1e309"' AS JSON),1,0)` returns 0 (overflow folded to false); F5 - cross-block `IF(v,1,0)` returns 0 for the ordinal-1 ''-group (same-block truth 1) and 1 for 'a'.

### 1.2 Invariant (revision 4; Section 7 durable ownership corrected in revision 5)

> In a MySQL-compatible boolean context, the truth of an ENUM/SET/BIT-literal/JSON
> operand derives from its **stored payload**, never from display text:
> - ENUM: stored ordinal != 0; SET: stored bitmask != 0;
> - BIT value literal: uint64 payload != 0 (genuine strings keep raw-byte text truth);
> - JSON **in IF and CASE WHEN conditions only** (#30932 scope): conditional numeric
>   truth - numbers compare against zero by exact stored value, strings use the
>   shared decimal-prefix scanner with saturating overflow BELOW the
>   extension-dispatch boundary (Section 8/D9), JSON null and SQL NULL select the
>   ELSE branch;
> - JSON consumers outside IF/CASE conditions keep their pre-change behavior
>   cell-for-cell, and the strict `jsonScalarToBool` kernel remains the JSON
>   BOOL-target cast path;
> - the BOOL-target explicit CAST of ENUM/SET/BIT is defined by this design as
>   storage-payload truth (MySQL defines no BOOL cast target; Section 3);
> - the invariant survives the grouping boundary with the D6 activation contract
>   and the D10 materialized-boundary contract;
> - the invariant holds on SELECT planning AND on every persisted-expression
>   authoring/evaluation path (generated columns, defaults, CHECK, ON UPDATE),
>   which reach execution through catalog metadata, not streamed plans (Section 7);
> - every new admission, rewrite, kernel branch, and the grouping-identity
>   construction itself are gated on one statement compatibility scalar resolved
>   from the session's `MatrixOneNativeMode` flag and carried on BOTH owners -
>   the BindContext (SELECT path) AND the `ddlExpressionContext`-attached setting
>   (DDL expression binders) - so MatrixOne-native sessions keep pre-change
>   behavior everywhere (Section 3.3/D11).

### 1.3 Goals, non-goals, assumptions

**Goals.** Restore MySQL boolean semantics for the three members per the issue acceptance checklist; keep JSON strictness, JSON outside IF/CASE, and text semantics unchanged; keep ENUM/SET display output unchanged; define BOOL-target casts coherently; keep native-mode behavior byte-identical to base on every authoring and evaluation path; keep remote and persisted expression consumers safe across versions.

**Non-goals.** BIT columns (#30922); conditional JSON semantics outside IF/CASE; changing native-mode behavior; grouping numeric consumers; MySQL-parity for cross-block truth over ambiguous declarations (zone 3 fails closed; R3 ordinal-carrying materialization is the recorded future generalization); an EXPLAIN surface for hidden keys.

**Assumptions (verified).** ENUM/SET bind as a display call over the stored expression; SET storage is physical `uint64`, ENUM storage `T_enum`; no wire/catalog/persistence format changes are needed; one new MORPC protocol slot serves BOTH the remote-pipeline floor and the persisted-expression authoring/read requirements because both derive from the shared `plan.RequiredRemoteExpressionFeatures` walk (persisted_ip.go:95-181); the durable cross-version guarantee for catalog expressions is carried by the PRE-EXISTING HAKeeper admission floor - raised automatically at upgrade to the new binary's `MORPCLatestVersion` (which contains the minted slot), committed in replicated state and monotonic; a below-floor binary that JOINS or RESTARTS against the raised floor is fail-closed at admission/start (ingress readiness opens only at admission completion), a CN already serving when the floor raises keeps its established sessions, and no per-expression read-gate rejection exists for a reader compiled before this fix (a reader lacking the new feature detector computes requirement 0 and passes, Section 7/R2) - so while a below-floor heartbeat stays FRESH the cluster-wide authoring closure holds automatically, but HEARTBEAT EXPIRY IS NOT A SAFETY BOUNDARY: releasing the pending activation on expiry carries no shutdown evidence, and the supported rollout prerequisite is the VERIFIED process retirement (shutdown + session drain + released listeners) of every below-floor CN before authoring new-operand definitions - with no per-definition floor persisted for generated columns/defaults/CHECK/ON UPDATE (view/CTAS targets persist their own per-definition requirement through the existing mechanism, which inherits the minted mapping from the same feature->version table); the planner can read the session's native-mode flag (`builder.compCtx.GetProcess()` -> `GetSessionInfo().MatrixOneNativeMode`, and for DDL binders the same flag through the CompilerContext inside `ddlExpressionContext`).

## 3. Representation, admission, and the coercion matrix (D7 + D11)

### 3.1 One matrix: type x context x compatibility mode

| Operand (MySQL mode) | IF/CASE condition | WHERE/HAVING/ON predicate | AND/OR/XOR/NOT/IS TRUE/IS FALSE/IN | Explicit `CAST ... AS BOOL` |
| --- | --- | --- | --- | --- |
| ENUM (display or direct) | storage-truth ordinal != 0 (sibling-slot routed above GROUP BY; D6 joints) | storage-truth ordinal | storage-truth ordinal | storage-truth ordinal: MySQL has no BOOL cast target, so this design defines the BOOL-target cast to match the boolean contract; native mode reverts to prior behavior |
| SET (display or direct) | storage bitmap != 0 | storage bitmap | storage bitmap | storage bitmap != 0 (same rationale and mode gate) |
| BIT value literal (`b'...'`) | payload != 0 | payload != 0 | payload != 0 | payload semantics for the BOOL target; other cast targets keep prior numeric-cast semantics |
| JSON scalar | **conditional kernel (D9)**: numbers vs 0 by exact stored value; strings via the shared decimal-prefix scanner with saturating overflow, NO extension dispatch (hex/binary/octal and NaN/Inf-prefixed text have no numeric prefix -> false); true literal true; false/''/'abc'/'true' string variants false; JSON null and SQL NULL -> ELSE | **pre-change behavior** (preserved-binary strict [JSON -> BOOL] cast errors on non-ParseBool values, probe 1; base-parity is a planned F2 oracle) | **pre-change behavior** (not yet probed on base; F2 oracle) | **strict kernel** (preserved-binary path is `jsonScalarToBool`, probe 1; admission parity with base is an F2 oracle) |
| VARCHAR/text | existing numeric-prefix text truth (mode-dispatched today) | unchanged | unchanged | unchanged (including the extension-candidate hex/binary/octal and NaN/Inf behavior of general string->numeric casts, which D9 does not alter) |

**Where the matrix is enforced.** Admission sites: `iffCheck`, CASE condition typing, the boolean-argument implicit-coercion rules, and the boolean-context rewrite in `appendCastBeforeExprWithOverload` (base_binder.go:12044-12052). These sites are shared by ALL binders - SELECT planning, generated columns, defaults, CHECK, ON UPDATE - because standalone DDL binders call the same `baseBindExpr` binding path with a context they own (Section 3.3). One matrix therefore governs every authoring and evaluation surface.

### 3.2 Truth kernels

`IffConditionTruthyAt(vec, row, mode)` remains the single per-row evaluation point; the T_json branch calls the conditional kernel (D9) **only through IF/CASE condition positions** and consults the mode; the colexec `EvalCase` keeps the per-row JSON branch (protected remotely by D8's pipeline floor and in catalog-bound expressions by D8's persisted-expression gates plus the HAKeeper cluster admission floor, Section 7); text keeps the existing `parseBytesToFloat` prefix truth with its existing mode dispatch - unchanged.

### 3.3 D11 mode propagation: both carriers (revision 4, fixes H2)

**Verified owner of durable cross-version safety (P2 + R1 + R2 corrections); all pre-existing, none added by this design.**

- **No per-definition floor in table expression metadata.** `GeneratedCol`/`Default`/`OnUpdate` carry only the expression and origin string (proto/plan.proto:470-487, no required-floor field); every reader recomputes the requirement from its OWN compiled feature walk over the persisted expression and compares it against its local deployment protocol - the reader's `MOProtocolVersion` plus the `PersistedExpressionProtocolFloor` runtime global published from the admission snapshot (`persistedProtocolRuntimeAllows`, persisted_ip.go:328-340; read gate `RequirePersistedProtocolVersion`, :223-246). R2 consequence, stated explicitly: a reader whose compiled walk lacks a feature computes requirement 0 and the read gate returns nil (persisted_ip.go:73-83) - the gate cannot reject any definition whose feature it cannot detect, and pre-fix binaries cannot be retrofitted (HEAD's mappings all cap at MORPCVersion130 while `MORPCLatestVersion = MORPCVersion131`, defines/const.go:168-170, so no existing bit can reject on such a reader either). The per-definition persisted requirement exists only for VIEW/CTAS targets (`builder.persistedViewTarget` creates the accumulator, bind_context.go:62-65; `observeExpressionProtocol` folds each bound expression into it, persisted_ip.go:185-210; the view requirement is picked up at build_ddl.go:273-290).
- **Floor state and transport.** The floor lives in HAKeeper replicated state: `handleActivatePersistedExpressionProtocol` commits `s.state.PersistedExpressionRequiredProtocolVersion` (view_metadata_admission.go:588-613), and the committed value is monotonic - an activation command targeting a lower floor is dropped (:597-598). It reaches CNs only inside the admission snapshot (`ViewMetadataAdmission.PersistedExpressionRequiredProtocolVersion`, proto/logservice.proto:700-713, produced at view_metadata_admission.go:845), where each CN publishes it into runtime globals: the durable READ floor early - while the snapshot is still Preparing - and the AUTHORING floor only after the epoch fence, the catalog fence and the local fence commits succeed (server_view_metadata_admission.go:60-66, 168-175, 216-243).
- **Activation timing (upgrade raises the floor before any new definition can exist).** When the enabled state lags the running binary (`RequiredProtocolVersion < MORPCLatestVersion` or a pending activation), the log-service store proposes the activation command at the new binary's `MORPCLatestVersion` (store.go:1170-1176); the initial enable waits until every live CN advertises at least that protocol version (store.go:1131-1146); and the CN authoring gate refuses with the typed NotSupported error while the enabled/admitted/catalog-fenced snapshot or the binary's own protocol version is below the requirement (persisted_ip.go:247-282). A definition using the new operands therefore cannot be authored until the raised floor is committed, the pending-activation authoring closure across all live CNs has lifted (every below-floor CN upgraded, or its heartbeat gone stale - which is an ADMINISTRATIVE release with no shutdown evidence, Section R2), and any below-floor binary joining or restarting meanwhile is fail-closed at start.
- **CN admission rejection and the already-serving transition (R1 scope split).** A CN binary whose `MORPCLatestVersion` is below the snapshot floor rejects the snapshot with the typed NotSupported error ("requires persisted expression protocol version %d (local version %d)"), keeping a closed, poisoned snapshot with the authoring floor cleared - "until it is upgraded" (server_view_metadata_admission.go:134-158). The scope of this closure is TWO-PART, and revision 5's "serves no SQL at all" wording is corrected: (1) JOINING/RESTARTING binaries are fail-closed - the poisoned snapshot is observed by startup/readiness consumers, and `viewMetadataIngressReady` opens only at admission completion (server_view_metadata_admission.go:432/:487; the TestServiceStart* family), so a below-floor binary cannot complete start and never opens ingress. (2) For a CN ALREADY SERVING when the floor raises, generation revocation (`revokeViewMetadataGeneration`, server_view_metadata_admission.go:251-285: ingress false, pipeline admission closed, queryWork beginClose, frontend/task-runner stop, async full Close) IS NOT triggered by the floor - it is invoked only in the strictly-newer-generation branch (:127-133) - so the same-generation future-floor heartbeat response merely poisons the snapshot, clears the authoring floor, and returns a typed error that the heartbeat handler only LOGS (server_heartbeat.go:303, :314-316). Its established direct sessions therefore stay open. What the supported rollout instead closes while the heartbeat stays FRESH: `persistedExpressionProtocolReady` (view_metadata_admission.go:146-160) keeps the activation PENDING, so every CN receives a preparing/pending snapshot whose `persistedExpressionAuthoringSnapshotReady` is false (:226-239) and whose application clears the authoring floor on EVERY CN - the expression-level authoring gate refuses cluster-wide (typed NotSupported, floor 0/below requirement); the below-floor CN's own rebind safety during this window is only VACUOUS (no new-operand definition exists anywhere to rebind, because authoring is closed) - its read gate provides no independent protection, since it recomputes requirement 0 from its pre-fix walk for any new-operand expression (persisted_ip.go:73-83, R2); HAKeeper advertises it not-ready in cluster details so new routed connections are excluded, and its routing entry is removed by the expiry barrier - an administrative release implying nothing about its process or sessions (R2: the governing closure is the verified process retirement prerequisite, not expiry).
- **Recovery and restore boundaries (R2: expiry versus verified shutdown).** HEARTBEAT EXPIRY IS NOT SHUTDOWN EVIDENCE. The release of the pending activation on expiry is pure tick arithmetic (`commandDeliveryStoreExpired(store.Tick, s.state.Tick, timeoutTicks)`, view_metadata_admission.go:146-160); a CN whose heartbeat send fails only logs and returns (server_heartbeat.go:290-296) and keeps serving its established direct sessions; the same-generation future-floor rejection clears only its authoring floor, leaving its ingress and its read floor at their last accepted values (server_view_metadata_admission.go:134-175); and its requirement-0 read gate passes a newly authored `CASE WHEN j` definition straight to the pre-change BOOL-vector `EvalCase` assumption (HEAD pkg/sql/colexec/evalExpression.go:1601-1604). Therefore: after expiry unblocks phase two elsewhere, an expired-but-serving old CN's surviving sessions CAN consume new-operand definitions, and routing withdrawal plus the non-revocation assertions close none of it (direct sessions, R1). **The load-bearing safe rollout prerequisite for THIS design** is operator-verifiable process retirement: retire every below-floor CN with VERIFIED process shutdown - stop the mo-service process, confirm the process exits, its frontends and established sessions drain with the frontend shutdown (the generation-revocation body stops frontends only on generation handover; process exit stops them unconditionally), and its listeners are released - BEFORE authoring new-operand definitions. The in-system signals compose as: (fresh below-floor heartbeat -> pending activation -> authoring closed cluster-wide) is a NECESSARY guard, and its release (upgrade, or stale ticks) is NOT sufficient by itself; the sufficient completion is that every below-floor CN binary has been upgraded or its process retired with the above verification. With the prerequisite honored, the expired path is unreachable: a retired process has no sessions and cannot re-read or execute anything; a healthy rollout upgrades all CNs first and authoring opens only after the last one. Reconnection case, recorded for completeness: a stale-then-fresh below-floor heartbeat re-registers the CN NotReady in cluster details and its next admission response re-poisons its snapshot and re-clears its authoring floor, but a completed activation is not re-closed by the reconnection (the activation handler runs on activation commands; the other CNs' published authoring floors do not retract) - so a merely-partitioned old CN must not be treated as retired, and the primitive that makes reconnection impossible is verified process shutdown (Section 9 class vi pins the deterministic sequence). No supported path lowers the committed floor - not DDL, not dropping the new definitions, and not restarting on older binaries (a below-floor binary restarted against the raised floor fails closed at start: it cannot serve the DROP/re-author sequence, which is why re-upgrade - not drop-and-re-author - is the supported rollback recovery; the authored definitions remain intact in the catalog). Restoring cluster admission state from before the activation restores the pre-raise floor, exactly as any other admission state; a logical dump re-authored on another cluster re-binds through that cluster's own gates at its own floor. This design adds no activation, transport, restore, floor-lowering or CN-fencing mechanics anywhere; it adds NO new mechanism for the expired-path either - the prerequisite is procedural, recorded here as the deployment contract, and pinned by the class (vi)/(vii) tests so a future change cannot silently assume the system closes what it does not.
