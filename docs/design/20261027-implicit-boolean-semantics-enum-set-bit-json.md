## 1. Problem, evidence, and invariants

### 1.1 Observed defects (facts, with evidence)

- **#30931 (ungrouped truth).** On the reported base `d4c37f4d` and the assigned base `5fe08a3307`, `IF(e,1,0)`/`IF(s,1,0)` return 0 for nonzero ordinals/masks, and `WHERE e`/`WHERE s`/`e AND 1` fail with `ERROR 20301 "invalid input: 'a' is not a valid bool expression"`, while `e+0`/`s+0`/`IF(e+0,1,0)` are correct.
- **#30931 (grouped).** Above `GROUP BY`, truth re-read display text; for declarations whose ordinal-0 sentinel and a valid member display identically (`ENUM('')`, `SET('')`), grouped truth cannot distinguish them, and base silently merges rows MySQL keeps separate (recorded INSERT..GROUP BY 2 -> MySQL duplicate-key 1062).
- **#30930.** `b'1'`/`b'0'` BIT value literals evaluate through the raw-byte text truth path instead of their numeric payload; BIT columns stay with #30922.
- **#30932.** `IF`/`CASE WHEN` reject JSON scalar conditions MySQL accepts; the table-path CASE evaluator cast branch condition vectors to `[]bool` (panic/error when a T_json condition vector reached it).
- **Probe-confirmed preserved-binary defects** (revision-2 receipts, the pre-repair red baseline): F1 - `WITH ROLLUP` merges the empty-label groups and returns IF=0 on all rollup rows incl. active groups (non-rollup control correct 1/0/1); F2 - `WHERE j`, `j AND 1`, `CAST(j AS BOOL)`, `j IS TRUE` error 20203 [JSON -> BOOL] on non-ParseBool strings while IF/CASE return the conditional vector; F4 - `IF(CAST('"1e309"' AS JSON),1,0)` returns 0 (overflow folded to false); F5 - cross-block `IF(v,1,0)` returns 0 for the ordinal-1 ''-group (same-block truth 1) and 1 for 'a'.

### 1.2 Invariant (revision 4; Section 7 ownership corrected in revision 5, fence removed and rescoped to the same-binary contract in revision 9)

> In a MySQL-compatible boolean context, the truth of an ENUM/SET/BIT-literal/JSON
> operand derives from its **stored payload**, never from display text:
> - ENUM: stored ordinal != 0; SET: stored bitmask != 0;
> - BIT value literal: uint64 payload != 0 (genuine strings keep raw-byte text truth);
> - JSON **in IF and CASE WHEN conditions only** (#30932 scope): conditional numeric
>   truth - numbers compare against zero by exact stored value, strings use the
>   shared decimal-prefix scanner with saturating overflow BELOW the
>   extension-dispatch boundary (Section 8/D9), JSON null and SQL NULL select the
>   ELSE branch;
> - JSON consumers outside IF/CASE conditions keep their pre-change behavior
>   cell-for-cell, and the strict `jsonScalarToBool` kernel remains the JSON
>   BOOL-target cast path;
> - the BOOL-target explicit CAST of ENUM/SET/BIT is defined by this design as
>   storage-payload truth (MySQL defines no BOOL cast target; Section 3);
> - the invariant survives the grouping boundary with the D6 activation contract
>   and the D10 materialized-boundary contract;
> - the invariant holds on SELECT planning AND on every persisted-expression
>   authoring/evaluation path (generated columns, defaults, CHECK, ON UPDATE),
>   which reach execution through catalog metadata, not streamed plans (Section 7);
> - every new admission, rewrite, kernel branch, and the grouping-identity
>   construction itself are gated on one statement compatibility scalar resolved
>   from the session's `MatrixOneNativeMode` flag and carried on BOTH owners -
>   the BindContext (SELECT path) AND the `ddlExpressionContext`-attached setting
>   (DDL expression binders) - so MatrixOne-native sessions keep pre-change
>   behavior everywhere (Section 3.3/D11).

### 1.3 Goals, non-goals, assumptions

**Goals.** Restore MySQL boolean semantics for the three members per the issue acceptance checklist; keep JSON strictness, JSON outside IF/CASE, and text semantics unchanged; keep ENUM/SET display output unchanged; define BOOL-target casts coherently; keep native-mode behavior byte-identical to base on every authoring and evaluation path; obey the repository's shutdown-only upgrade contract for remote and persisted expression consumers - same-binary workers and rebinders, with no per-feature protocol version, gate extension, or fallback path (upgrade-compatibility.md), and close the one supported hazards surface, same-version cross-mode consumption of persisted definitions.

**Non-goals.** BIT columns (#30922); conditional JSON semantics outside IF/CASE; changing native-mode behavior; grouping numeric consumers; MySQL-parity for cross-block truth over ambiguous declarations (zone 3 fails closed; R3 ordinal-carrying materialization is the recorded future generalization); an EXPLAIN surface for hidden keys.

**Assumptions (verified).** ENUM/SET bind as a display call over the stored expression; SET storage is physical `uint64`, ENUM storage `T_enum`; no wire/catalog/persistence/protocol-version changes occur: the repository's upgrade contract is shutdown-only (upgrade-compatibility.md) - peers inside one cluster always run the same binary - so remote workers and every persisted-expression rebind are same-binary consumers, the pre-existing feature->version table and its gates are NOT extended for this feature (existing gates stay untouched pending a dedicated cleanup PR, and the HAKeeper admission floor is neither raised nor consulted by this design; revision 9 supersedes the revisions-2..8 minted-slot assumption, which defended an unsupported mixed-version deployment mode and triggered exactly the durable floor-raise/admission machinery that contract forbids); the planner can read the session's native-mode flag (`builder.compCtx.GetProcess()` -> `GetSessionInfo().MatrixOneNativeMode`, and for DDL binders the same flag through the CompilerContext inside `ddlExpressionContext`).

### 3.1 One matrix: type x context x compatibility mode

| Operand (MySQL mode) | IF/CASE condition | WHERE/HAVING/ON predicate | AND/OR/XOR/NOT/IS TRUE/IS FALSE/IN | Explicit `CAST ... AS BOOL` |
| --- | --- | --- | --- | --- |
| ENUM (display or direct) | storage-truth ordinal != 0 (sibling-slot routed above GROUP BY; D6 joints) | storage-truth ordinal | storage-truth ordinal | storage-truth ordinal: MySQL has no BOOL cast target, so this design defines the BOOL-target cast to match the boolean contract; native mode reverts to prior behavior |
| SET (display or direct) | storage bitmap != 0 | storage bitmap | storage bitmap | storage bitmap != 0 (same rationale and mode gate) |
| BIT value literal (`b'...'`) | payload != 0 | payload != 0 | payload != 0 | payload semantics for the BOOL target; other cast targets keep prior numeric-cast semantics |
| JSON scalar | **conditional kernel (D9)**: numbers vs 0 by exact stored value; strings via the shared decimal-prefix scanner with saturating overflow, NO extension dispatch (hex/binary/octal and NaN/Inf-prefixed text have no numeric prefix -> false); true literal true; false/''/'abc'/'true' string variants false; JSON null and SQL NULL -> ELSE | **pre-change behavior** (preserved-binary strict [JSON -> BOOL] cast errors on non-ParseBool values, probe 1; base-parity is a planned F2 oracle) | **pre-change behavior** (not yet probed on base; F2 oracle) | **strict kernel** (preserved-binary path is `jsonScalarToBool`, probe 1; admission parity with base is an F2 oracle) |
| VARCHAR/text | existing numeric-prefix text truth (mode-dispatched today) | unchanged | unchanged | unchanged (including the extension-candidate hex/binary/octal and NaN/Inf behavior of general string->numeric casts, which D9 does not alter) |

**Where the matrix is enforced.** Admission sites: `iffCheck`, CASE condition typing, the boolean-argument implicit-coercion rules, and the boolean-context rewrite in `appendCastBeforeExprWithOverload` (base_binder.go:12044-12052). These sites are shared by ALL binders - SELECT planning, generated columns, defaults, CHECK, ON UPDATE - because standalone DDL binders call the same `baseBindExpr` binding path with a context they own (Section 3.3). One matrix therefore governs every authoring and evaluation surface.

### 3.2 Truth kernels

`IffConditionTruthyAt(vec, row, mode)` remains the single per-row evaluation point; the T_json branch calls the conditional kernel (D9) **only through IF/CASE condition positions** and consults the mode; the colexec `EvalCase` keeps the per-row JSON branch (evaluated by the same binary's remote workers and persisted-expression rebinders under the shutdown-only upgrade contract, with its catalog-bound session-mode boundary enforced by the retained cross-mode consumption gate, D8 rev 9, Section 7); text keeps the existing `parseBytesToFloat` prefix truth with its existing mode dispatch - unchanged.

### 3.3 D11 mode propagation: both carriers (revision 4, fixes H2)

The statement compatibility scalar is resolved ONCE from the session flag the executors read (`proc.GetSessionInfo().MatrixOneNativeMode`; `CompatibilityModeFromProcess`, func_cast.go:7563-7568, is the executor-side read) and carried on TWO owners:

## 7. Remote and persisted expression contracts (D8; rev 9 removes the revisions-2..8 version fence under the repository's shutdown-only upgrade contract)

**Governing repository contract (round-9 finding P2, verified).** `.agents/skills/mo-dev/references/upgrade-compatibility.md` (lines 13-40): MatrixOne supports **shutdown upgrade only** - stop every service in the cluster, replace the binaries, start the cluster; rolling upgrade, mixed-version serving, and downgrade are all unsupported. "Peers inside one cluster always run the same binary", therefore: do not add a per-feature `MORPCVersion` constant, bump `MORPCLatestVersion`, or gate a feature on `AllCNsSupportProtocol`, a heartbeat-reported protocol version, or any other "all peers support X" capability check; do not add legacy encode/decode paths, neutral fallbacks, or downgraded plans for an older peer ("a new or changed proto field, plan node, operator, table function, function overload ... needs no version gate"; "An old CN would not understand this" is not a finding); existing gates stay until a dedicated cleanup PR removes them and must not be extended for new features; a version bump is reserved for framing/handshake changes (so a misconfigured mixed deployment fails at connect instead of corrupting data) or an explicit project-level design decision reintroducing supported mixed-version operation, and "adding features, fields, operators, or functions is never by itself a reason to bump". `feature-design-review.md` section 3 records the same boundary for design review. What remains hard compatibility is what that contract enumerates - persisted state a new binary must read (catalog rows, TAE formats, WAL records, persisted views/plans/expressions), upgrade steps, backup/restore, and external boundaries - not per-feature version fences.

(b) Persisted expressions reach execution through catalog metadata rather than streamed scopes: generated-column authoring binds and persists the expression through the catalog (build_util.go:1230-1264), CHECK authoring runs the same standalone-DDL binder path (build_ddl.go:4779-4794), DML rebinding copies the persisted expression into execution plans (bind_insert.go:2943-2953), and VIEW/CTAS targets persist their per-definition requirement through the pre-existing accumulator (bind_context.go:62-65; persisted_ip.go:185-210; build_ddl.go:273-290). **Shutdown-only coverage for persisted state (the contract's actual obligation, closed by the mode contract).** A new binary must read everything an older binary wrote: base REJECTS persisted ENUM and in-domain T_json boolean-condition authoring outright (probe receipts: F8 block F "invalid argument function if, bad value [ENUM BIGINT BIGINT]", F2's bind-time JSON consumer errors), so no pre-existing catalog definition contains the new-condition forms; SET persisted conditions run on kernels unchanged by this fix (F8); and every legacy persisted definition reachable before this fix (for example a BIT value-literal in an IF/CASE condition, or an ENUM display cast feeding numeric consumers) is re-bound by the new binary with the corrected storage-payload truth in MySQL mode - the intended defect repair - while native mode keeps byte-identical base kernels (D11), so both session modes evaluate every legacy definition with the semantics each session promises, exactly as they do for newly planned statements.
