# Session-dependent virtual generated columns (issue #28140)

## Contract and scope

For a SELECT against a base table, a virtual generated column whose expression depends on a TIMESTAMP must have the value obtained by evaluating its declared expression in the SELECT session. Predicates, grouping, ordering and joins use that same value. A secondary index containing such a column cannot determine membership or supply a covering value: its key was materialized by a writer in another time zone. A base-row scan with a residual expression is the safe access path, including for FORCE INDEX.

This repairs the reported nonunique `KEY kd(d)` SELECT and lookup. STORED generated columns keep their write-time value. Stable virtual columns and their indexes keep the existing fast path. The physical value of an affected virtual column remains a write-time cache for DML and storage; existing UNIQUE constraints on it continue to use the writer's time zone and cannot provide session-dependent uniqueness. That constraint is outside this SELECT correction and must be addressed by a separate DDL/catalog compatibility design before the engine claims general indexed virtual-column semantics.

## Design

Classify columns per table during planning. An affected column is virtual and its expression references a TIMESTAMP base column or another affected virtual column. A stored generated dependency is a physical leaf. Traverse expression trees with column-ordinal bounds and cycle checks; malformed catalog expressions must never recurse without a bound. Memoize classification by column so a shared generated-column dependency graph takes linear classification work. Classification is conservative: false positives cost a base scan, never change results.

At base-table column binding, replace an affected virtual reference with a deep copy of its generated expression. Remap its row-local column references to that scan's binding tag and recursively substitute affected virtual dependencies. Preserve the declared assignment cast already present in the catalog expression. For an outer reference (`depth > 0`), remap each expression leaf to a `CorrColRef` at the same depth; never insert an ordinary scan-tag `ColRef` into a nested query. The rewrite applies only when the binding resolves to a base `TABLE_SCAN` with the expected tag. Derived table, CTE, and view bindings expose their already computed projection, so a second substitution would be wrong. SELECT branches within INSERT SELECT and CTAS use the same read contract; UPDATE/DELETE internally project the persisted old generated value for index maintenance while user WHERE predicates keep read-time semantics. The ordinary optimizer and executor then evaluate the expression for projection, WHERE, JOIN, GROUP BY, ORDER BY and prepared statements, using the execution session's time zone.

Expression inlining can grow exponentially in a compact dependency graph. Bound the expanded read expression to 65,536 nodes. Compute prospective expanded node counts with dynamic programming over the complete resulting table graph, saturating at the limit. Validate **every affected virtual column** after CREATE and after all COPY/INPLACE ALTER actions, including an unchanged descendant made newly affected by an upstream expression/type/ordinal change. Stable virtual dependencies are physical leaves and do not inflate this count. Reject a resulting schema above the limit with a named table/column error. The same bound remains a read-time guard for malformed or historically oversized catalog definitions; a read of an old oversized column returns an explicit unsupported-size error rather than OOM or an incorrect physical value.

Ship a read-only preflight tool that queries the system account's `mo_catalog.mo_columns` in one consistent transaction, across all accounts, tables, and hidden functional backing columns. Decode the persisted type/generated-expression metadata and use the same planner classifier/count. Missing or undecodable metadata must fail closed; report account/database/table/column and cost for every oversize finding. Operators must freeze relevant DDL, rerun the preflight immediately before the all-CN cutover, and retain its zero-finding receipt. Any oversize finding blocks corrected-contract activation until the table owner approves a semantics-preserving application/schema rewrite, or the upgrade is deferred; a generic automatic STORED conversion is not safe. Rolling back returns old semantics and requires a new preflight before retry. This is a deliberate rollout gate for historical catalogs, not a claim that the planner can evaluate every formerly accepted deep dependency graph.

Use one eligibility predicate on `(TableDef, IndexDef)` that checks **every** index part after resolving aliases. Apply it wherever an index can be admitted, not merely on the leading part. The call-site audit must include regular filter lookup/range and index-only access, `FORCE INDEX` for JOIN/ORDER/GROUP and hinted backfill, join access, master/spatial candidates and functional-index predicate synthesis. Defense at both candidate collection and final access construction prevents a direct caller from bypassing the guard. Validate index names before eligibility filtering so a misspelled hint remains an error. An unsafe FORCE INDEX falls back to the base scan; it must not pick a different unforced index. Do not mutate the shared catalog TableDef. Keep the base-row predicate as a residual, so index avoidance cannot remove the actual evaluation.

## Validation

Use a timestamp on a UTC day boundary. Insert at `+00:00`, read at `+08:00`, switch back, and compare `d` with `DATE(ts)` in projection and filtering. Compare default, FORCE INDEX (including JOIN/ORDER/GROUP scopes) and IGNORE INDEX, and inspect the plan to confirm no stale index access. Cover a control STORED column, a stable virtual index, dependent columns, NULL, cross-zone UPDATE/DELETE, correlated predicates, INSERT SELECT, CTAS, view reads, and a prepared query executed after a time-zone switch. Test a stable shared-dependency DAG for linear classification, affected DAGs just below/above the expansion limit for CREATE and ALTER admission, historical oversized read error, and preflight's complete/incomplete catalog cases. Run on the remote development machine. Keep a planner unit test for classification and index eligibility to catch an access-path regression.

## Operational limits

No catalog or storage format changes are required for the SELECT repair; old physical keys remain but are ignored by affected SELECT plans. This is a planner behavior change: rolling/mixed-CN deployments can return different SELECT results from upgraded and old nodes. No CN routing or admission mechanism is added here, so the corrected SELECT contract begins only after all serving CNs are upgraded. Prepared plans from old CNs must be invalidated/reprepared at the all-upgraded boundary; connection restart is a sufficient operational way to do that. Rolling back a CN restores the old wrong reads until all serving CNs are upgraded again and prepared plans are recreated. State this operational boundary in the PR.

Scan fallback can be substantially slower than the prior (incorrect) lookup on large tables. Before PR, compare the new indexed-table query at 10,000 and 100,000 rows against an explicit `WHERE DATE(ts)=...` full-scan control on the same data. The median of three warm runs should stay within 2× that control and peak query memory within 20%; otherwise profile and either correct an avoidable regression or record a specific capacity blocker before delivery. Verify an unaffected stable virtual-index query still uses its index. The old wrong point lookup is recorded for context, not a performance acceptance target. This trades point-lookup latency for correct results. DDL rejection alone would leave existing rows and queries wrong; a full virtual-column storage redesign would resolve more cases but requires catalog, uniqueness and mixed-version changes beyond this issue's nonunique SELECT contract. A safe later optimization could map `DATE(ts)` to TIMESTAMP ranges, with residual evaluation, NULL handling, and DST transition coverage; a write-time key rebuild cannot satisfy all session zones. Existing UNIQUE virtual indexes still enforce persisted writer-time values. SELECT must ignore those keys for access just like nonunique keys, but INSERT/UPDATE/ODKU can still reject or accept according to writer-time values. Do not present this change as fixing that contract; a separate versioned DDL/index policy is needed for true session-dependent uniqueness.
