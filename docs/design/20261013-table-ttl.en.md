## Behavior

```sql
CREATE TABLE events (
    id BIGINT PRIMARY KEY,
    event_time DATETIME(6),
    payload VARCHAR(256)
) TTL event_time + INTERVAL 7 DAY DELETE;

SHOW CREATE TABLE events;
ALTER TABLE events MODIFY TTL event_time + INTERVAL 30 DAY DELETE;
ALTER TABLE events REMOVE TTL;
ALTER TABLE events TTL event_time + INTERVAL 1 WEEK;
```

`DELETE` is optional. The TTL column must be DATE, DATETIME or TIMESTAMP; NULL values are retained. SECOND, MINUTE, HOUR, DAY and WEEK are fixed-length intervals. The positive integer duration is bounded by 100 × 365 days. A row expires when `column + duration <= the invocation's fixed UTC time`. Equality expires the row; future values remain. Late expired inserts are accepted and processed by a later invocation.

DATE uses UTC midnight. DATETIME has no timezone and is interpreted as UTC wall time by TTL. TIMESTAMP follows the normal client-timezone conversion on insertion and is compared as an absolute time under the worker's UTC session. Microsecond precision is retained.

Expiry is asynchronous: rows remain visible until the DELETE transaction commits. Logical deletion does not promise immediate object/disk reclamation; existing MVCC, snapshot, PITR and GC retention rules still apply.

The first version supports permanent, ordinary, non-partitioned user tables. Temporary, external, cluster, partitioned and system tables are rejected, as are existing referenced FK parents. Ordinary DELETE continues enforcing constraints, including references added later. Source-column DROP, MODIFY, CHANGE and RENAME require REMOVE TTL first. TTL mutation must be a standalone ALTER. Unrelated COPY ALTER, table rename, SHOW CREATE reconstruction and CREATE TABLE LIKE retain the policy through the existing metadata paths. LIKE inherits TTL; REMOVE TTL explicitly disables it on the target.

The non-reserved `ttl` identifier remains usable as a table/column name, including `MODIFY ttl INT` and `MODIFY COLUMN ttl INT`. Unsupported syntax is rejected: calendar MONTH/YEAR intervals, fractional/negative durations, arbitrary expressions, conditional deletion, column TTL, rollup and storage movement.

## References and implementation choice

| Reference | Relevant behavior | Choice for this version |
|---|---|---|
| [ClickHouse TTL](https://clickhouse.com/docs/concepts/features/operations/delete/ttl) | Declarative expiry applied asynchronously during merges; additional column/move/rollup actions | Similar table-level declaration and eventual cleanup; no TAE merge rewrite in this version |
| [DuckDB DELETE](https://duckdb.org/docs/current/sql/statements/delete) | SQL deletion and CHECKPOINT reclamation are distinct operations | Reuse transaction DELETE and distinguish logical deletion from physical reclamation; do not assume an equivalent native TTL scheduler |
| [Snowflake storage lifecycle policies](https://docs.snowflake.com/en/user-guide/storage-management/storage-lifecycle-policies) | Automatically apply row expiry/archive policies in bounded incremental work | Persist the policy and bound background execution; no separate reusable policy objects or archive tier yet |
| [Snowflake policy expressions](https://docs.snowflake.com/en/sql-reference/sql/create-storage-lifecycle-policy) | Expressions select rows for expiry | Start with a bound temporal column and fixed duration to constrain dependencies |
| [InfluxDB retention](https://docs.influxdata.com/influxdb/v2/reference/internals/data-retention/) | Periodically reclaim fully expired shard groups | Adopt background eventual cleanup, retain row granularity for mixed-age objects |
| [Timescale retention](https://www.tigerdata.com/docs/reference/timescaledb/data-retention/add_retention_policy) | Scheduled removal of older chunks | Leave fully expired partition/object reclamation as an optimization follow-up |

Snowflake lifecycle expiry is distinct from Time Travel retention. MatrixOne TTL likewise does not replace snapshot/PITR retention. Snowflake's clone policy behavior differs from this version's explicitly documented LIKE inheritance.

Using normal DELETE first preserves the existing index, FK, MVCC and transaction paths. It adds scanning and locking cost and does not fulfill the issue's partition fast-drop or large-volume performance objective. The PR associates the initial implementation with #24552 without closing the broader issue.

## Metadata and lifecycle

A versioned `mo_ttl` JSON property is carried by the existing StreamConfigsDef encoding in `mo_tables.constraint`; there is no new catalog table or SchemaExtra field.

```json
{"version":1,"column":"event_time","seqnum":1,"seconds":604800}
```

CREATE binds the sequence number assigned by physical column order. ALTER binds the catalog identity. Unknown versions/fields, malformed metadata and duplicate policies fail closed. Plan deep copies, protobuf serialization, catalog reconstruction and restart retain the policy. SHOW CREATE emits a native TTL clause and excludes the internal property from PROPERTIES. ALTER reuses ReplaceDef/UpdateConstraint, publishing constraint updates only when TTL changes.

CN registers a `TableTTL = 17` executor and the `table_ttl` cron through the existing task framework and stopper-owned registration retry/cancellation. Task metadata limits scheduling concurrency to one; transactional revalidation still protects duplicate invocations.

| Default | Value |
|---|---:|
| Cron | `0 * * * * *` |
| DELETE batch | 1024 rows |
| Batches per table per invocation | 8 |
| Per-table budget | 5 seconds |
| Invocation budget | 50 seconds |
| Lock wait | 1 second |
| Whole-transaction retry attempts | At most 8 with bounded backoff |

These are code defaults in `pkg/sql/ttl/worker.go`, with WorkerOptions available to internal callers/tests. There is no new SQL/session/config tuning surface. Scheduler delay, contention and backlog make this an eventual progress mechanism, not a fixed completion SLA.

Each batch:

1. Provisional system-account discovery records the tenant, physical table ID, version, names and policy-bearing constraint bytes. Checked lengths skip unrelated index/FK messages without unchecked allocation.
2. The invocation fixes its UTC time and uses the bounded discovery window and task-owned continuation below.
3. A new pessimistic RC transaction in the target tenant obtains the table lock, then revalidates the tenant, physical ID, schema version and complete constraint bytes.
4. It checks the source name, sequence number, hidden flag and the catalog's **serialized** type encoding.
5. It performs `DELETE ... WHERE column <= CAST('fixed cutoff' AS DATETIME(6)) LIMIT batch_size`, commits and waits for logtail application.
6. Transient RC failures restart the entire transaction and all metadata checks. `errors.As` recognizes retry errors and local/remote lock-wait timeouts wrapped by the executor's rollback result. A lock timeout restarts the whole transaction instead of continuing the aborted transaction. Permanent failures and cancellation propagate. Other tables can still progress.

The locked revalidation query projects the current constraint only when its byte length equals the credited candidate constraint; a NULL/different-length result invalidates the candidate. Intervening metadata growth therefore cannot bypass the discovery bound through revalidation.

A same-name DROP/CREATE, policy change, rename or schema-version change invalidates the old candidate. The exclusive table lock briefly serializes same-table writes and DDL during the bounded batch. There is no per-table resident goroutine or query-time expiry filter. Discovery visits bounded pages of user-table metadata; 8192 rows per table per invocation is a count ceiling, not a measured throughput guarantee.

## Discovery resource owner and fair continuation (2026-10-14 amendment)

The review of `b65fa0d` identified a concrete resource gap: non-streaming `Exec` retained all catalog result batches while discovery cloned complete constraints into a growing Go slice. Cancellation at result handoff did not stop that copy. DELETE limits and deadlines cannot bound that memory owner.

The invariant is now: discovery owns at most one bounded catalog page, a finite credited candidate window, and bounded diagnostics. Cancellation never returns a partially discovered window or publishes its continuation. The scheduled executor owns one fixed-size continuation and one non-waiting admission token; it never accumulates per-table resident state.

| Resource | Default hard ceiling / owner |
|---|---|
| Catalog page | 128 rows; one `executor.Result`, closed before the next page and on every error/cancel path |
| Pages per invocation | 4, including an empty terminating page; one additional fixed-width high-water query |
| Returned constraint per row | 16 KiB, enforced by SQL `CASE WHEN LENGTH(constraint) <= limit THEN constraint ELSE NULL END` before the executor collects results |
| Database/table/source-column names | 256 bytes each; catalog name projections are also capped before result materialization |
| Page logical variable-width payload | At most 128 × (16 KiB + 2 × 256 bytes), plus fixed numeric/vector bookkeeping; independent of catalog cardinality |
| Candidate window | At most 32 entries and 128 KiB of conservative allocation credit: `512 + 2 × (constraint + database + table + policy-column byte lengths)` per retained entry |
| Diagnostics | At most eight samples with 128-byte error details plus a count of omitted errors; final task error text remains below 2 KiB |
| Continuation/admission | Two `(account_id, rel_id)` pairs, one active-cycle flag, one capacity-one non-waiting token; owned by one registered task-executor closure |

Internal discovery options may lower these ceilings for focused tests; they cannot raise them. An entire-window oversized candidate, oversized metadata/name, or malformed row is skipped, counted and reported without retaining raw bytes or an unbounded underlying error chain. A row that only exceeds the *remaining* candidate credit is left for the next invocation. Non-TTL rows consume the same finite page/count budget and advance the scan, without entering the retained candidate window.

At the start of a scan cycle, a fixed-width `ORDER BY account_id DESC, rel_id DESC LIMIT 1` query captures an upper key. Page queries use keyset predicates `after < (account_id, rel_id) <= upper`, ascending order and `LIMIT`; they never use OFFSET. The upper fence prevents ongoing creation of higher-key tables from extending the current cycle indefinitely. Earlier-key inserts or policies newly attached to already passed rows are visited in the next cycle. Dropped tables are harmless; each DELETE still revalidates identity/constraint under its tenant table lock.

The window records the last consumed catalog key and whether the fenced cycle ended. After each completed table attempt, the task commits its continuation to that candidate's key. It advances to the window's final catalog key (or resets at cycle end) only after every retained candidate was attempted. A run deadline or cancellation therefore cannot jump over unattempted candidates. A completed per-table timeout/permanent error advances fairly to the next table; that table is retried in the next cycle. Discovery errors retain the previous task continuation. The cursor is in memory, not new durable catalog state: CN restart or task migration starts a new scan from zero. Fair progress assumes an executor remains assigned long enough to complete a finite fenced cycle; there is no cross-restart SLA or durable cursor claim.

Cancellation is checked before queries, immediately after result handoff, between batches/rows, inside binary item decoding and after policy decode. Every acquired result is immediately covered by cleanup. Retained catalog-name and constraint copies are made only after candidate credit admission; the one-row policy decoder has a separately bounded 16-KiB input, and its temporary decoded column is admitted into the candidate only after the credit check; results are closed before deletion begins. The admission token rejects a duplicate invocation immediately instead of waiting behind the 50-second data path, and is released on every terminal path. The task framework still enforces scheduling concurrency one.

These are TTL-owned materialized-output, retained-candidate and diagnostic bounds, not a new hard process-RSS or storage-I/O quota. The engine's scan/Top-N buffers, native query admission, caches and reading one stored record follow existing MatrixOne resource controls. Keyset pagination can still scan metadata without a suitable catalog access path; each query remains deadline-bound. Increasing resource limits, a TTL-specific catalog index, durable continuation and metrics are separate work.

Alternatives considered: (1) retaining the all-table query with only a deadline fails the demonstrated memory invariant; (2) a credited streaming executor could bound live result batches, but needs a new producer/channel cancellation and credit protocol and still requires a cursor to avoid replay under a deadline; (3) bounded keyset queries reuse the executor's existing result owner, cap its emitted values and need only constant task-local state. Select (3) for V1. OFFSET paging was rejected because concurrent catalog mutation can shift rows and scan cost grows with the offset.

Deterministic acceptance map:

- Cancel at completed-result handoff: no candidate escapes, continuation stays unchanged and the result pool returns to zero; use the review's 32/64-row controls.
- Small page/page-count and candidate-count/byte limits: assert exact selected/consumed keys, page release before the next query, bounded clones and continuation over later rows.
- Many non-TTL rows followed by a TTL row: repeated bounded windows reach the policy without retaining non-TTL metadata.
- Oversized/corrupt rows and long error text: bounded diagnostic samples, no uncredited candidate, and later keys remain reachable.
- Upper-fence and wrap: new higher keys do not extend the cycle; earlier inserted keys are visited next cycle; account boundaries use the compound key.
- Timeout during table processing: completed earlier candidates advance; unattempted candidates remain reachable. Duplicate/canceled task admission and sequential reuse are race-tested with barriers, not sleeps.
- Existing real-storage TTL tests verify generated catalog projections/keyset SQL, DELETE revalidation, tenant behavior and cron/restart. No scale-throughput or whole-process RSS assertion is claimed by these functional tests.

## Deployment and remaining work

Use homogeneous TTL-capable CN builds. Older CNs cannot parse the syntax or run the new executor; an independent cluster protocol capability fence has not been added. Validation covers one real CN with transactions, indexes, tenants and restart. Multi-CN/TN failure injection, clock drift, large-backlog throughput and disk reclamation speed are not validated claims.

Follow-ups include configurable scheduling/batch size, backlog/progress metrics, temporal-index scans, fully expired partition/object reclamation, defined calendar MONTH/YEAR semantics, conditional TTL, source-column dependency rewriting, archival/rollup actions and a cluster rollout fence. Those capabilities are outside this initial implementation.
